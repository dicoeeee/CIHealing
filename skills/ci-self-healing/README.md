# CI 自愈 Skill

本 Skill 诊断具体 CI 失败，在授权范围内修改代码或构建配置、执行验证并交付报告。适用于确定性的代码、测试、依赖和构建问题；已确认的 Flaky/基础设施恢复、合并、部署和生产事故处置不在默认范围内。

**本 README 用于让 AI 根据企业实际情况完成配置。** 配置时按下方流程选择所需资源；日常诊断、分类、修复和报告只遵循 [SKILL.md](SKILL.md) 及其引用的执行资源，不把维护模板作为运行指令。

已有企业故障分类表时，可从[企业分类与处置方式](#企业分类与处置方式)开始。需要 AI 协助整理企业材料时，使用下方的[配置请求示例](#让-ai-完成配置)。

主流程由 `SKILL.md` 统一安排。定制 reference 时保留局部知识、操作顺序、判断规则和结果说明，不在其中增加跳转主流程步骤、恢复自愈或直接结束调用的指令；局部失败只说明缺口与受限动作。

#### 企业分类与处置方式

**准备分类表。** 在企业 Profile 入口写明标准 ID、版本、适用产品或仓库，列出类别编号、名称、父类、确认判据和可选的 **处置方式**。企业已有分层目录时，保留原编号和层级，详细判据可链接到现有细则。Skill 从失败步骤、命令、报错及相关上下文自行判断小类，上游只需提供现场证据。症状已满足判据时即可分类，原因型小类再按需核对源码、配置或其他证据。[目录与细则模板](docs/enterprise-configuration.md#1-准备目录与细则)

下面以制品上传和公共契约问题为例。空白单元格表示该类别未指定处置方式。

| 编号 | 类别 | 父类 | 确认判据示例 | 处置方式 |
| --- | --- | --- | --- | --- |
| U | 制品上传失败 | | 上传步骤返回失败，可定位发布命令 | |
| U.1 | 机器账户认证被拒 | U | 上传请求返回 401，服务端记录本次机器账户认证失败 | `case_lookup_only` |
| U.2 | 制品坐标配置错误 | U | 发布命令使用的坐标与当前产品约定不一致 | `standard_flow` |
| C | 公共契约变更 | | 失败项指向本次变更涉及的公共契约 | `diagnose_then_handoff` |
| C.1 | 公共接口兼容性冲突 | C | 消费方调用的旧签名与当前发布接口不兼容 | |
| C.2 | 共享依赖版本冲突 | C | 本次依赖契约变更后，两个组件对同一共享依赖的版本要求无交集 | `diagnose_then_handoff_with_cases` |

**选择处置方式。** 企业按小类选择下表中的原样枚举。子类各有处置要求时可将父类留空。修复权限、禁修范围和审批要求由企业修复策略另行声明。[主流程选路规则](SKILL.md#按小类选择处置方式)

| 处置方式 | 确认小类后，Skill 对当前问题执行什么 |
| --- | --- |
| `standard_flow` | 进入通用诊断，按证据、企业策略和授权决定能否修改、怎样验证，或是否需要转人工。 |
| `case_lookup_only` | 用分类证据和报错直查绑定案例源，交付实际返回或未查到的原因。跳过通用根因诊断、试修及候选验证。 |
| `diagnose_then_handoff` | 做只读诊断，交付失败操作和证据、已经确定的结论或缺口、接手角色及下一步。跳过查库、试修和候选验证。 |
| `diagnose_then_handoff_with_cases` | 按相同条件完成只读诊断，再有限检索绑定案例源。随交接材料附上实际结果或无法检索的原因。跳过试修和候选验证。 |

**继承与缺口。** 小类确认后，从该小类向上取最近的非空值。例中 C.1 继承 C 的 `diagnose_then_handoff`，C.2 用自己的值。整条路径都留空或旧表没有“处置方式”列时，使用 `standard_flow`。有分类义务却只确认到 C 时，先按判据补证，仍无法确认小类就保留 C 和所缺证据，暂停该问题。已确认路径取到拼写错误等未知值时，报告类别、原值及允许值，暂停该问题，交由配置维护者更正。

**同一失败符合多个小类。** 企业在判据中写清哪些小类允许共存。Skill 解析各条已确认路径后统一选路：有 `standard_flow` 就走常规流程，其次取 `diagnose_then_handoff_with_cases`。若同时出现直查与诊断后交接，也合并为诊断后附案例交接。其余沿用唯一取值。企业只需定义共存条件。若 A 已确认、B 仅有共存线索，B 是否成立都不改变流程时按 A 执行并保留 B 待定。会改变流程时定向补证，仍无结论就暂停当前问题。[共存判据与分类记录](references/failure-classification.md#判断与多类别关系)

**启用配置。** 在企业发行包创建实际入口后，替换 [SKILL.md 唯一绑定表](SKILL.md#自定义资源绑定)中的对应行。以下两行为示例，名称和路径应换成企业自己的值，其他绑定沿用。固定 Profile 后，每次诊断或修复都要按该标准交付初始与最终分类，调用方无需逐次传入类别。既无固定 Profile、也无分类要求或指定时，直接走常规流程。

| 资源类型 | 固定 ID 示例 | 接入入口示例（相对 Skill 根目录） |
| --- | --- | --- |
| 分类 Profile | `my-company/my-product` | `references/my-product/profile.md` |
| 案例源 | `company/ci-cases` | `references/case-sources/company-ci.md` |

选用直查或附案例交接时，案例源接入说明写明企业 Wiki/RAG 的实例、授权范围、实际 MCP 工具或 CLI、搜索及按案例 ID 读原文的方式。可约定本源的关键词、查询顺序和结果不足时的调整条件。[案例源填写示例](docs/enterprise-configuration.md#企业案例库接入)

直查时，只要已绑定的来源可访问、权限和预算允许，就要在本次调用实际查库。同一调用对同一失败已有访问记录时复用。请求附旧案例且能在绑定源定位时，先按 ID 或链接读取，只有本次返回的条目计作命中。直查和附案例交接都按同一调用、同一失败累计检索预算，最多搜索 3 次、读取 3 篇候选原文，时间预算为 60 秒或宿主规定的更短时间。正常查询为空时可依现场证据调整，访问被拒则停止并保留已取得材料。[检索规则](references/case-retrieval.md#转人工前的检索流程)

### 3. 写入配置并准备可信启动输入

先核对下文的[企业运行方式](#4-核对企业运行方式)，确认本次配置与现有合同兼容，再在授权的 Skill 目录中按已确认材料完成配置；现有授权足够时不逐项重复确认。修改前说明文件范围，保留无关配置。新资源只在实际需要时创建，不生成整套空目录或带占位值的有效绑定。

- **分类与案例源**：先准备可读入口，再更新 `SKILL.md` 的唯一绑定区。ID 与入口声明一致，保留另一类型已有绑定。固定绑定是发行包选择；更换须属于本次维护请求，不能让运行中的自愈任务自行覆盖。
- **企业输出规范**：先准备实际产品的一份完整 Markdown，再在唯一绑定区填写 ID 和入口；可以使用 `references/enterprise-output-spec.md`，也可引用可信既有路径。不要直接绑定带占位值的维护示例；没有额外要求时保留明确未配置。标准报告不进入企业可变清单，文件位置由企业逐个写清。
- **企业策略**：用新声明替换原声明，不让“未配置企业附加策略”与有效规则并存。企业规则只增加限制和必要条件，其他通用准入与验证仍适用。
- **Provider**：接入文件存在不会自动选中。已知宿主启动配置位置且在授权范围内时更新它；否则交付待注入的命名输入并说明尚未接通，不发明启动配置文件或自动扫描机制。

Provider 启动输入示意如下，实际文件创建且身份确认后才替换为企业值：

~~~yaml
provider: company-ci
provider_reference: references/providers/company-ci.md
~~~

分类或案例源采用本次选择时，提供资源类型、实际 ID 和入口即可；已有固定绑定时遵循绑定与冲突规则。Provider、分类、案例和企业输出规范的入口相对路径以 **Skill 根目录** 解析，入口文件内的相对链接以该文件为基准。

| --- | --- |
| **双目录场景** | 修复调用同时提供 `work_dir`、`output_dir` 时，按无人值守 CI Job 在本地验证。企业核对现场日志、源码映射和执行目录。需要人工处理时，将原因、证据、接手角色和下一步写入报告，交齐报告及已绑定的企业文件后结束。即使宿主另有通用交接工具，本场景也以报告完成交接。[场景与交付](references/ci-job-failure-directory.md) |
| **宿主调用能力** | 核对宿主能否加载既有 `arguments` 扩展；不支持位置展开时使用 [可信命名输入](references/invocation-inputs.md)。执行角色、实际协作通道、权限和时间/计算预算由宿主声明；`max_attempts` 可降低，当前版本最多 5 次 |
| **业务知识与验证** | 需要内部语义、当前状态或专项验证器时，提供 [领域知识要求](references/diagnosis-and-repair.md#路由通用与企业知识) 中的来源、版本、范围、规则和实际工具。结合项目入口明确 [必要检查与通过条件](references/candidate-verification.md#分层验证)，分类目录或历史案例不能替代这些依据 |
| **产物与交接** | 普通编译产物可保留，宿主负责工作空间回收及 Patch 筛选、提取、打包和归档。Skill 按[工作空间约定](references/execution-modes.md)保护源码、核对候选与验证有效性，只声明已观察到的接手结果 |
| **另行远端验证** | 按 [远端合同](references/remote-verification.md) 落实专用候选 ref、发布/触发权限、准确候选对应的逐项检查和后续观察能力。只读日志接入不表示具备完整远端验证能力 |

若企业要求与现有合同不兼容，例如双目录调用需要交互式修复、分类只交付到大类，或必须更改报告结构，单列为 **Skill 行为改造需求**。完成可独立的配置，说明冲突和所需改造；不把改动通用流程、提高 Attempt 上限或弱化验证包装成已完成配置。

### 5. 检查并交付

先完成本次配置的静态检查：

- 入口文件与链接可读，ID/实例/范围一致，版本有来源或明确未知；模板占位值没有进入有效声明。
- 分类、案例源与企业输出规范只有一处固定声明，策略没有“未配置”与有效规则并存；本次未涉及的已有绑定保持不变。
- 按类别限制的策略与 Profile 版本、编号及父子关系对应；企业材料不足时保留具体缺口。
- 分类表中每个非空处置值都与四个枚举之一完全一致。选用查库分支时，核对实际案例源的绑定、只读访问能力及允许范围。
- 双参数接口、通用安全边界、案例建议分支和六章报告合同保持一致；未声明的工具能力不编造，文件中没有凭据或敏感原文。

然后按所选项的配置参考，在已授权环境中执行适用的接入验收。没有真实环境或授权时，交付静态结果与待验收项；不为完成配置自行安装工具、登录、连接服务、发布候选或触发 CI。文件检查、脱敏样例、实际 Agent 行为和真实服务验收分别报告。

可用上表的 U.1、C.1、C.2 各挑一条脱敏失败日志验收。U.1 应直接查库，C.1 应继承父类、诊断后交接且零查库，C.2 应先诊断再查库。对照案例源访问记录和最终交接材料核实顺序。再用一条只支持父类的日志、一条含非法处置值的测试配置，核对是否交付具体缺口并暂停对应问题。企业采用共存分类时，增加一条能同时确认两个小类的日志，核对合并后实际走的分支。

最终给出：

1. **实际修改**：文件、配置项、企业依据和适用范围。
2. **使用方式**：可用的调用示例，以及已写入或仍待宿主注入的可信输入。
3. **未完成项**：缺什么、影响哪项能力，以及需要谁提供什么条件。
4. **验证范围**：实际执行的检查、结果与未验证能力。

只有已要求的资源配置和启动输入均落实，才称对应配置完成；仅准备了接入文件时说明完成到哪一步。配置完成不等于平台、分类准确性或案例召回已经验收。

## 配置后的调用

两个可选位置参数依次是 `work_dir`、`output_dir`：

~~~text
/ci-self-healing "/path/to/failure-scene" "/path/to/healing-output"
~~~

宿主不支持位置展开时：

~~~text
使用 $ci-self-healing 修复本次构建失败。
work_dir: /path/to/failure-scene
output_dir: /path/to/healing-output
~~~

以上为双目录 CI Job 修复场景，此时按六章模板生成 `analysis-fix.md`；参数已提供但无效或报告无法落盘时，用同结构完整正文披露缺口。仅诊断、单参数、无参数或通用远端调用用普通回复，不自动生成正式报告。企业文件仍按固定规范的各自路径生成，不受正式报告是否适用影响。

“修复本次构建失败”从当前故障入手。排查或必要验证中实际发现属于本次构建的独立问题时，按新问题的分类继续处置。请求明确限定只修某个问题时，范围外发现记作后续事项。本地验证优先选择能保留失败目标、执行上下文和验收条件的最小命令，例如重跑原失败测试。覆盖不足或有明确的额外验证要求时再扩大范围。[修复范围与验证](SKILL.md#5-验证与处理结果)

流水线内修复报告在记录信息表中填写唯一“处理结果”：`local_verified`、`repair_advised` 或 `unresolved`。`repair_advised` 表示本次未完整成功，案例库实际返回了至少一条案例，或已独立交付明确修复方案。案例指导质量由案例库负责。未完整成功、无命中且无明确方案时为 `unresolved`。正文分别说明限制、待核实项和验证情况。具体条件见[结果判定](references/pipeline-outcomes.md#结果判定)，报告范围见[输出适配](references/output-delivery.md#报告适用范围)。

## 企业输出文件如何配置

通用版本的企业输出规范绑定为“未配置”，按调用范围交付正式报告或普通结论，无额外企业文件。`file_change.json` 已改为企业示例，不是所有企业的默认必交文件；原字段与生成规则完整收在[企业输出规范填写说明](docs/enterprise-output-specification.md#file_changejson-示例)。

配置由企业/产品维护者完成，运行时 Agent 不选择规范或输出目录：

1. 在一份 Markdown 中逐文件填写目标路径、内容格式/字段、数据来源、合法空模板、未知或失败处理及校验方式；分别注明生成和检查依赖哪些报告内容或其他文件，排除循环依赖。可以只提供说明，不开发脚本；所有声明文件均必交。
2. 确认 ID、版本和适用范围，将实际规范 ID/入口固定写入 `SKILL.md` 的“企业输出规范”行。若沿用示例 JSON，可声明包内 `file_change_check.py`；若修改格式或文件名，选择与之匹配的校验方式。
3. 核对路径与权限、同名文件归属和工作空间检查范围。标准报告仍由 `output_dir` 决定；企业文件可以基于 `work_dir`、`output_dir` 或已授权固定目录，缺少必要参数时不得自行换目录。
4. 用脱敏样例验证有数据、无数据、未知数据、路径缺口、校验失败和部分文件交付；涉及跨文件依赖时，再验证报告就绪后检查、报告更新后重查及循环依赖缺口。按[适配层](references/output-delivery.md#生成校验与读回)验收实际行为。

运行分层是 `SKILL.md → output-delivery.md → 固定企业输出规范`。通用适配层管理读取、路径、安全写入、逐项生成、检查和完整读回；具体字段与目录只由企业规范定义。标准报告的文件名、六章结构、流水线报告三种结果语义和唯一“处理结果”字段保持共用。

标准报告第 6 节呈现文件交付记录；完成条件及其与修复结果的关系统一见[交付完成与修复结果](references/output-delivery.md#交付完成与修复结果)。

## 维护与离线检查

本仓库目录是正式来源，无需全局安装。详细企业模板与验收场景见 [配置参考](docs/enterprise-configuration.md)；执行规则从 [SKILL.md](SKILL.md) 按需导航，报告格式以 [唯一模板](assets/analysis-fix.template.md) 为准。

包内辅助脚本用于日志提取、报告格式检查及可选的示例变更清单检查，使用 Python 3.9+ 标准库。具体操作见 [日志工具指南](references/log-evidence-tool.md)、[报告指南](references/result-report.md) 和 [企业输出示例](docs/enterprise-output-specification.md)。修改脚本或相关合同后，从 Skill 根目录运行离线测试：

~~~sh
python3 -B -m unittest discover -s tests -v
~~~

通用 `quick_validate.py` 的字段白名单不包含现有 `arguments` 扩展；不要为消除该兼容性提示删除双参数接口。修改执行资源布局时，还需核对 [资源合同声明](assets/execution-resources.json)、宿主执行审计与评审摘录映射，保留历史合同及证据。当前 [交付合同声明](assets/delivery-resources.json) 使用 v6：双参数流水线报告采用三结果合同；企业文件独立按固定规范交付。评测器按每个冻结 Skill 版本绑定 v1、v2 或 v3 报告校验器，旧交付合同和历史证据保留原规则。通用评测器可验证未配置时的报告交付；已绑定企业规范的额外文件需企业宿主或独立评审核对，不将未知企业要求自动判为完成。README 和配置参考属于维护文档，不新增运行时必读资源。
