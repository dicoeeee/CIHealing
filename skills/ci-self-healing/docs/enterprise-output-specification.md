# 企业输出规范填写说明与示例

本文件供企业或产品维护者配置 Skill 使用，不是已绑定的运行规范。通用版本的“企业输出规范”固定绑定为“未配置”，只交付标准报告。企业在一份 Markdown 中填写所有实际必交文件，配置时在 `SKILL.md` 的“自定义资源绑定”表中填写规范 ID 和入口；运行时读取这一固定规范，不扫描目录或接受临时参数切换。

## 填写方式

复制下方栏目到企业自有的一份 Markdown（例如 `references/enterprise-output-spec.md`），填写真实内容并删除占位提示。所有文件在同一文档按小节说明，不再每个文件拆一份 reference；标准报告不列入企业清单，不改变它的文件名、六章结构、五种处理结果和唯一结果字段。

规范开头注明 ID、版本、适用企业/产品和完整必交文件清单。每个文件填写以下栏目：

| 栏目 | 必须说明的内容 |
| --- | --- |
| 目标路径 | 包含文件名的明确绝对路径，或基于已解析的 `work_dir` / `output_dir` 等可信输入的确定路径规则；写清基准，不能让 Agent 搜索或选择目录 |
| 内容格式与字段 | 编码、文件格式、结构、字段含义及必填约束；企业负责具体数据格式，不要求新增配置语言或解析器 |
| 数据来源 | 每项内容来自哪些已有诊断、最终修改、验证或可信输入；依赖报告或其他产物时注明文件及所需内容，不能用建议修改冒充实际修改 |
| 无数据内容 | 已确认无数据时应生成的完整合法空内容模板；可以是 JSON 空结构、仅表头等企业约定内容 |
| 未知或失败处理 | 无法取得数据、生成或校验失败时的处理；如允许失败内容，给出明确模板及字段含义，不能与无数据混同；未提供失败内容时披露交付缺口 |
| 校验方式 | 可以指定真实可用的校验器、参数、所需输入和通过标准；或明确按本规范核对格式/字段并完整读回。涉及多个文件时写清检查依赖，企业不必开发校验脚本 |

清单中的文件全部必交，不配置“可选”、按处理结果启用或仅有修改时生成等条件。空内容、失败处理和完成条件统一遵循[输出适配层](../references/output-delivery.md#生成校验与读回)。

生成依赖和校验依赖分别填写。例如 JSON 与报告都取自已有诊断，可分别生成，再运行两者一致性检查；若 JSON 需要报告的最终摘要，则应明确这一生成依赖。配置时排除无法得到稳定最终版本的循环依赖，不能要求两个文件互含对方最终摘要。运行顺序由适配层按这些依赖安排，无需另建调度文件。

目标路径分别解析：未提供 `output_dir` 时，标准报告在宿主消息交付，基于 `work_dir` 或已授权固定目录的企业文件仍须生成。依赖缺失参数的文件记录路径缺口，不改用其他目录。声明路径、文件格式或校验器不扩大源码修改、外部发布或 Patch 提取权限。

配置后更新固定绑定，例如（占位值不能直接用于运行）：

```text
| 企业输出规范 | <实际规范 ID> | references/enterprise-output-spec.md |
```

显式未配置表示没有额外文件要求；已配置但文件缺失、不可读、版本/ID 冲突或栏目不全是配置缺口，不自动降级为未配置。规范中如确实没有额外产物，应明确写“必交文件清单：无”，不能用遗漏清单表达。

## file_change.json 示例

以下为可选用的完整企业要求示例，不是通用 Skill 的必交文件。企业应将此节改写为自己实际采用的规范后再固定绑定；改变字段、文件名或含义时同时调整校验方式，不能沿用不匹配的校验器。

- 规范 ID：`example-file-change`；版本：`0.1`；适用范围：由采用方填写。
- 必交文件清单：`file_change.json`，所有结束结局均交付，含仅诊断、建议、停止和验证失败。
- 目标路径：已解析的 `output_dir` 下的 `file_change.json`；本示例依赖 `output_dir`，缺失时报告该文件路径缺口。企业可在自己的规范中改为其他明确路径。
- 用途：供外部系统读取最终净修改并生成 Patch；Skill 不因此执行 Patch 提取、commit、push 或其他外部动作。
- 无数据内容：已确认无净修改时为 `{"version":"0.1","changes":[]}`。
- 未知或失败处理：本示例不定义失败内容。条目范围、仓库或操作无法确认时不写伪空清单；生成、校验或读回失败时报告对应缺口，继续其他独立文件。
- 校验方式：采用包内可选示例脚本 `scripts/file_change_check.py`，参数为 `["--manifest", "<该文件的实际绝对路径>"]`，要求 `format_status: valid` / 退出码 0，并完整读回；此脚本仅适用于下述固定格式和文件名。

### 内容格式

使用 UTF-8 标准 JSON，无注释或尾逗号，数组键名固定为 **`changes`**：

```json
{
  "version": "0.1",
  "changes": [
    {
      "file": "src/main/xxx/xxx.java",
      "op": "modify",
      "repo": "example-repo",
      "desc": "补充缺失的导入，恢复已有接口调用"
    }
  ]
}
```

顶层仅有 `version`、`changes`；条目仅有 `file`、`op`、`repo`、`desc`，所有字段必填：

| 字段 | 约定 |
| --- | --- |
| `version` | 固定字符串 `"0.1"`，不是数字 |
| `changes` | 文件变更条目数组；无代码修改时为 `[]`，不省略、不填 `null` |
| `file` | 相对该文件所属 Git root 的 POSIX 文件路径，用 `/` 分隔；无前导 `/`、仓库前缀、反斜杠、空路径段、`.` 或 `..` 路径段；删除文件也保留其原相对路径 |
| `op` | 仅 `modify`、`create`、`delete` |
| `repo` | 该文件所属实际 Git root 的 basename（最后一级目录名），与外层调度器的仓库匹配键一致；不是项目显示名、远端仓库名、目录绝对路径或 `owner/repo` |
| `desc` | 非空修改说明，描述实际变更及作用，不填写凭据或敏感原文 |

无代码修改时的完整文件：

```json
{"version": "0.1", "changes": []}
```

### 数据来源与生成规则

1. 复用已确认的仓库身份、实际 Git root、修改归属和交付基线。`repo` 固定取该 Git root 的 basename，`file` 相对同一 Git root 计算；必要时只读确认 `git rev-parse --show-toplevel` 的结果。`work_dir` 不一定是 Git root，不能直接取其 basename；也不能用 `build_info` 等仓库映射中的逻辑名称、远端名称或构建项目名替代。多仓按各自 Git root 分别计算；worktree 使用当前工作树的 Git root，不取 `.git` 或公共 Git 元数据目录。无法确认 Git root，或多个 Git root 的 basename 相同、调度器无法唯一匹配时，报告交付缺口，不自造别名或添加路径前缀。
2. 核对本次及明确继承、属于本次交付范围的源码、测试、构建配置等净变更。保护用户/Job 原有修改，不能直接把全量 `git status` 当作本次清单；同文件混有原有修改时在报告说明，文件级清单不能分离修改片段。Patch 提取基线与介入时的修改归属判断分别核对，不能互相替代。
3. `op` 按对应仓库已确认的 Patch 提取基线与最终状态判定：原有文件改变为 `modify`，新增为 `create`，删除为 `delete`；重命名/移动拆为旧路径 `delete` 与新路径 `create`。同路径多次编辑合并为一项，恢复到交付基线或先创建后删除且无净差异的不列入。每个 `(repo, file)` 唯一，建议按仓库名、路径排序。
4. 排除报告、`file_change.json` 本身、取证日志、校验清单和构建临时副产物；实际作为候选交付的源码或配置按归属判断，不能仅凭目录名排除。已有恢复/清理完成或其缺口已查明后，按最终状态填写；停止或验证失败不等于无修改，仍留下的未恢复源码改动须在条目说明和报告中如实披露，不能用空数组隐藏。

例如项目显示名为 `routing-feature`、实际 Git root 为 `/job/scene/sourcecode`，修改 `/job/scene/sourcecode/src/main/java/example/Feature.java` 时，必须填写 `repo: "sourcecode"` 和 `file: "src/main/java/example/Feature.java"`。即使从其 `src/` 子目录开始工作，取值也不变。

仅诊断且没有继承的交付修改时，直接输出空数组，无需为了生成清单建立修复身份、读取修复专用合同或开始构建。无法确认条目范围、Git root、其 basename 或操作时，不编造条目或以空数组代替未知，记录该文件交付缺口。

### 校验与接手边界

示例校验器使用 Python 3.9+ 标准库，只读检查 JSON、字段、版本、路径格式、操作和重复条目，返回 `format_status`、最终字节的 `sha256` 与问题列表。`valid`/0 为格式通过，`invalid`/1 为格式错误，`incomplete`/2 为读取不足。它不检查实际仓库、修改归属、净差异、Git root 的 basename 或修复正确性。

Agent 还须对照最终差异核对条目与操作，确认 `repo == basename(Git root)`，由该 root 与 `file` 定位文件；删除项核对原位置。仅诊断且没有继承的交付修改时使用空模板，不建立修复身份。建议修改不进入实际变更条目；停止或验证失败仍保留的净修改不能隐藏为空数组。

文件写完后校验和完整读回同一份最终字节；文件或所描述的源码再次改变时，重新核对、校验并读回。标准报告第 4 节与其实际修改一致，第 6 节披露文件路径、生成/校验/读回结果及缺口。外部系统在本次交付完成后按真实仓库和基线接手，不能把文件出现或空数组当作修复成功、清理完成或安全提取的许可。
