# 清理基准恢复与候选撤销

仅在发现漏采、误采、检查组内候选变化、决定撤销/放弃候选，或状态文件发布/收尾异常时读取；在恢复、重新采集或撤销前读完适用规则。先按[清理指南](workspace-cleanup.md)停止相关写入、保留原始事实与可靠恢复依据。本指南不授予候选准入，也不改变成功交付条件。

## 基准缺失或时序错误的恢复

执行后才发现漏采、在候选应用前误采，或组内改动候选时，先停止新增构建与其他写入，保留原检查、差异和时序错误。**旧清单不再适用于当前候选，也仍须按原路径保留原文件及收据**；不以“过期”“误采”或“已有新基准”为由删除。按[清单与结果保留](workspace-cleanup.md#清单与结果保留)将其排除在副产物清理之外。恢复按以下顺序进行：

1. 核对候选准入仍有效，凭可靠的原始内容与范围证据处理本次副产物、误删误改，重建**包含该候选且尚未执行本组检查**的完整状态；保留原有用户/Job 文件。只清理已知目录、查看 Git 差异或断言“剩下的都是修复”不足以证明已重建；无法确认的路径保留为缺口。
2. 能确认重建时，使用新清单路径重新 `capture`，沿用真实候选身份；在已有记录中说明旧基准不适用的原因及新旧引用，原清单保持不变。若候选确有变化，先重新核对受影响准入和绑定。不能只改候选 ID、覆盖清单或在残留状态上补采。
3. 对重建的当前候选重做受影响验证，再清理并取得最新有效 `match`；随后复核最终状态与验证有效性。原来的成功检查不能替代这轮验证。

这是一条重新满足交付条件的路径，不是追认首次构建前已有有效基准。记录恢复依据和重验结果；无法确认重建、重验或最终校验时返回 `inconclusive` 并交付报告，不靠解释差异放行。若已决定放弃候选或语义准入已失效，走下方撤销分支，不为取得 `match` 重做无准入的修复。

## 候选撤销与基准

编译前清单可能包含后来被否决的候选。撤销候选按[基线与候选恢复](execution-modes.md#基线与候选恢复)恢复介入时内容；不要为了取得旧清单的 `match` 重新引入被否决修改。旧清单与恢复依据共同用于区分预期撤销和残留副产物，保留原比较事实并逐项说明差异，不能把 `mismatch` 改称 `match`。

继续试修时，先确认旧候选与副产物已安全处理，再为获准的新候选采集新基准、执行受影响验证；不能把未解释的残留带入新基准。结束或移交时，如实记录已恢复内容、最新差异及未解决项，不为结束任务而重新采集“干净”基准。

## 状态文件异常

本节仅解释脚本的发布与收尾行为。按[返回结果与绑定](workspace-cleanup.md#返回结果与绑定)处理实际错误；不能用文件存在或其中的 `match` 替代有效的本次收据。

- 清单与报告先写入同一状态目录的私有临时文件，完整写入、同步并关闭后，再通过不覆盖已有目标的硬链接发布到正式路径；该能力不可用时报告缺口，不改用直接写入正式路径或覆盖式替换。发布前失败不会在原本不存在的正式路径留下本次成功报告，报告交付失败返回 `incomplete` / 2。脚本只收尾本次创建且身份仍匹配的临时文件，不清理其他状态文件。
- 正常发布时报告 JSON 与 stdout JSON 一致；发布后的临时文件清理或其他常规收尾错误仅在 stderr 告警，不改写已发布结论。这不是断电一致性保证；进程异常终止、无最终输出或绑定不符时，不能仅凭文件存在或其中的 `match` 判定本次成功。
