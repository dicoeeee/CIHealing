# 修复准入与验证

仅在已授权修复请求中使用。先按 [诊断与上下文](diagnosis-and-repair.md)完成主动取证；方法由 Agent 选择，本文件约束进入候选和报告结果所需的依据。

写入式诊断实验、候选修改或发布前，读取固定的[企业修复策略入口](enterprise-policy.md)，完成适用性与动作限制核查并纳入准入；后续复核按该指南执行。入口缺失或不可读时暂停依赖该判断的写入，按[自主推进与停止](diagnosis-and-repair.md#自主推进与停止)处理。

## 修复依据

进入修复候选前，先按诊断指南的 [修复依据核查](diagnosis-and-repair.md#修复依据核查)完成判断；已有诊断与准入记录合起来应提供以下可核查内容：

1. **目标行为**：本次要实现或保留的行为及其来源，区分直接声明、观察和推断。
2. **修复位置**：所选位置、限制来源，以及重要替代方向和反证的处理依据。
3. **修改约束**：必须保留的行为、兼容性、授权范围及适用企业策略的判断依据；受影响文件、配置、依赖和下游，以及相关风险与恢复方式。
4. **验证计划**：能检验目标行为与根因修复、发现候选仍然错误的检查及通过条件，且可在所选模式中执行。
5. **关键缺口**：剩余未知项对修复选择、必须保留的行为及必要验证的具体影响，包括尚未解决的 [语义方向歧义](diagnosis-and-repair.md#语义方向歧义)。关键缺口未解决时不进入候选修改，按 [自主推进与停止](diagnosis-and-repair.md#自主推进与停止)处理。

调查顺序由信息缺口决定。`diagnosis` 保存根因、目标行为、约束与证据；`repair_admission` 引用这些内容，简短记录当前决定和验证计划。候选说明与最终报告复用已有记录。

新候选、目标变化或重要新证据出现时，在相应候选修改或发布前重新评估并记录决定；仍适用的内容可引用，仅更新受影响部分。旧执行收据保留原始事实，适用性按 [收据绑定与失效](core-contracts.md#收据绑定与失效)检查。准入允许试修，不表示候选已经验证正确。

## 候选修改前的准入记录

首次候选修改前，必须在宿主可观察的消息、日志、记录或事件中输出 `repair_admission`，绑定当前失败与基线，引用对应诊断、目标行为、约束与验证计划。不能只保留内部判断，也不能用最终报告中的事后补写代替修改前准入；宿主未指定格式时可简写，不要求新增文件或重复展开 YAML。

存在有依据的不同语义解释时，记录各解释的支持来源、行为分歧、已取得的区分性证据，以及为何足以排除替代方向，或仍需什么证据而停止。仅写“已消解”或“无风险”不满足要求；依据明确的局部修正无需强列两个解释。判据见 [语义方向歧义](diagnosis-and-repair.md#语义方向歧义)。

会写入文件的诊断实验先记录 `experiment_only` 及其已确认的范围；该决定不授予候选修改或发布准入。记录的格式完整或 `allow` 字段本身不构成放行证据。

## 决定修复准入

```yaml
repair_admission:
  decision: experiment_only | allow_local_candidate | allow_remote_candidate | stop
  evidence_refs: []
  unknowns: []
  required_verification: []
  rationale: <本次决定及对诊断、目标行为和约束的引用>
```

- `experiment_only`：仅执行已确认范围内可逆的诊断修改或临时插桩；写入前读取 [基线与候选恢复](execution-modes.md#基线与候选恢复)。实验不作为修复候选发布，非有意保留的修复内容须移除。
- `allow_local_candidate`：失败与基线已准确绑定，上述修复依据充分，且没有尚未解决的语义方向歧义。在这些前提下，定位足以行动，根因为 `confirmed` 或 `supported`，或确定性工具直接指出机械性修正。根因判断和机械性修正均不能替代目标行为证据。此决定允许创建候选，不要求候选已通过验证；原失败复验可在所选模式允许的位置执行。
- `allow_remote_candidate`：满足本地候选准入；实际候选通过 V0、明确要求的发布前本地检查和差异范围/策略检查，远端必需检查及准确候选绑定方式已确定，且 [远端执行授权](remote-verification.md#授权与能力)已满足。必需发布前检查失败或无法完成时不发布。
- `stop`：存在尚未解决的语义方向歧义，或其他依据、权限不足以继续修改或发布的情况；取得足以解决相应缺口的新证据或授权后重新评估，否则按协作能力结束本次调用。

## 构建与更新候选

依据已记录的决定实施候选，保留与其对应的修复依据及验证计划。候选指相对于介入时工作空间的完整修改集合，恢复和修改归属统一遵循 [执行模式](execution-modes.md#基线与候选恢复)，不额外要求生成 Patch 文件。

在符合目标与约束的方案中选影响较小的修改，综合比较依赖影响、行为变化、额外机制、运行时处理与维护负担，不以文件数或增删行数单独判断。测试、断言、策略或检查只有在当前意图和证据表明它们本身错误时才应调整，不以压制失败作为修复目的。

验证失败后，结合候选差异、依赖上下文、基线证据与实际结果，将新失败判断为 related、unrelated 或 uncertain，并记录依据，再按下节选择后续动作。放弃候选先恢复，再创建下一候选。

## 失败后的路径选择

先区分原始 CI 失败、候选验证失败与自愈工具执行失败，保留失败步骤、实际结果、候选身份及相关证据。以下路径按证据选择，不要求依次尝试所有方法；同一失败有多个阻塞因素时，分别处理影响当前动作的条件。

| 当前证据 | 下一步与停止条件 |
| --- | --- |
| 取证工具不可用、超时或响应不完整 | 复用已取得且绑定有效的材料；按 [Provider 访问](providers/provider-access.md#选择访问方式)补取当前缺口，不重做全部取证。无获准替代路径且缺口影响判断时，转入协作或结束；不能换工具绕过权限拒绝。 |
| 验证证据反驳候选或其关键前提 | 更新诊断，撤销受影响的准入；放弃候选时先按 [恢复规则](execution-modes.md#基线与候选恢复)恢复并核对。只有存在有依据的新策略且限额允许时，重新准入下一候选；无新进展则结束。 |
| 验证被环境、工具或无关失败阻断，尚不能判断候选 | 保留仍有依据的候选和真实检查结果；在已选模式及授权范围内寻找能够满足同一验证要求的可行路径。无法完成必需检查时报告缺口，不删检查、不降低通过条件、不因本地环境缺失自行切换到远端发布。 |
| 新证据使目标行为或修复方向出现关键歧义 | 暂停依赖该判断的修改与发布，按 [自主推进与停止](diagnosis-and-repair.md#自主推进与停止)补取区分性证据；仍无法解决时请求澄清、移交或结束，不以换候选试到变绿代替意图判断。 |
| 策略禁止、必要授权被拒绝或适用性未决 | 按 [企业策略判断](enterprise-policy.md#判断与行动)和 [交互与移交](execution-modes.md#交互与移交)停止或处理缺口；不以工具替换、其他 Agent 或重试绕过限制。 |

发布或触发操作的结果不明时，不按普通工具失败重试，先执行 [远端结果核对](remote-verification.md#外部动作结果不明时)。恢复不安全时暂停相关写入，不能带着被放弃候选的残留继续试修。

自动 fallback 仅覆盖既有授权内、有证据支持的替代路径或有界重试；记录所解决的缺口与新结果，不机械重复无新信息的动作。所有路径共用 [调用限额](core-contracts.md#调用身份与限额)，不重置身份或预算。需协作时复用 [复核请求](execution-modes.md#复核请求与继续条件)，结束时按 [结果判定](#结果判定)报告；不因一次工具失败就将原问题判为非修复路径。

## 分层验证

| 层级 | 目的 |
| --- | --- |
| V0 Candidate Guard | 检查基线、实际差异、路径、策略、语法、Schema 和候选身份 |
| V1 Root Failure | 重跑原始失败的命令、任务、PoC 或检查 |
| V2 Affected Scope | 运行受影响测试、调用方、依赖检查、配置验证或 dry-run |
| V3 Broader Scope | 在已声明或确有必要时，运行更广的回归或下游检查 |
| V4 Outer CI | 观察准确发布候选对应的宿主流水线或 Required Checks |

在 `required_verification` 中逐项注明检查标识、层级、命令或 Job/Check、执行位置（`local` 或 `remote`）、是否必须在发布前完成及通过条件。V0 和仓库/Harness 声明的发布前本地检查必须先于发布完成。位置选择不能删除必需检查或降低通过条件。

涉及参数去留、值传递、接口行为或配置含义时，V2 包含能检验该修复决定的针对性检查；共享接口变更覆盖相关调用方兼容性。预期结果来自已确认目标与契约，不从候选实现反推。独立遗留问题按其与当前改动的实际关联判断是否影响必要验证。

V1/V2 及适用的 V3 可由 V4 中具体任务完成，无需本地重复执行，但须逐项映射到准确候选的实际检查。每项收据保留执行位置、命令或 Job/Check、结果、未执行/未完成原因，并遵循核心合同的身份绑定。

本地尚未执行的检查记录 `not_run`，注明原因和承担验证的远端检查；已启动但无法完成的检查记录 `incomplete`。远端通过不改写本地记录，也不抹去已观察失败。本地预检通过只证明预检范围。

会在受控源码工作空间产生或改写文件的诊断、构建或验证，执行前读取[清理与校验](workspace-cleanup.md)，将工作空间校验列为必需检查；构建检查与文件一致性分别记录。该指南的[结束与协作](workspace-cleanup.md#结束与协作)统一定义成功交付和清理缺口处置。

## 结果判定

报告 `local_verified` 或 `outer_ci_passed` 前，复核当前修复依据与准入仍然有效，检查实施与验证过程中是否出现会改变目标行为、修复方向或必要验证的新证据，以及重要反证是否已处理；在结果中简要记录复核结论和证据引用。可复用仍适用的依据，只更新受影响部分，不要求重新进行全量调查。

这两类成功结果均以没有尚未解决的 [语义方向歧义](diagnosis-and-repair.md#语义方向歧义)或其他关键缺口为前提，并须满足适用的[清理完成条件](workspace-cleanup.md#结束与协作)；编译或外层 CI 通过不能豁免本地清理校验。预期独立于候选且能区分行为方向的适用测试可以提供目标行为证据，但测试通过本身不保证其具备这种区分力。

| 结果 | 成立条件 |
| --- | --- |
| `not_eligible` | 已确认属于重试、Flaky、基础设施、事故或其他非修复路径 |
| `local_verified` | `local_verify` 中 V0、V1 及所有适用且已声明的 V2/V3 在当前工作空间环境实际通过 |
| `outer_ci_passed` | `remote_verify` 中发布前检查通过，V1、必需 V2/V3 在计划指定位置实际通过，且准确候选对应的 V4 通过；不要求先取得 `local_verified` |
| `no_progress` | 后续候选尝试不再增加有用证据或策略 |
| `inconclusive` | 证据、环境、领域知识、能力或必要验证不足，无法给出完整修复结论 |
| `denied` | 必要动作被适用策略禁止，或策略允许申请的必要授权被拒绝 |

语义歧义未解决时，`repair_admission` 为 `stop`，即使 V1/V2 或 V4 通过也不成立上述成功结果。保留已通过检查的观察事实，按 [交互与移交](execution-modes.md#交互与移交)请求澄清、移交或结束；因该缺口无法继续而结束调用时返回 `inconclusive`，不把行动决定、协作请求和终局结果混为一谈。

必需检查未触发、跳过、取消或缺少有效证据时，不成立成功结果，即使流水线汇总为 `passed`。实际失败保留失败事实；运行仍排队或执行时按预算观察，无法取得必要证据时按关键缺口规则处理。

协作中的请求与部分结果不强行包装成整次修复终局结果，遵循 [交互与移交](execution-modes.md#交互与移交)。`queued` / `running` 是带观察时间的进度，后续观察责任见 [Provider 合同](provider-contract.md#实时观察边界)。
