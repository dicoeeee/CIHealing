# 修复准入与验证

修复准入部分仅用于已授权修复；[完整成功条件](#完整成功条件)适用于修复调用，[结果判定](#结果判定)中的枚举仅用于双参数流水线内修复报告。只读诊断不进入准入或套用该报告。评估准入前完整读取[通用诊断流程](diagnosis-and-repair.md)并完成适用主动取证，未读全先补读。写入式实验、候选修改或发布前，读取固定的[企业修复策略入口](enterprise-policy.md)，将适用性/动作限制纳入准入，后续复核也按该指南；入口缺失或不可读则暂停相关写入，按[自主推进与停止](diagnosis-and-repair.md#自主推进与停止)处理。

## 修复依据

评估实验或候选准入前，核对下述目标行为、位置、反证、语义歧义和完整候选缺口。诊断保存机制、目标、约束与证据，`repair_admission` 引用它并记录决定及验证计划，候选与报告复用。

修改约束包括必须保留的行为、兼容性、授权与企业策略依据，以及受影响文件/配置/依赖/下游、风险和恢复方式。准备形成候选或开展构建/验证时，先完整读取[候选实施与分层验证](candidate-verification.md)，再制定能在所选模式执行、检验目标及根因修复并证伪候选的检查计划，明确层级、位置和通过条件；明确只读停止时跳过。

新候选、目标变化或重要新证据出现时，在相应修改/发布前重评，仅更新受影响内容。旧收据保留，适用性按[收据绑定与失效](core-contracts.md#收据绑定与失效)核对；准入允许试修，不表示验证正确。

## 目标行为与证据

本项核查形成三项可追溯内容：

- **目标行为**：说明影响本次修复选择的输入条件、预期输出或效果，以及必须保留的兼容性；只列与决定有关的内容。凡特性设计会影响当前修复选择，均纳入判断；其余特性开发保持在本次范围之外。行动始终受现有授权约束。
- **证据支撑**：对影响修复方向、授权或兼容性边界及成功结论的每项关键判断，引用已取得的证据，说明材料的具体内容支持哪个判断及其当前适用性，并区分原始声明、观察事实与推断。依据来自其他结论或推断时，追溯并核对其中决定性的前提。材料存在或被引用不表示其支持关系成立；证明失败机制的证据不自动证明应修改哪一侧。
- **推断适用性**：从仓库模式、结构或历史作类比时，核对该模式成立的关键条件与当前对象的对应关系，以本处适用的证据支撑相应约束。

有充分支撑的代码、测试与历史推断可以用于决策；作者额外说明或固定文档不是默认前置条件。取证深度由上述关键判断的信息缺口决定。尚未核实且足以改变修复方向的关键前提，不得用于排除有依据的替代方向或放行依赖该前提的候选，按 [自主推进与停止](diagnosis-and-repair.md#自主推进与停止)处理。

复用此前案例材料时，引用原文及版本，核对机制、环境、目标行为和验证范围与当前对象的对应关系、差异及重要反证。同一报错、旧 Patch 或历史验证通过不能证明当前候选正确；决定性契约须追溯当前适用来源。需要本轮案例检索时记录符合哪项[触发判据](diagnosis-and-repair.md#路由通用与企业知识)，由主入口安排；已转入案例建议分支后，本轮不再放行实验或候选准入。

## 选择修复位置

在收窄候选范围前，说明限制来源和位置取舍：

- **限制来源**：逐项核对实际限制修法的前提，包括未明说的“必须保留”“只能改这一侧”“必须增加适配”等默认判断。约束来自明确指令与授权边界、适用契约或有充分证据支持的判断，其支持关系按 [目标行为与证据](#目标行为与证据)核查。前提被反证动摇时，重新开放受其影响的候选方向并评估。
- **位置取舍**：依据目标行为、当前契约和兼容性，选择调用方、被调用方、适配层、输入构造或依赖配置等修复位置，同时评估既有实现遗漏与新调用错误等有据解释。将当前实现的行为作为观察，将有证据确认的兼容性要求作为约束。

将所选位置、限制来源与重要替代方向的取舍记入[修复依据](#修复依据)；比较范围限于有据的重要方向，依据明确的局部修正可自主择优。候选的影响范围与复杂度权衡见[构建与更新候选](candidate-verification.md#构建与更新候选)。

## 重要反证

对每条已发现的重要反证，说明它影响哪项失败机制、目标行为、修复位置、兼容性或必要验证，并给出维持或调整当前决定的依据。分别评估失败机制与修复方向：机制不变的反证仍可能改变应修改哪一侧。确与当前决定无关的遗留问题，记录关联判断依据后作为非阻塞项；仍影响关键修复选择的未决项写入 `unknowns`，按 [自主推进与停止](diagnosis-and-repair.md#自主推进与停止)处理。

## 语义方向歧义

当当前变更证据支持多个合理的修复解释，而它们对应不同或相反的目标行为，且现有证据不足以区分时，必须认定存在关键意图歧义，暂停依赖该选择的候选修改与发布。同一目标下的不同实现方式可自主择优；不要求枚举没有证据支持的任意假设。

接口、实现和调用方可能在同一特性的不同提交中分阶段引入。应结合整个特性变更判断，不能把先出现的签名当作已稳定契约，也不能仅凭较晚的调用认定最终意图。提交顺序、签名延续时间、改动范围、相对于现有实现或当前样例的运行时等价、编译通过，不能因数量叠加就成为目标契约依据；整组证据若仍同时容纳相反语义方向，歧义就未消解。故障机制已明确或被称为机械性修正，也不豁免这一要求。

判定歧义已消解，必须引用适用于当前变更的目标行为依据，指出重要解释在哪些输入、条件或兼容性要求下产生行为差异，并说明证据如何排除有依据的重要替代解释。仅证明一个修法可行、另一方向尚未实现，或没有找到反对所选修法的材料，不满足该判据。

依据可来自当前适用的声明、契约、测试、迁移记录及完整变更，也可由这些材料形成有据推断；核对版本、适用范围与重要反证，不限定为作者解释或某份文档。材料名称不保证区分力：若样例或测试在两个方向下结果相同，其通过不能消解分歧；仅从候选实现反推的预期也不能证明目标行为。

在宣告消解前，按 [变更上下文与预期行为](diagnosis-and-repair.md#变更上下文与预期行为)读取已定位、可访问且直接影响该判断的材料，围绕行为分歧取证并处理重要反证。取不到的材料记录缺口及影响，不把“未查到”当作另一方向不存在；证据已经充分时无需穷尽所有材料。修复任务将各解释、区分性证据和放行或停止的依据写入 [候选修改前的准入记录](#候选修改前的准入记录)。

不依赖未决语义选择、且安全与权限能够独立确认的可逆诊断实验，可以按[实验准入](#决定修复准入)另行评估；候选的停止决定仍有效。不能把选定某一语义的修复包装为临时实验，或用“先改到编译通过”替代意图判断。

修复请求中歧义仍未解决时，对依赖该选择的候选修改与发布给出 `stop` 判断，列明所缺的区分性证据；不能报告修复已验证，也不能将依赖未决方向的方案判为明确修改建议。最终结果按[结果判定](#结果判定)选择。若在候选实施后才发现歧义，受影响的后续候选修改与发布不具备准入条件，记录当前代码、收据及其有效性，不以已有检查通过掩盖目标未决。

## 完整候选与缺口

逐项判断缺口对**拟交付的完整候选行为**的影响，而不只对报错行、签名或编译条件的影响。在已有诊断或准入记录中说明：

- 现有证据仍支持哪些不同解释，它们在哪些输入、效果或兼容性要求上产生差异；无需穷举无依据的假设。
- 完整候选在这些差异下实际会做什么。若任一仍有依据的解释会使候选遗漏必要行为、破坏兼容性或改变必需验证，该缺口就是阻塞项；先补取能区分的证据，不能只声称与本次修改无关。
- 只有当前决定在这些解释下均有据成立，才能把缺口记为非阻塞，并说明为何不影响修复选择、必须保留的行为及必需验证。未知项与独立局部修正确无关联时可继续，不因缺少特定文档或泛化风险自动结束。

不能把一个依赖未决语义的完整修复拆称“先修结构，行为以后补”，来降低准入要求。新增参数仅接收但忽略、继续原实现、为未明输入填默认值，均已选择一种行为，不是中立占位；需要各自的目标行为依据。低置信度应具体体现为证据不足、重要解释冲突或验证缺失，不以“最保守”“最小改动”替代上述关联判断。

## 候选修改前的准入记录

首次候选修改前，在宿主可观察的消息、日志、记录或事件中输出 `repair_admission`，绑定失败/基线，引用诊断、目标、约束和验证计划。准入的策略依据引用已完整读取的[固定策略入口](enterprise-policy.md)及实际声明；未读或入口缺失不能记作未配置，明确未配置也不豁免通用限制。按“目标行为及证据支持关系 → [完整候选与缺口](#完整候选与缺口) → 决定”组织；不能只留内部判断或报告事后补写。无宿主指定格式时可简写，不新增文件或重复 YAML。

[语义方向歧义](#语义方向歧义)统一规定消解证据；有据的局部修正无需强列两种解释。写入式实验事前记录 `experiment_only` 及确认的范围，不授予候选/发布准入；格式完整或 `allow` 字段本身不证明可放行。

## 决定修复准入

决定只绑定具体动作/范围。`stop` 表示依赖未决依据的动作不具备条件；独立取证的权限不由该值扩大，写入式实验仍须满足自身条件并事前记录，不解除候选停止。重评须有新增或重新核对的有效证据。主入口已经确定转人工或只读建议范围时，下方判据不构成恢复实验、候选或发布的授权。

```yaml
repair_admission:
  evidence_refs: [] # 关键判断及材料具体内容的支持关系；可引用已有诊断
  unknowns: [] # 对完整候选行为的影响；非阻塞须说明在仍有依据的不同解释下为何均成立
  required_verification: []
  rationale: <目标行为、重要替代解释的取舍与证据；不能用结论替代依据>
  decision: experiment_only | allow_local_candidate | allow_remote_candidate | stop
```

- `experiment_only`：权限、策略、范围及可逆性可独立确认的实验/临时插桩，说明区分的问题及为何不依赖未决目标。写前满足[恢复](execution-modes.md#基线与候选恢复)和[清理前置条件](workspace-cleanup.md#执行前条件)，完成时保留实验观察及改动/副产物处理记录；未经另行候选准入不作为候选/发布，不绕过禁修、授权或实施未获准语义修复。
- `allow_local_candidate`：失败/基线准确绑定，上述依据充分、无语义方向歧义；定位足以行动且根因 `confirmed`/`supported`，或确定性工具直接指出机械修正。两者都不替代目标证据。允许创建未验证候选，原失败可在所选模式允许处复验。
- `allow_remote_candidate`：满足本地准入，实际候选通过 [V0（候选基础检查）](candidate-verification.md#分层验证)、明确的发布前本地检查及差异/策略检查；确定远端必需检查和准确候选绑定，满足[远端授权](remote-verification.md#授权与能力)。必需预检失败/未完成不发布。
- `stop`：依赖未决语义、依据或权限的修改/发布不具备条件，注明受限范围及再次评估所需依据。无候选、无写入式实验/构建副作用时，`required_verification` 可为空并说明未执行原因，不为填计划加载验证/清理指南；已有写入的恢复与清理义务保持。主入口使用这一判断安排后续动作。

关键缺口仍影响决定时 `allow` 无效。解除停止或改非阻塞须按[完整候选与缺口](#完整候选与缺口)和[语义方向歧义](#语义方向歧义)核对新增或重新核对的区分性证据，记录解决的问题及决定变化；机制明确但目标不明时保留机制判断，停止依赖目标的候选。

已完整读取且仍适用的候选指南可复用；取证工具、实验或候选验证实际失败后，在选择后续动作前读取[失败后的处理](verification-failures.md)。

## 结果判定

本节只用于[双参数流水线内修复报告](output-delivery.md#报告适用范围)。记录信息表必须且只能填写一个处理结果：`local_verified`、`repair_advised` 或 `unresolved`。它描述本次目标的修复成果；停止原因、信息缺口、建议内容和文件交付情况分别保留，不增加行动权限。

以本次约定目标的完整范围判定。多仓或多问题不能以局部成功代替整体完成；明确方案须覆盖尚未完成的全部必要部分。下文“已交付明确方案”统一指已形成并交付符合[明确修复方案](#明确修复方案)全部要求的方案，写出具体建议或已有代码本身不证明方案成立。以下每行都是独立的完整条件，不靠表格顺序消解交集：

| 处理结果 | 含义与成立条件 |
| --- | --- |
| `local_verified` | 本次修复目标已完成，当前候选在 `local_verify` 下通过全部必要验证，并满足[完整成功条件](#完整成功条件) |
| `repair_advised` | 本次尚未达到完整成功条件，但已交付明确方案；知道怎么修及如何完成剩余必要工作，本次尚未完成实施、必要验证或清理。禁修或范围限制仍保留，不改变已交付方案这一成果 |
| `unresolved` | 本次未达到完整成功条件，且未交付明确方案；包括关键信息缺失、修法未定、明确禁修、超出自愈范围、尝试失败、能力或预算不足等情况，正文保留实际停止原因 |

候选未完成必要验证，不能因已有代码就报告成功。区分两类缺口：缺目标行为、接口契约或关键适用性等决定修法的依据时，方案尚未确定；仅缺实施权限或执行验证的环境时，已确定且交付的方案仍可成立。明确禁修、范围外处置和信息不足均可导致 `unresolved`，但停止原因分别保留；需要人工本身不证明已有明确方案，也不改变权限。

转人工、案例建议和 `stop` 是行动分支，不是处理结果。已成立的停止限制继续生效；结果形成后不因该结果恢复本轮自愈。通用只读、单参数或远端调用直接交付其事实、缺口和下一步，不套用这三个枚举。

### 完整成功条件

本节的验证与证据要求适用于所有修复调用；仅上述流水线报告将本地成功记为 `local_verified`。首次使用层级判据前读取[分层验证](candidate-verification.md#分层验证)：V0 为候选基础检查，V1 为原失败复验，V2 为受影响范围验证，V3 为必要的更广回归，V4 为准确发布候选对应的外层 CI。

- `local_verify`：V0、V1 和全部必要的 V2/V3 在当前工作空间环境实际通过。
- `remote_verify`：V0 与发布前检查先通过；V1、必要 V2/V3 在计划指定位置实际通过，准确候选对应的 V4 通过。远端任务可承担对应检查，不要求本地重复；远端事实按[远端验证](remote-verification.md)交付，不使用流水线报告或将部分本地检查称为完整成功。

宣告成功前按完整实际修改复核修复依据、准入、原记非阻塞的未知项、重要反证及证据有效性，保留结论和引用。候选必须符合有据的目标行为，无未决语义方向或其他关键缺口，并满足[清理条件](workspace-cleanup.md#结束与协作)。准入、验证和清理各自成立，编译或 CI 通过不能替代其他条件；清理须有最新有效的 `match`。

必要检查不得通过漏报计划来省略。未触发、跳过、取消、失败、缺少有效证据或仍未完成，均不构成完整验证成功；流水线汇总为 `passed` 不能覆盖这些事实。预期独立于候选且能区分方向的测试可提供目标证据，通过本身不证明这种区分力。语义歧义未解决时，依赖该选择的修改与发布保持 `stop`。

仅后续合并、部署等本次目标之外的动作未获授权，不影响本次修复成功判断。`queued` / `running` 是带观察时间的进度，不是最终结局；等待和后续观察沿用原权限、预算及[实时观察边界](provider-contract.md#实时观察边界)。

### 明确修复方案

`repair_advised` 必须同时交付：

- **改哪里、怎么改**：具体文件、配置项、函数或明确对象，以及确定的修改步骤。
- **为什么这样改**：当前证据和目标行为依据，已核对的关键适用条件与重要反证。缺失的信息不能仍影响修改方向；未经适用性核对的历史 Patch 或被当前证据否决的候选不算确定方案。
- **如何验收**：修改后的预期行为、必要检查和通过条件；方案覆盖本次尚未完成的全部必要问题，包含适用的恢复、清理与复验安排。
- **本次为什么未完成**：实际遇到的实施、验证或清理障碍，以及已做、未做、失败、恢复或残留的事实。可已有部分或全部修改，但不能把计划检查写成本次通过。

方案依据已核对不等于修复效果已在当前现场验证成功。一般排查方向、仅要求人工接手、多个未决修法、仅有未验证代码或失败尝试复述，均不足以成立明确方案。候选已被当前证据反驳时，须有处理该反证的有据新方案，不能把原候选换成建议继续交付。方案可来自当前诊断或已核对案例，不为取得该结果额外检索或重启已停止的修复。

人工介入按其要解决的问题判断：需要人工补齐目标或决定修法的关键信息时，交付的是补证建议；修法、调整方式及验收已明确，人工只需实施或恢复执行条件时，才可能交付明确方案。案例方案须核对当前适用性，说明历史改法在本项目的保留项、调整项及依据；历史成功或“结合实际情况调整”不能代替这些内容。

权限、环境和预算允许继续修复时，仍应按主流程实施并验证，不自行选择“只给建议”作为捷径。结果分类与执行遵从分别检查：即使已经交付方案，无正当原因提前结束仍属于流程不遵从，不能凭枚举填写正确认定整次执行合规。

### 未修复结果的边界

确定方案所必需的信息缺失，例如目标行为、实际接口契约或依赖版本不明，应记录缺什么、为什么会影响修法、如何获取；有多个可能方向不等于已有明确方案。方案已确定但缺执行条件时，说明实施前需要满足什么以及如何验证。

本次未完整成功且未交付明确方案时统一为 `unresolved`，既包括关键证据不足、候选失败后无有效新方案、工具不可用、预算耗尽、中断或必要清理无法完成，也包括确定的范围、故障性质、策略或授权禁令。区分这些原因是为了说明接手条件，不再拆成不同结果码。案例访问失败不抹掉已确认的禁令或范围事实；已有明确方案时仍可为 `repair_advised`，原限制继续有效。

下表均以本次尚未完整成功为前提：

| 已有事实 | 处理结果 |
| --- | --- |
| 需人工确认目标行为或契约后才能选择修法 | `unresolved` |
| 已读相似案例，但当前适用性或调整方向仍需人工确定 | `unresolved` |
| 当前修法或案例适配方案有据且已交付，待人工实施或完成必要验证 | `repair_advised` |
| 明确禁修，但已交付上述明确方案 | `repair_advised` |
| 明确禁修且未交付明确方案，即使同时缺信息或案例访问失败 | `unresolved` |

方案和成功都按完整目标判断。已有失败、恢复与清理义务不能因转建议或不适用而隐藏。结果码不表示人工已经接手，移交提交与接手事实分别记录。
