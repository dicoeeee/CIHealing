# 流水线修复结果判定

仅在入口已确认本次属于双参数流水线内修复报告时读取。输入是已有的诊断、准入、实际修改、验证、恢复、停止原因、案例库返回记录和已交付方案；不为填写枚举启动修复、检索或验证，也不要求未发生相关动作的停止调用加载操作指南。

## 结果判定

完整成功是入口依据实际候选、必要验证及最终候选的有效绑定复核后交回的事实，不由枚举字段或报告格式证明。没有形成候选、没有执行验证的停止调用不具备完整成功事实；直接核对本次案例库命中或已交付明确方案的事实，不为排除成功补读候选指南。已有写入时，仍依据实际记录保留未完成的恢复义务。

本节只用于双参数流水线内修复报告。记录信息表必须且只能填写一个处理结果：`local_verified`、`repair_advised` 或 `unresolved`。它描述本次目标的修复成果；停止原因、信息缺口、建议内容和文件交付情况分别保留，不增加行动权限。

按完整目标复核成功，局部修复或部分检查通过不足以判定整体成功。未完整成功时，依据本次案例库返回记录和已交付的方案判定：

| 处理结果 | 含义与成立条件 |
| --- | --- |
| `local_verified` | 本次修复目标已完成，最终候选在 `local_verify` 下通过全部必要验证，入口已依据实际证据确认完整成功。 |
| `repair_advised` | 本次未完整成功，满足以下任一条件：案例库已返回至少一条案例；已交付符合下节要求的明确修复方案。 |
| `unresolved` | 本次未完整成功，既无本次案例库命中，也未交付明确修复方案。正文说明实际停止原因和接手所需条件。 |

案例命中以本次绑定案例源（如企业 Wiki 或 RAG）实际返回的案例条目为准，包括直接按案例标识读取。一次命中即满足建议结果条件，即使只返回标题或摘要、后续正文读取失败、适用性待定，或只覆盖部分问题。案例内容能否准确指导修复由案例库负责。报告引用实际返回的内容，标明未覆盖的问题、已知冲突及本次验证情况。

仅连接案例库、发起查询、返回空结果或在返回任何案例前访问失败，均无命中。请求附带或此前调用留存的历史材料可用于形成方案，单独使用这些材料不计作本次案例库命中。转人工、禁修和 `stop` 的原因另行记录；普通只读、单参数或远端调用直接交付事实、缺口和下一步。

### 明确修复方案

未命中案例库、依据当前诊断判为 `repair_advised` 时，明确修复方案须同时交付以下内容。

- **改哪里、怎么改**：具体文件、配置项、函数或明确对象，以及确定的修改步骤。
- **为什么这样改**：当前证据和目标行为依据，已核对的关键适用条件与重要反证。缺失的信息不能仍影响修改方向；未经适用性核对的历史 Patch 或被当前证据否决的候选不算确定方案。
- **如何验收**：修改后的预期行为、必要检查和通过条件；方案覆盖本次尚未完成的全部必要问题，包含适用的恢复与复验安排。
- **本次为什么未完成**：实际遇到的实施、验证或必要恢复障碍，以及已做、未做、失败、恢复或残留的事实。可已有部分或全部修改，但不能把计划检查写成本次通过。

方案依据已核对不等于修复效果已在当前现场验证成功。一般排查方向、仅要求人工接手、多个未决修法、仅有未验证代码或失败尝试复述，均不足以成立明确方案。候选已被当前证据反驳时，须有处理该反证的有据新方案，不能把原候选换成建议继续交付。方案可来自当前诊断或已核对案例，不为取得该结果额外检索或重启已停止的修复。

人工介入按其要解决的问题判断：需要人工补齐目标或决定修法的关键信息时，交付的是补证建议；修法、调整方式及验收已明确，人工只需实施或恢复执行条件时，才可能交付明确方案。案例方案须核对当前适用性，说明历史改法在本项目的保留项、调整项及依据；历史成功或“结合实际情况调整”不能代替这些内容。

权限、环境和预算允许继续修复时，仍应按主流程实施并验证，不自行选择“只给建议”作为捷径。结果分类与执行遵从分别检查：即使已经交付方案，无正当原因提前结束仍属于流程不遵从，不能凭枚举填写正确认定整次执行合规。

### 未修复结果的边界

| 本次事实（均未完整成功） | 处理结果 |
| --- | --- |
| 案例库返回一条相似案例，需人工确认适用性或决定调整方式 | `repair_advised`，说明命中条目及待核实项 |
| 明确禁修，检索命中案例 | `repair_advised`，保留禁令和未实施事实 |
| 无案例命中，但已交付有据的完整方案，待人工实施或完成验证 | `repair_advised` |
| 无案例命中，仍需人工确认目标或选择修法 | `unresolved` |

报告分别记录已有失败、恢复义务及实际移交情况。
