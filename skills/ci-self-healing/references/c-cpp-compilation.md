# C/C++ 编译诊断与修复

本指南只补充 C/C++ 原生构建的取证入口、修复决策和验证注意事项；共用 [诊断与上下文](diagnosis-and-repair.md)。只读任务保持只读取证，以下涉及修改或验证候选的内容仅在修复分支使用。它不把报错类别映射为固定修法，也不替代通用的修复依据核查。

## 适用范围与方法选择

适用于 C/C++ 主源码或测试源码的预处理、编译、模板实例化、符号解析、链接、ABI 和由这些阶段直接暴露的构建配置或生成代码问题。先依据实际失败动作识别发生阶段；依赖下载、认证、解析或制品选择问题按[依赖诊断与修复](dependency-diagnosis-and-repair.md)判断，与编译、链接或 ABI 同时相关时按信息缺口组合使用。Runner、资源或已确认 Flaky 失败仍按[通用失败准入](diagnosis-and-repair.md#准入正确的失败)判断。

C/C++ 的源文件不是完整的编译输入。宏、条件编译、头文件搜索顺序、强制包含、预编译头、模块、生成文件和编译选项共同决定翻译单元。围绕会改变修复判断的输入，核对其与实际失败的对应关系，再按[修复依据核查](diagnosis-and-repair.md#修复依据核查)判断目标行为、限制和修复位置。

## 有效构建动作

选择修法前，按实际失败阶段核对与失败源码状态对应的构建入口、目标、配置及已执行动作。配置或生成阶段尚未产生编译/链接动作时，依据该阶段的日志、规则和输入定位，不要求取得尚不存在的动作。根据项目已有入口选择工具；下表按当前信息缺口选用，不是每次都要执行的固定清单。

| 需要回答的问题 | 相关证据与入口 |
| --- | --- |
| 哪个阶段和目标失败？ | 原始命令、工作目录、构建目标、失败翻译单元、目标文件/库和退出码；区分预处理、编译、链接及构建脚本失败 |
| 实际使用了什么工具链？ | 编译器/链接器及版本、target triple、语言标准、标准库、ABI、sysroot、架构和项目声明的 toolchain |
| 编译器实际收到哪些参数？ | 完整命令或 response file、-D 或 /D 宏、-I/-isystem 或 MSVC 等价路径、强制包含、PCH/模块、优化和 sanitizer 选项 |
| 命中了哪个头文件或生成物？ | include 搜索顺序、实际头文件路径、宏展开、生成头/源文件、生成规则及其输入；区分源码树、构建树和系统/第三方版本 |
| 影响哪些目标和消费者？ | 构建图、target 依赖、反向 include/链接消费者、插件或动态库载入方，以及 CI 中实际启用的平台/配置矩阵 |

CMake/Ninja 优先读取已有构建日志、生成构建目录的 compile_commands.json、cache、toolchain file 和 target properties。Make 需要结合实际展开的规则、被 include 的 makefile 和环境变量。Bazel 需要核对实际 action、平台/配置转换、select、copts、defines、includes 和生成动作，可结合已有日志或项目允许的 aquery 等入口取证。不要用顶层配置、另一构建目录或默认本地工具链替代失败动作。

`cmake --build <build-dir> --verbose`、带 `--subcommands` 的 Bazel 构建会实际执行构建，可能写入产物或运行自定义命令，并非只读观察。仅在修复分支的既有实验或验证授权内执行，并遵守[工作空间保护](execution-modes.md#基线与候选恢复)；只读任务不执行会改写文件的命令。

## 翻译单元与预处理

根据信息缺口检查预处理输出、include trace、宏定义和生成输入。-E、-H、-M、-dM、MSVC 等价选项只是示例，应使用项目工具链支持的等价取证方式。执行前检查继承的输出及依赖文件选项，不因使用预处理或查询选项就将命令视为无副作用；会写入文件时遵守上述执行边界。

重点核对：

- 同名头文件是否因搜索顺序、sysroot、第三方版本或生成目录而解析到不同文件；
- #if、平台宏、编译器宏和命令行定义是否使 CI 走到本地没有覆盖的代码路径；
- include 顺序、强制包含、PCH 或模块接口是否改变了可见声明；
- 生成头文件、配置头、协议代码和模板输入是否来自当前目标的实际生成任务；
- 源码修改是否会影响其他翻译单元、unity build、PCH 或模块缓存。

当宏、头文件解析、生成物或编译配置可能改变源码归因或修复方向时，核对相关有效输入并绑定失败动作；已有证据足以判断时，无需完整展开翻译单元或重新生成预处理输出。针对同一源码的不同宏/平台配置分别记录适用范围，不把一个配置的通过扩展为全部构建矩阵。

## 按阶段诊断

| 阶段 | 需要确认的边界 | 常见的不同修复方向 |
| --- | --- | --- |
| 预处理/语法 | 实际宏、标准、头文件和展开后的 token | 修正源码、宏/条件、标准设置、include 来源或生成输入 |
| 类型/语义/模板 | 实际声明、namespace、重载、模板推导、const/ref、生命周期、完整类型和实例化上下文 | 调整调用或声明/定义、约束/模板输入、类型归属或生成源；不要只按最深模板栈帧改代码 |
| 符号/接口 | 声明与定义、所有翻译单元、命名空间、extern/extern C、可见性和生成实现 | 修正声明/定义、调用方、导出/导入、生成规则或依赖；先确认实际解析到的接口 |
| 链接/ABI/ODR | 符号表、库和目标文件、架构、ABI、链接顺序、可见性、name mangling、重复定义及动态载入 | 补齐正确实现/库、修正签名或链接图、处理 ODR/导出和 ABI 兼容；不要把链接器放宽选项当成默认修复 |

C 语言还需核对 tag/typedef、对象定义与 extern、结构布局和 C 链接约定；C++ 还需核对 namespace、重载、模板/concept、值类别、移动/拷贝、ODR 和模块边界。相同拼写或逐字相同字段不证明类型、所有权、布局、生命周期或 ABI 可互换。

## 选择修复位置与类型边界

沿用[修复依据核查](diagnosis-and-repair.md#修复依据核查)，在收窄候选前明确限制来源和行为差异。C/C++ 中常见的有据分歧包括：

- 调整调用方，还是调整公共头文件、声明或实现；
- 增加显式转换/适配，还是消除错误引用、重复定义或错误类型归属；
- 增加直接 include，还是修正 include 路径、顺序、宏或生成头；
- 修改模板调用，还是修改约束、推导输入或实例化边界；
- 修改源代码，还是修正 target 依赖、编译定义或生成规则；
- 调整链接关系，还是补齐缺失实现、修正签名、导出或 ABI。

遇到不同 namespace、tag、typedef、模板实例或生成来源的同名类型时，检查独立消费者、公共接口、序列化/协议、所有权与修改隔离、动态加载和 ABI 约束。零消费者可以削弱“必须保留该类型”的推断，但不能单独授予删除权限；是否统一或保留仍依据当前目标行为、兼容性和授权判断。

适配器、复制或强制转换改变了运行时语义时，核对所有权、生命周期、别名/可变性、深浅拷贝、分配器、异常、安全边界、布局和性能。只有当目标行为和边界确实要求类型分离时，才引入转换层；只有当统一不会破坏已确认边界时，才消除重复定义。reinterpret_cast、C 风格转换、放宽诊断、允许重复定义或屏蔽链接错误等工具性手段必须有独立的契约和授权依据，不能仅为通过编译或链接而使用。

## 高风险变更

- 公共头文件、宏、PCH、模块接口或 target 传递属性可能影响大量下游；验证范围按实际反向依赖和配置矩阵确定。
- 模板、concept 和宏错误常在实例化或展开深处暴露；先定位第一个能区分候选的边界，不把报错最底层位置当作根因。
- 生成代码应优先修正模板、协议、schema、生成器或构建规则；只有项目明确把生成输出作为权威输入时才直接修改输出。
- 链接成功不证明 ABI、动态库加载、符号可见性或运行时生命周期正确；接口/ABI 变更按必要范围补充符号检查和运行时 smoke test。
- 不默认清空构建缓存、删除 PCH/模块/目标文件、升级工具链或修改全局环境。若需排除陈旧产物，采用范围受控且可恢复的重建，并记录它改变了哪些输入。

## C/C++ 分层验证

在[修复准入与验证](repair-and-verification.md)中声明实际检查，按候选和构建配置绑定收据：

- V0：确认候选 fingerprint、有效编译/链接动作、宏/头文件/生成物、目标和构建图；
- V1：以原失败目标、配置和验收范围为基准，通过候选对应的正常构建入口复验；若候选有据地修正了构建规则或参数，使用当前构建图生成的实际动作并记录变化依据，不机械重放已失效的底层命令，也不靠手改命令绕过构建规则；
- V2：覆盖受影响翻译单元、目标、直接消费者和相关生成/链接检查；公共头、类型或 ABI 变化不能只验证报错文件；
- V3：在证据表明相关时，覆盖不同编译器、标准、平台宏、架构、Debug/Release、sanitizer、LTO 或插件配置；
- V4：观察准确候选对应的外层 CI，并保留原始运行身份和范围。

局部编译可以缩短反馈，但不能冒充完整目标或 CI 矩阵。涉及宏/配置的修复要验证会激活不同代码路径的配置；涉及 ABI/链接的修复要验证符号、库和必要的下游/运行时边界。预期结果来自已确认目标与契约，不从候选实现反推。

## 结束条件

当有效构建动作、翻译单元或链接边界无法取得且会改变修复判断，或类型/接口/ABI 的目标行为仍有有据的相反解释时，暂停依赖该判断的修改，按[自主推进与停止](diagnosis-and-repair.md#自主推进与停止)取证、澄清、移交或结束。证据充分时按通用准入自主修复；本指南不把 C/C++ 错误类别变成固定决策树。
