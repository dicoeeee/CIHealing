# 协作与移交

本指南定义协作能力核对、请求内容、通道提交及答复核验。等待、结束子任务或恢复某阶段由主入口决定。没有已授权且可用通道时，记录通道缺口与继续所需条件，不发送请求、不承诺续接，也不因此新增通信权限。

## 交互与移交

沿用主入口确定的行动范围。已转人工或进入案例建议时，澄清或移交仅用于完善诊断、建议或完成既有恢复清理，不请求或委派新的修复；答复本身不恢复本轮自愈。保留原请求类型、已有身份与实际操作记录。

**只读诊断**：直接使用明确请求或可信宿主提供的执行角色、授权范围、实际可用通道和接收方。主 Agent 可通过已授权通道请求澄清或必要读取权限；子 Agent 只向已确认的主 Agent 移交，不绕过它联系用户或另行委派。角色、所需通道或接收方无法确认时，记录该项能力未具备及继续条件，不发送无法确认目标的请求。

只读协作请求说明失败上下文、具体缺口、所需信息或读取动作、证据和继续条件，保留实际提交情况。收到补充后核对来源与适用性，记录可更新的判断及仍未解决的问题，不绕过禁止或拒绝的访问。此任务不建立修复身份或候选，下方修复复核约定不适用；只读诊断记录不套用修复终局结果。

**修复调用**：以下身份、候选、准入、验证和复核约定仅适用于修复调用。按[执行身份与协作能力](core-contracts.md#执行身份与协作能力)核对协作条件，独立于验证位置。

| 条件 | 当前执行者的行为 |
| --- | --- |
| 适用策略明确禁止完成任务所必需的动作 | 记录禁令及 `denied` 判据；只有策略允许申请的额外授权才可提出审批请求 |
| `executor_role: main` 且用户交互能力已声明并可用 | 向用户说明具体缺口；需要目标行为时提出澄清或业务选择，需要额外权限时申请具体动作审批 |
| `executor_role: subagent` 且向主 Agent 移交的能力已声明并可用，接收者已确定 | 按下方交接内容提交给主 Agent，保留实际提交回执；回执不证明接收方已经执行 |
| 角色未知、所需能力未声明或相应通道不可用 | 记录缺口和通道情况，不推测本地环境一定可交互 |

主 Agent 直接执行本 Skill 时，取证、修复和验证要求适用于它自身。收到用户补充或审批后，记录对目标行为、授权范围、验证计划和已有证据有效性的影响。审批不替代验证；必要审批被拒绝是 `denied` 的判定依据，信息不足与预算耗尽分别记录。交互暂停期间仍沿用[调用身份与限额](core-contracts.md#调用身份与限额)，不通过协作重置预算。

子 Agent 只向指定主 Agent 交回问题，不绕过它向用户请求审批或另派设计、编码 Agent。移交提交情况以通道返回的证据为准；提交失败时报告失败并按通道不可用处理。接收方是否继续执行或完成验证，取决于其指令与宿主机制，不能由子 Agent 的 Skill 保证。

交互或移交前，仍有依据的候选可保留，并标明其修改归属、已完成验证和未完成检查；已否决的候选和临时实验按 [基线与候选恢复](execution-modes.md#基线与候选恢复)处理。交接前完成候选及相关构建输入的写操作，提交后保持它们不变；报告可补记通道返回情况，但不得改变待交付候选。接手者应核对当前文件状态与交接记录，再使用证据；更换继承的候选前确认其恢复依据，不能把它与用户原有修改混同。

### 交接内容

协作请求说明 `invocation_id`、接收方、需要补充的信息或业务选择、待审批的具体动作或待接续工作，以及证据引用；澄清与审批分开表达。

向主 Agent 移交还提供失败与变更上下文、诊断与修复依据、当前缺口、工作空间或候选 ref、基线与 fingerprint、修改文件及归属、候选恢复依据、逐项验证结果和未完成检查。区分用户/Job 原有修改、本次修改及继承候选；可用受控引用提供，无需导出完整 Patch。

请求提交后记录当前事实和待答复事项。子 Agent 分别说明通道是否确认提交、已完成工作及整次修复未完成事项；不将交接提交报告为已接手、已验证或整次修复已完成。

### 复核请求与继续条件

需要人工或主 Agent 复核时，先明确请求解决哪一类缺口；同一请求可包含多项，但不能只写“请人工检查”。复用上述交接内容与已有诊断，给出决定所需的最小证据、当前暂停的动作，以及收到什么答复或观察后才能重新评估：

| 复核目的 | 请求内容与继续所需依据 |
| --- | --- |
| 确定目标行为 | 给出有据的不同解释、行为分歧及仍缺的区分性证据，请有权决定目标的人确认本次应实现或保留的行为。不能仅问是否接受当前 Patch。 |
| 复核候选语义或兼容性 | 绑定准确候选与受影响契约，列出反证、风险和未覆盖的必要检查；请求具体判断及依据，或补充验证结果，而非笼统认可。 |
| 获得动作授权 | 列明目标仓库/ref、具体动作、范围及影响；仅在策略允许审批时申请。审批仅解决对应权限缺口，不消解语义歧义，也不覆盖其他禁令。 |
| 恢复验证或访问条件 | 说明缺失工具、环境、证据或恢复依据，以及已尝试路径；请求可用条件或由有权限的执行者完成指定检查，并返回候选/环境绑定的实际结果。不索取或记录凭据原文。 |

收到答复后，核对来源是否有权决定所请求事项、答复是否覆盖具体缺口，以及候选、环境和策略是否漂移，列明哪些判断或收据需要复核。对明确且单一的审批请求，明确同意可作为该动作授权；泛泛的“可以/没问题”不能同时替代尚缺的目标决定、判断依据和必要检查。缺口仍在则保持相应动作暂停，不自动解锁全部动作。

无可用交互或移交通道的 CI Job，协作记录仅包含待复核事项、证据和继续条件；这不表示已通知、创建人工任务或安排复核。不自动建立工单、消息通知或唤醒服务；实际交接需宿主提供已授权的通道。
