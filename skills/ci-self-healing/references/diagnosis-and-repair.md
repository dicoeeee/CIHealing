# 诊断与上下文

只读诊断与修复任务共用本指南。使用失败与变更证据形成判断；置信度落实为支持依据、重要冲突和剩余缺口，不使用数值阈值替代证据。本文示例表示逻辑内容，不要求新增文件或反复展开完整 YAML。

## 准入正确的失败

本 Skill 处理确定性的代码、测试、依赖、配置、构建和发布工程失败；这些失败必须能够形成候选修改并进行有意义的验证。

已确认的网络中断、资源耗尽、Runner 丢失、临时 Provider 失败和已知 Flaky 行为属于重试或基础设施恢复范围，符合修复调用的 `not_eligible` 判据；只读诊断保留分类与依据。记录其范围判断及[案例建议适用性](#路由通用与企业知识)。如果还无法判断是否确定性，先收集具有区分度的证据；仍存在关键歧义时记录缺口，不把未决判断归为 `not_eligible`。是否继续取证、转建议或交付由主入口决定。

## 建立失败合同

改变日志或工作空间前，用 [Failure Snapshot](#failure-snapshot) 保留原始信号、仓库、基线、环境、输入、影响范围及可用复现入口。快照只记观察；机制、预期/实际行为及推断写入[诊断评估](#诊断评估字段)。`recent_changes` 和证据引用保留对应源码状态的 MR/提交范围、相关历史及特性材料来源。

先复用已有材料并按下方规则绑定；需 CI 信息或平台身份时读取 [Provider 访问](providers/provider-access.md)，将访问结果写入快照或引用已有观察，不另建 Failure Evidence。日志缺位置/上下文时才读[日志证据提取](failure-evidence-extraction.md)，工具及引用局限以其为准。`incomplete` 不表示健康；影响诊断或必要验证的缺口按[自主推进与停止](#自主推进与停止)处理。

`baseline_sha` 是对应仓库的来源 Git 提交，不代表工作空间无额外修改。多仓分别绑定身份、实际路径与基线，不共用主仓 SHA；下方快照按单仓展示。首次写入前按[基线与候选恢复](execution-modes.md#基线与候选恢复)保留相关文件介入时内容，不要求新增实时状态或快照服务。

### 失败绑定

结合可信请求目标与实际观察，核对原 Provider 与主机、仓库及源码状态、run/build、Job/task、重试，以及可取得的失败命令和退出码。只从当前仓库、环境或 Provider 证据中补齐身份；未知项如实记录。纯本地失败用 `local`；来自 CI 但平台未确认时用 `unknown`，本地存有日志不改变其来源。

- **实例隔离**：不同运行、Job、矩阵任务及重试分别绑定；合并日志保留片段归属。旧重试或成功构建可以作为有来源的对照，不能拼入当前实例。同名 Job、分支或 SHA 不能单独证明是同一次执行。
- **身份语义**：使用 Provider 自身的 ID；工作流定义、运行、展示名称和重试号不能互换。未给出重试时按可信目标和 Provider 语义解析并固定，不默认最新运行/重试。没有独立重试字段时说明实际唯一执行标识；纯本地失败不要求远端字段。`run_attempt` 不是自愈候选的 Attempt。
- **补齐与冲突**：相同身份的分页或访问来源可以合并，记录原始引用、实际取得范围与观察时间。取证中发生重跑或身份冲突时保留各次事实，先解决目标归属；准确绑定前不创建或发布候选。

已有材料已绑定仓库、源码状态与具体失败时，Provider 名称未知本身不阻止本地诊断或修复，只阻止依赖平台身份的访问。仍无法区分当前运行、任务、仓库或基线等关键身份时，按[自主推进与停止](#自主推进与停止)处理。

## 变更上下文与预期行为

在选择并实施修复候选前，确认与失败相关的变更目标、范围和行为约束。主动查找权限内可获取的材料，先查看整体变更范围，再沿关联深入；已定位、可访问且直接影响修复判断的材料应在选择修法前读取。

- 本次 MR 的描述、全部变更文件范围及相关 diff，确认它们与失败源码状态对应；没有 MR 时，从触发失败的提交或合入范围建立上下文。
- 引入调用、调整接口、改变参数含义的相关提交，以及有关迁移或回退记录；按关联程度选择历史深度。
- 当前适用的需求、设计文档、配置示例、测试及相关评审结论；核对版本、适用范围和结论是否仍有效。
- 实际使用的接口、调用方输入、被调用方处理方式、相关调用方，以及配置和依赖对该路径的影响。

记录材料是未查询、查询后未找到、存在但无法访问，还是已读取但有冲突，并说明它对当前判断的影响。未主动提供不表示不存在。取证可与定位交错进行，工具和顺序由 Agent 选择，已有有效材料可以复用。

取证结果写入下方诊断评估，为[修复依据与准入](repair-and-verification.md)提供目标、位置、反证和关键缺口。简短的依据记录不替代上述主动调查，也不减少所需上下文。

## 定位但不过度声称因果

区分错误位置与失败机制。[定位层级](#定位层级)是报告词汇，不是必经步骤；日志/`file:line` 通常只支持 L1/L2，锚点、最早/最后报错或展示顺序不能自动建立因果或 L4。

按缺口选择代码检查、最小复现、成败对照、diff/bisect、聚焦插桩、上游追踪，或从测试、历史、规范、ADR 重建意图。方法、顺序、假设数量及调查深度由问题决定，不要求全仓扫描、重复复现或遍历工具。诊断命令会写文件时，只读任务不执行；修复任务须已有[实验准入](../SKILL.md#3-判断修复准入)、恢复及清理基准，再执行相应实验并记录观察与副作用，不能按命令名称判定只读。

未选 Profile 时可在普通诊断文字中归纳故障类型，不由此产生 Profile 分类表或分类交付要求；有固定绑定或可信选择时按[分类执行](failure-classification.md)遵循标准边界、初始/最终记录及类别/规则变化后的下游复核，不用通用标签替代或倒填初始判断。类别不能证明根因，诊断结论也不直接授权候选修改或验证；分类与诊断共用日志提取入口，不另设扫描规则。

## 自主推进与停止

本节提供取证是否充分、缺口是否关键及有无有效新线索的判据；阶段选择由主入口控制。修复调用按[完整候选与缺口](repair-and-verification.md#完整候选与缺口)判断缺口影响；只读任务记录判断与影响，不建立修复准入。已有只读或建议范围不能由新线索自行扩大。

关键依据不足时，依赖它的修改/发布不具备条件。有效补证线索须针对具体未决问题、有可访问材料，并能说明结果如何影响决定，记入已有诊断即可。已查材料没有区分力且无具体新线索时，标明无有效新线索；不要求穷尽来源，也不能隐去可行且有望解决缺口的取证路径。不设固定文件数或轮数。

收束取证时核对已有记录是否足以说明：已知机制及其证据边界；阻塞缺口如何改变完整候选的行为或必要验证；已读取的直接相关材料与重要反证；还有哪些具体可访问线索可能改变决定。列明线索所需权限与预算；缺口只是被重复描述、没有新的区分性问题时，不重新遍历已查材料或再次比较同一组方向。

诊断评估保留停止原因、处理结果依据与下一步/接手方，以及[案例触发判据](#路由通用与企业知识)是否满足。已有说明足够时直接引用，不补建完整候选准入表；停止记录的适用范围见主入口[停止分支](../SKILL.md#停止分支)。复核发现新反证、适用性变化或错误时，修正受影响的判断并保留变化依据，不自行撤销已有停止决定。

合理取证后仍有关键歧义时，相关修改的依据仍不足；记录待澄清问题及其影响。因该缺口无法形成完整修复结论时符合 `inconclusive` 判据，不属于修复成功。“尽快修绿”不豁免停止义务；已通过检查保留为实际观察，不扩大为修复结论。

### 术语与映射

企业标签、行动决定和调用结果分别记录，不互作别名；不新增机器状态或改变现有结果码。

| 层次 | 术语与解释 |
| --- | --- |
| 企业分类或处置标签 | `HUMAN_FIX`、`AI_FIX` 等以实际 Profile 的定义为准，保留原标签及版本；它们不是通用 Skill 的结果码。普通分类标签不直接授予或改变权限，须由可信执行策略说明其行动影响。 |
| 修复准入决定 | `repair_admission.decision` 的 `stop`、`experiment_only`、`allow_local_candidate`、`allow_remote_candidate` 表示当前允许的动作；`stop` 本身不说明结束原因，也不等于需人工处理。只读调用不为案例检索建立准入记录。 |
| 最终结果 | 沿用[结果判定](repair-and-verification.md#结果判定)：`not_eligible` 表示已确认属于非修复路径；`denied` 表示必要动作被策略禁止或必要授权被拒；`inconclusive` 表示依据、条件或验证不足。其他既有结果码及成立条件不变。 |

**转人工处置**表示已有证据确认不适用当前自愈流程，或可信策略明确要求由人工处理；记录停止原因、当前结果及其依据，再补充交接建议。已确认的 `HUMAN_FIX` 只有在适用的可信策略赋予该含义时才触发；不能靠日志关键词、名称相似或未核对的 Profile 推导。`AI_FIX` 最多提示继续评估，不能替代修复准入或证明修复成功。

例如外部服务凭据认证失败：已确认处置属于范围外的账号/凭据维护时为 `not_eligible`；必要操作被策略禁止时为 `denied`；影响当前结果判定的关键依据或必要条件仍未明时为 `inconclusive`。停止依据已经成立时，具体根因仍可未查明；根因未知不自动推翻已有结果，结果确定也不提高根因的确定性。不能仅凭同一认证报错或“需要人工”把这些原因全部映射为 `not_eligible`，也不将所有 `stop` 自动归为转人工。

## 路由通用与企业知识

当仓库上下文、公开软件工程知识和标准工具已经足够时，使用通用路径。

只有当正确诊断依赖内部概念、当前业务状态、受治理的组合、私有基线或专项验证器时，才使用企业领域。兼容的 Domain Knowledge Pack 必须标识版本、适用范围、来源、规则、状态查询、工具和验证器。

仅提供分类目录与判据的 Classification Profile 不等于完整领域知识包；无需为分类创建状态查询或验证器。分类引用了诊断资料时，仍核对其来源、适用性及当前决策实际需要的证据。

如果正确修复所需的领域存在歧义、兼容知识包缺失或过期、当前状态不可查询、规则冲突或验证器不可用，记录具体影响，按[自主推进与停止](#自主推进与停止)处理。不要为了出现语义相似的规则而扩大检索范围。

历史案例用于以下两种建议交付；先完成与失败直接相关的必要诊断，不要求先试修：

- **受阻后的建议**：仍缺关键机制或有据的修复方向，或修复已受阻且当前证据没有有效新策略，并且案例有望帮助形成建议。记录当前缺口及案例可能补齐的依据。
- **转人工前的建议**：已按[术语与映射](#术语与映射)确认不适用当前自愈流程，或可信策略明确要求转人工。诊断明确、无法提供自动修法均不取消该条件；即使同时满足受阻条件，建议目的仍为补充人工定位、处置和验证，而非重新开放自愈。

在已有诊断中记录满足哪项条件、对应证据、检索目的及已有停止决定；主入口据此安排[案例建议分支](../SKILL.md#案例建议分支)。本节不决定案例访问时序、分支进入或交付。

缺当前源码、准确日志或运行身份属于[现场证据缺口](#变更上下文与预期行为)，不能单凭缺口名称认定案例有用。一次验证失败或仅缺权限、工具、验证环境不自动满足上述条件；`stop`、`denied`、`inconclusive` 等单独一个值也不替代触发原因。仅提供历史案例的来源无需完整 Domain Knowledge Pack 的状态查询或验证器。

## 记录诊断评估

以下字段表达已有事实和判断，按需要引用或简写；不要求为了填写示例新增记录文件，也不以字段齐全证明调查完成。

### Failure Snapshot

```yaml
failure_snapshot:
  repository: <稳定的仓库身份>
  baseline_sha: <准确的 Git 提交基线>
  provider_run:
    provider: <原失败的 Provider；纯本地失败用 local，来源未确认用 unknown>
    pipeline_id: optional
    run_id: optional
    run_attempt: optional
    job_id: optional
    task_id: optional
  failure:
    command: optional
    exit_code: optional
    error_refs: []
    log_refs: []
    artifact_refs: []
  environment:
    execution_context: <local 或 CI 身份>
    tool_versions: {}
  recent_changes: []
  completeness: complete | incomplete
  observed_at: <时间戳>
```

### 定位层级

| 层级 | 含义 |
| --- | --- |
| L0 Signal | 已识别失败的检查、告警或症状 |
| L1 Execution | 已识别失败的工作流、作业、步骤、任务或命令 |
| L2 Code | 已识别相关仓库、文件、类、函数或代码行 |
| L3 Boundary | 已识别第一个发生偏离的数据、状态或组件边界 |
| L4 Cause | 某个机制得到可证伪实验、对照、追踪或等价证据的支持 |

### 诊断评估字段

```yaml
diagnosis:
  classification: <失败类别、领域路由及适用的 Profile 记录>
  localization:
    level: L0 | L1 | L2 | L3 | L4
    target: <观察到的位置或边界>
  hypotheses:
    - statement: <候选机制>
      supporting_evidence: []
      conflicting_evidence: []
      predicted_signal: <什么结果会支持或反驳它>
  root_cause:
    status: confirmed | supported | unclear | not_investigated
    statement: optional
  expected_behavior: <与本次修改有关的目标行为与约束，说明声明或推断依据并引用来源>
  repair_constraints:
    must_preserve: []
    allowed_scope: []
    prohibited_directions: []
  unknowns: []
```

`classification` 引用已有分类记录即可；类别的确定性不等于 `root_cause.status`。

`hypotheses.conflicting_evidence` 记录机制反证；目标行为、约束等方面的反证及处置写入对应内容，未解决项进入 `unknowns`。未检查不等于检查后未发现；空列表本身不能证明取证完成或准入成立，不要求为了填表虚构反证。

`confirmed` 要求当前上下文中存在直接因果证据。`supported` 表示现有证据相较于重要替代解释更支持该机制，并且验证能够有意义地证伪该候选。不要仅因为建议的 Patch 看起来合理，就将 `supported` 升级。

根因状态对应 `root_cause.statement` 中解释本次失败的具体机制，不由分类命中或停止决定推导。将已知现象、原因判断及处理决定保留在同一份已有诊断中，后续摘要、报告和最终消息复用，不各自重写归因；有新证据时同步更新受影响的判断。区分“发生了什么”“为什么发生”和“为什么停止”，例如当前只观察到上传返回 `401 / invalid_client`：

| 判断对象 | 有据的表述 |
| --- | --- |
| 发生了什么 | 上传认证被拒，日志有直接记录 |
| 为什么发生 | 尚不能区分凭据失效、绑定错误或服务端配置，具体根因为 `unclear`，列出待核实项 |
| 为什么停止 | 已核对的企业策略要求转人工，独立支持 `stop / denied` |

此时不能把“认证被拒”改称上层根因，写成“根因 `supported`、具体子因 `unclear`”来代替具体原因判断，也不据此升为 L4。日志未提供凭据值不证明环境未配置凭据；编译成功或 `auth_required:true` 不排除其他认证配置错误；策略禁止某类操作不证明技术上只有这一种修法。已有证据支持或确认具体机制时，仍按上述定义使用 `supported` 或 `confirmed`，不因转人工一律记为 `unclear`。

诊断记录表达判断；修复与验证事实由实际执行证据提供。其产出为已确认事实、机制及置信依据、目标与约束、关键缺口和适用性结论，供主入口安排后续阶段。
