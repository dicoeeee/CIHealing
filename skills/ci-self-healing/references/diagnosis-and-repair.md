# 诊断与上下文

只读诊断与修复任务共用本指南。使用失败与变更证据形成判断；置信度落实为支持依据、重要冲突和剩余缺口，不使用数值阈值替代证据。本文示例表示逻辑内容，不要求新增文件或反复展开完整 YAML。

## 准入正确的失败

本 Skill 处理确定性的代码、测试、依赖、配置、构建和发布工程失败；这些失败必须能够形成候选修改并进行有意义的验证。

将已确认的网络中断、资源耗尽、Runner 丢失、临时 Provider 失败和已知 Flaky 行为路由到重试或基础设施恢复；修复调用返回 `not_eligible`，只读诊断报告分类与依据。如果还无法判断是否确定性，先收集具有区分度的证据；仍存在关键歧义时按[自主推进与停止](#自主推进与停止)处理，不把未决判断归为 `not_eligible`。

## 建立失败合同

在改变日志或工作空间前保留原始失败，记录信号、仓库、基线、环境、输入、影响范围及可用的复现命令或检查。用 `Failure Snapshot` 保存观察事实；预期与实际行为的解释写入诊断评估。

先复用已有证据，按下方[失败绑定](#失败绑定)确认归属。需要补取 CI 信息或核对平台身份时读取 [Provider 访问](providers/provider-access.md)；访问结果写入此快照或引用已有 Provider 观察，无需另建一份 Failure Evidence 文件。

已取得日志但缺少可用位置或上下文时，按[日志证据提取](failure-evidence-extraction.md)检索和补读；已有片段足够时跳过。工具选择、引用与读取局限统一由该指南定义。

```yaml
failure_snapshot:
  repository: <稳定的仓库身份>
  baseline_sha: <准确的 Git 提交基线>
  provider_run:
    provider: <原失败的 Provider；纯本地失败用 local，来源未确认用 unknown>
    pipeline_id: optional
    run_id: optional
    run_attempt: optional
    job_id: optional
    task_id: optional
  failure:
    command: optional
    exit_code: optional
    error_refs: []
    log_refs: []
    artifact_refs: []
  environment:
    execution_context: <local 或 CI 身份>
    tool_versions: {}
  recent_changes: []
  completeness: complete | incomplete
  observed_at: <时间戳>
```

快照记录观察到的事实，不记录根因或修复结论。`recent_changes` 与证据引用记录失败源码状态对应的 MR 或提交范围、相关历史和特性材料来源；预期行为的推断写入诊断评估。`incomplete` 永远不表示健康。影响诊断或必要验证的材料缺口按[自主推进与停止](diagnosis-and-repair.md#自主推进与停止)处理。

`baseline_sha` 标识来源 Git 提交，不代表工作空间没有额外修改。Agent 对相关文件保留介入时的内容作为恢复依据，修复任务在首次写入前按 [基线与候选恢复](execution-modes.md#基线与候选恢复)处理；不要求新增实时状态或快照服务。

### 失败绑定

结合可信请求目标与实际观察，核对原 Provider 与主机、仓库及源码状态、run/build、Job/task、重试，以及可取得的失败命令和退出码。只从当前仓库、环境或 Provider 证据中补齐身份；未知项如实记录。纯本地失败用 `local`；来自 CI 但平台未确认时用 `unknown`，本地存有日志不改变其来源。

- **实例隔离**：不同运行、Job、矩阵任务及重试分别绑定；合并日志保留片段归属。旧重试或成功构建可以作为有来源的对照，不能拼入当前实例。同名 Job、分支或 SHA 不能单独证明是同一次执行。
- **身份语义**：使用 Provider 自身的 ID；工作流定义、运行、展示名称和重试号不能互换。未给出重试时按可信目标和 Provider 语义解析并固定，不默认最新运行/重试。没有独立重试字段时说明实际唯一执行标识；纯本地失败不要求远端字段。`run_attempt` 不是自愈候选的 Attempt。
- **补齐与冲突**：相同身份的分页或访问来源可以合并，记录原始引用、实际取得范围与观察时间。取证中发生重跑或身份冲突时保留各次事实，先解决目标归属；准确绑定前不创建或发布候选。

已有材料已绑定仓库、源码状态与具体失败时，Provider 名称未知本身不阻止本地诊断或修复，只阻止依赖平台身份的访问。仍无法区分当前运行、任务、仓库或基线等关键身份时，按[自主推进与停止](#自主推进与停止)处理。

## 变更上下文与预期行为

在选择并实施修复候选前，确认与失败相关的变更目标、范围和行为约束。主动查找权限内可获取的材料，先查看整体变更范围，再沿关联深入；已定位、可访问且直接影响修复判断的材料应在选择修法前读取。

- 本次 MR 的描述、全部变更文件范围及相关 diff，确认它们与失败源码状态对应；没有 MR 时，从触发失败的提交或合入范围建立上下文。
- 引入调用、调整接口、改变参数含义的相关提交，以及有关迁移或回退记录；按关联程度选择历史深度。
- 当前适用的需求、设计文档、配置示例、测试及相关评审结论；核对版本、适用范围和结论是否仍有效。
- 实际使用的接口、调用方输入、被调用方处理方式、相关调用方，以及配置和依赖对该路径的影响。

记录材料是未查询、查询后未找到、存在但无法访问，还是已读取但有冲突，并说明它对当前判断的影响。未主动提供不表示不存在。取证可与定位交错进行，工具和顺序由 Agent 选择，已有有效材料可以复用。

取证结果写入下方诊断评估；准备修复时，先按 [修复依据核查](#修复依据核查)检查证据与判断，再按 [修复依据](repair-and-verification.md#修复依据)记录准入所需内容。简短的依据记录不替代上述主动调查，也不减少所需上下文。

## 定位但不过度声称因果

将这些层级作为报告词汇，而不是强制检查清单：

| 层级 | 含义 |
| --- | --- |
| L0 Signal | 已识别失败的检查、告警或症状 |
| L1 Execution | 已识别失败的工作流、作业、步骤、任务或命令 |
| L2 Code | 已识别相关仓库、文件、类、函数或代码行 |
| L3 Boundary | 已识别第一个发生偏离的数据、状态或组件边界 |
| L4 Cause | 某个机制得到可证伪实验、对照、追踪或等价证据的支持 |

日志和 `file:line` 通常只能支持 L1 或 L2，不能自动建立 L4。

根据当前证据和信息缺口选择方法，例如检查可行动错误附近的代码、最小复现、成功与失败对照、diff 或 bisect、聚焦插桩、上游追踪，以及从测试、历史、规范或 ADR 重建意图。这些是可选手段，不是固定顺序或必走清单；假设数量和调查范围由问题决定，不要求每次都完整扫描仓库、重复复现或执行所有工具。

未选定 Profile 时，通用错误分类可以暂定、交叉、随证据修正或在结果报告时归纳；已选定时，遵循[分类标准边界](failure-classification.md#分类标准边界)及初始/最终分类记录要求，不用通用标签替代标准分类，也不等报告阶段倒填初始判断。类别本身不能证明根因。在修复请求中，完成与该修复有关的上下文确认且满足准入条件后，局部错误可以直接构造候选并验证；调查深度随问题和剩余信息缺口调整。

锚点命中、最早/最后报错和展示顺序不自动证明因果。分类和诊断共用上述日志提取入口，不另设扫描规则。

有发行包绑定或可信调用选择时，按[分类执行](failure-classification.md)记录判断；类别或规则变化后的下游复核也由该指南定义。未配置时沿用通用诊断。

## 修复依据核查

本节集中定义目标行为与证据、修复位置及限制性前提、重要反证和语义歧义的核查判据。修复任务的准入时机、记录要求与行动决定见 [修复准入与验证](repair-and-verification.md#修复依据)。

### 目标行为与证据

本项核查形成三项可追溯内容：

- **目标行为**：说明与本次失败和修复选择相关的预期行为。凡特性设计会影响当前修复选择，均纳入判断；其余特性开发保持在本次范围之外。行动始终受现有授权约束。
- **证据支撑**：对影响修复方向、授权或兼容性边界及成功结论的每项关键判断，引用已取得的证据，说明其支持关系和当前适用性，并区分原始声明、观察事实与推断。依据来自其他结论或推断时，追溯并核对其中决定性的前提。
- **推断适用性**：从仓库模式、结构或历史作类比时，核对该模式成立的关键条件与当前对象的对应关系，以本处适用的证据支撑相应约束。

有充分支撑的代码、测试与历史推断可以用于决策；作者额外说明或固定文档不是默认前置条件。取证深度由上述关键判断的信息缺口决定。尚未核实且足以改变修复方向的关键前提，不得用于排除有依据的替代方向或放行依赖该前提的候选，按 [自主推进与停止](#自主推进与停止)处理。

### 选择修复位置

在收窄候选范围前，说明限制来源和位置取舍：

- **限制来源**：逐项核对实际限制修法的前提，包括未明说的“必须保留”“只能改这一侧”“必须增加适配”等默认判断。约束来自明确指令与授权边界、适用契约或有充分证据支持的判断，其支持关系按 [目标行为与证据](#目标行为与证据)核查。前提被反证动摇时，重新开放受其影响的候选方向并评估。
- **位置取舍**：依据目标行为、当前契约和兼容性，选择调用方、被调用方、适配层、输入构造或依赖配置等修复位置，同时评估既有实现遗漏与新调用错误等有据解释。将当前实现的行为作为观察，将有证据确认的兼容性要求作为约束。

将所选位置、限制来源与重要替代方向的取舍记入[修复依据](repair-and-verification.md#修复依据)；比较范围限于有据的重要方向，依据明确的局部修正可自主择优。候选的影响范围与复杂度权衡见[构建与更新候选](repair-and-verification.md#构建与更新候选)。

### 重要反证

对每条已发现的重要反证，说明它影响哪项失败机制、目标行为、修复位置、兼容性或必要验证，并给出维持或调整当前决定的依据。分别评估失败机制与修复方向：机制不变的反证仍可能改变应修改哪一侧。确与当前决定无关的遗留问题，记录关联判断依据后作为非阻塞项；仍影响关键修复选择的未决项写入 `unknowns`，按 [自主推进与停止](#自主推进与停止)处理。

### 语义方向歧义

当当前变更证据支持多个合理的修复解释，而它们对应不同或相反的目标行为，且现有证据不足以区分时，必须认定存在关键意图歧义，暂停依赖该选择的候选修改与发布。同一目标下的不同实现方式可自主择优；不要求枚举没有证据支持的任意假设。

接口、实现和调用方可能在同一特性的不同提交中分阶段引入。应结合整个特性变更判断，不能把先出现的签名当作已稳定契约，也不能仅凭较晚的调用认定最终意图。提交顺序、签名延续时间、改动范围、相对于现有实现或当前样例的运行时等价、编译通过，不能因数量叠加就成为目标契约依据；整组证据若仍同时容纳相反语义方向，歧义就未消解。故障机制已明确或被称为机械性修正，也不豁免这一要求。

判定歧义已消解，必须引用适用于当前变更的目标行为依据，指出重要解释在哪些输入、条件或兼容性要求下产生行为差异，并说明证据如何排除有依据的重要替代解释。仅证明一个修法可行、另一方向尚未实现，或没有找到反对所选修法的材料，不满足该判据。

依据可来自当前适用的声明、契约、测试、迁移记录及完整变更，也可由这些材料形成有据推断；核对版本、适用范围与重要反证，不限定为作者解释或某份文档。材料名称不保证区分力：若样例或测试在两个方向下结果相同，其通过不能消解分歧；仅从候选实现反推的预期也不能证明目标行为。

在宣告消解前，按 [变更上下文与预期行为](#变更上下文与预期行为)读取已定位、可访问且直接影响该判断的材料，围绕行为分歧取证并处理重要反证。取不到的材料记录缺口及影响，不把“未查到”当作另一方向不存在；证据已经充分时无需穷尽所有材料。修复任务将各解释、区分性证据和放行或停止的依据写入 [候选修改前的准入记录](repair-and-verification.md#候选修改前的准入记录)。

诊断实验仍遵循修复准入；不能把选定某一语义的修复包装为临时实验，或用“先改到编译通过”替代意图判断。

修复请求中歧义仍未解决时，`repair_admission` 为 `stop`，按下方关键缺口规则请求澄清、移交或结束；无可用协作通道时返回 `inconclusive`，不能报告修复已验证。若在候选实施后才发现歧义，暂停后续候选修改与发布，按既有执行规则处理当前代码和收据，不以已有检查通过掩盖目标未决。

## 自主推进与停止

在请求范围、既有权限与预算内自主取证。修复任务中，多个修法已有证据支持取舍时，自主选择并验证。

将缺口判为关键前，说明它影响哪项当前修复选择、必须保留的行为或必需验证，并给出关联依据。低置信度应具体体现为证据不足、重要解释冲突或验证缺失。非关键未知项和独立遗留建议记录后继续，不因缺少特定文档或存在泛化风险而自动结束。

关键依据不足时，先暂停依赖该判断的修改或发布，尝试范围内有依据的取证或可行替代。只读任务报告判断与缺口后结束；修复任务仍无法解决时，阅读 [交互与移交](execution-modes.md#交互与移交)，按宿主能力协作或结束。报告已知事实、已尝试途径、缺口影响及继续所需条件；保留已观察到的编译或检查结果，不将其扩大为尚未证明的修复结论。

经过合理取证仍有关键歧义时，停止相关修改，并按可用能力请求澄清、移交或以 `inconclusive` 结束，是本次调用的合格处理，不代表代码修复成功。请求中的“修复”或“尽快修绿”不豁免停止义务；也不能用这一出口跳过权限与预算内可行且有望解决关键缺口的取证。

## 路由通用与企业知识

当仓库上下文、公开软件工程知识和标准工具已经足够时，使用通用路径。

只有当正确诊断依赖内部概念、当前业务状态、受治理的组合、私有基线或专项验证器时，才使用企业领域。兼容的 Domain Knowledge Pack 必须标识版本、适用范围、来源、规则、状态查询、工具和验证器。

仅提供分类目录与判据的 Classification Profile 不等于完整领域知识包；无需为分类创建状态查询或验证器。分类引用了诊断资料时，仍核对其来源、适用性及当前决策实际需要的证据。

如果正确修复所需的领域存在歧义、兼容知识包缺失或过期、当前状态不可查询、规则冲突或验证器不可用，记录具体影响，按[自主推进与停止](#自主推进与停止)处理。不要为了出现语义相似的规则而扩大检索范围。

历史 Case 只提供假设、负向约束和验证线索。使用 `Retrieve -> Compare -> Adapt -> Verify`，绝不要将旧 Patch 重放为当前修复。

## 记录诊断评估

```yaml
diagnosis:
  classification: <失败类别、领域路由及适用的 Profile 记录>
  localization:
    level: L0 | L1 | L2 | L3 | L4
    target: <观察到的位置或边界>
  hypotheses:
    - statement: <候选机制>
      supporting_evidence: []
      conflicting_evidence: []
      predicted_signal: <什么结果会支持或反驳它>
  root_cause:
    status: confirmed | supported | unclear | not_investigated
    statement: optional
  expected_behavior: <与本次修改有关的目标行为与约束，说明声明或推断依据并引用来源>
  repair_constraints:
    must_preserve: []
    allowed_scope: []
    prohibited_directions: []
  unknowns: []
```

`classification` 引用已有分类记录即可；类别的确定性不等于 `root_cause.status`。

`hypotheses.conflicting_evidence` 记录机制反证；目标行为、约束等方面的反证及处置写入对应内容，未解决项进入 `unknowns`。未检查不等于检查后未发现；空列表本身不能证明取证完成或准入成立，不要求为了填表虚构反证。

`confirmed` 要求当前上下文中存在直接因果证据。`supported` 表示现有证据相较于重要替代解释更支持该机制，并且验证能够有意义地证伪该候选。不要仅因为建议的 Patch 看起来合理，就将 `supported` 升级。

诊断记录表达判断；修复与验证事实由实际执行证据提供。只读任务到此按[文字版结果报告](result-report.md)交付；已授权修复任务继续[修复准入与验证](repair-and-verification.md)。
