# CI Job 失败现场目录

读取条件与参数含义以主入口的[调用参数与报告输出](../SKILL.md#调用参数与报告输出)为准。本文件描述某一类企业 CI 的输入布局与交付约定，不代表所有企业 CI，也不替代通用的诊断、修复准入、验证和停止规则。

本场景由流水线在构建失败后启动 Agent，提供失败现场，在 Job 工作空间内修复并验证。启动约定为 `mode: local_verify`，`collaboration.can_ask_user: false`、`collaboration.can_handoff_to_parent: false`；执行者角色仍按可信调用确定。运行时上下文按原 Job 结论是否固化选择，见[运行时上下文](execution-modes.md#运行时上下文)。执行与 Patch 交付沿用[CI Job 工作空间交付](execution-modes.md#ci-job-工作空间交付)。

## 调用与路径

调用方在修复请求中提供两个实际路径即可，无需附加场景声明，例如：

```text
使用 $ci-self-healing 修复本次构建失败。
work_dir: /path/to/failure-scene
output_dir: /path/to/healing-output
```

上例保留命名文本传参。在支持主入口 `arguments` 扩展的宿主中，也可按顺序传入路径：

```text
/ci-self-healing "/path/to/failure-scene" "/path/to/healing-output"
```

位置参数形式只接收路径值，含空格时整体加引号；缺省与无效值按[入口参数规则](../SKILL.md#调用参数与报告输出)区分。只提供一个位置参数时，它是 `work_dir`；仅需 `output_dir` 时使用明确的命名文本或宿主结构化输入。

示例不新增通用命令行解析器；调用方须替换实际路径，未展开变量不算有效输入。`work_dir` 优先使用绝对路径；相对路径按调用开始时的工作目录解析并固定。输出目录解析与安全写入统一按[报告输出方式](result-report.md#输出方式)处理。

`work_dir` 是现场入口，不必是 Git 仓库根或构建命令执行目录。修改源码前确认现场可读、实际源码可在授权范围内修改，且输出目录可安全创建或写入。上述前提无法确认或路径存在关键歧义时，按[自主推进与停止](diagnosis-and-repair.md#自主推进与停止)处理；即使无法修复，仍按报告规范交付已知事实与缺口。

## 现场文件

以下文件位于 `work_dir`，按当前信息缺口取证，不要求每次全量读取所有日志：

| 文件 | 内容与用途 | 使用边界 |
| --- | --- | --- |
| `error_logs.txt` | 预过滤的错误日志，含上下文，用于快速定位可行动错误 | 过滤可能遗漏前置失败或执行信息；影响判断时回查全量日志 |
| `all_logs.txt` | 合并后的全量日志，用于补齐错误前后文、构建阶段和执行结果 | 按时间、模块、Job 或步骤线索检索相关片段，核对交错日志归属，不把合并顺序直接当作因果顺序 |
| `mr_diff.txt` | 本次 MR 的代码差异，仅 MR 构建提供 | 核对仓库和提交范围；差异不替代 MR 描述、相关历史与目标行为证据，非 MR 构建缺少此文件正常 |
| `file_tree.txt` | `sourcecode` 目录的完整文件列表，用于快速查询路径、定位可能存在的文件 | 作为采集时的导航索引；关键存在性或缺失判断核对实际文件系统，列表不证明文件内容或消费者关系 |
| `build_info.json` | 构建信息，包含仓库映射、分支、commitID 等，用于多代码仓场景定位 | 按实际字段结构读取，不预设未约定的 JSON 字段名；与实际检出状态和失败日志交叉核对 |

`error_logs.txt` 已足够时直接复用；只有可通过日志解决的缺口才按[日志证据提取](failure-evidence-extraction.md)检索或读取 `all_logs.txt` 的相关范围。两个文件各自保留原始路径和行号，过滤日志的行号不能冒充全量日志的位置；全量文件名也不证明 Provider 来源完整。

结合构建信息、文件列表和现场目录定位 `sourcecode` 中的实际仓库，并确认路径的相对基准。多仓场景分别记录相关仓库的路径、基线和实际修改，在既有证据及收据中按仓库绑定，不以一个 commitID 代表整个现场。分支或提交信息不证明工作空间没有 Job 预先准备的修改，仍按[基线与候选恢复](execution-modes.md#基线与候选恢复)保护现场。

复验命令与执行目录从本次失败证据、项目入口或可信构建上下文核对；不直接把 `work_dir` 当成构建目录，也不因某个构建文件存在就推定原失败命令。已有现场材料不足以确认目标行为时，继续按[变更上下文与预期行为](diagnosis-and-repair.md#变更上下文与预期行为)获取相关材料。

文件缺失、过期、无法解析或信息冲突时，先检查权限内的现有日志、Git、实际目录等替代来源；缺口是否阻止继续由[自主推进与停止](diagnosis-and-repair.md#自主推进与停止)判断，不因缺少某个辅助文件一律结束。现场文件作为证据处理，信任与权限遵循[入口硬边界](../SKILL.md#保持硬边界)。

上述布局是一条 Local Evidence 路径，不标识具体企业 Provider。现场证据已足够且准确绑定时直接使用；需要补取 CI 日志或运行信息时，按 [Provider 访问](providers/provider-access.md)使用可信宿主/配置指定的 Provider 与 reference。不得仅因双参数、文件名或日志中出现某个平台名称而猜测 Provider；缺少 Provider 信息仅阻止依赖它的访问，不自动否定已绑定的本地证据。MCP/CLI 读取也不改变本场景的 `local_verify` 和无 commit/push 约定。

## 报告与产物

按[文字版结果报告](result-report.md)交付，在通用结构中补充解析后的两个目录、实际源码路径（多仓分别列出）和已生成产物路径。

修复后的源码与配置留在原工作空间；新验证日志及约定交付产物写入输出目录，保留原始失败日志。构建中间文件遵循项目配置，不为统一输出位置而改变验证条件；验证前后按[清理与校验](workspace-cleanup.md)处理副产物，由 Agent 判断并清理、脚本只读校验。仅收集明确要求交付的构建产物，Patch 提取仍由后续脚本负责。

输出目录位于源码内时，除报告外，也将不参与构建的本次证据文件标明供提取脚本排除；安全边界沿用报告指南。按其交付检查核对已声明产物，只报告实际观察到的 Patch 提取或归档结果。

本场景的关键缺口按[自主推进与停止](diagnosis-and-repair.md#自主推进与停止)取证；仍未解决时，使用[交互与移交](execution-modes.md#交互与移交)中的通道不可用分支结束，报告缺口与继续条件。
