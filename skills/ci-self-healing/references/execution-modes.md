# 执行模式

修复任务在文件写入、候选验证、交互或移交前读取本文件。模式选择以 [入口](../SKILL.md#选择模式)为准；本文件集中定义工作空间操作、协作与交付。

## 运行时上下文

| 上下文 | 含义 |
| --- | --- |
| `local_checkout` | 在本地仓库检出中进行交互式或自动化修复 |
| `inline_ci_job` | Job 结论固化前，由能捕获失败命令的包装器调用修复 |
| `terminal_repair` | Provider 已固化步骤或 Job 失败后才开始修复 |

运行时上下文不是验证模式，也不证明协作能力。`local_verify` 可在以上任一工作空间中执行；`terminal_repair` 的本地验证不能改写已固化的原 CI 结论。

## 交互与移交

协作路线由[执行身份与协作能力](core-contracts.md#执行身份与协作能力)决定，独立于验证位置。在诊断指南判定关键缺口仍未解决后，使用下列分支。

| 条件 | 当前执行者的行为 |
| --- | --- |
| 适用策略明确禁止完成任务所必需的动作 | 返回 `denied`；只有策略允许申请的额外授权才进入审批分支 |
| `executor_role: main` 且用户交互能力已声明并可用 | 向用户说明具体缺口；需要目标行为时提出澄清或业务选择，需要额外权限时申请具体动作审批 |
| `executor_role: subagent` 且向主 Agent 移交的能力已声明并可用，接收者已确定 | 按下方交接内容提交给主 Agent，结束当前子任务；后续安排由主 Agent 决定 |
| 角色未知、所需能力未声明或相应通道不可用 | 以 `inconclusive` 结束并报告缺口和通道情况，不推测本地环境一定可交互 |

主 Agent 直接执行本 Skill 时，取证、修复和验证要求适用于它自身。收到用户补充或审批后，更新目标行为、授权范围与验证计划，重新评估准入，并检查已有证据对当前候选是否仍有效。审批不替代验证；必要审批被拒绝时返回 `denied`，必要信息仍无法取得或预算耗尽时结束并报告。交互暂停后继续仍属于本次调用，按[调用身份与限额](core-contracts.md#调用身份与限额)计数。

子 Agent 只向指定主 Agent 交回问题，不绕过它向用户请求审批或另派设计、编码 Agent。移交提交情况以通道返回的证据为准；提交失败时报告失败并按通道不可用处理。接收方是否继续执行或完成验证，取决于其指令与宿主机制，不能由子 Agent 的 Skill 保证。

交互或移交前，仍有依据的候选可保留，并标明其修改归属、已完成验证和未完成检查；已否决的候选和临时实验按 [基线与候选恢复](#基线与候选恢复)处理。交接前完成自身的工作空间写操作，提交后停止修改。接手者应核对当前文件状态与交接记录，再使用证据；更换继承的候选前确认其恢复依据，不能把它与用户原有修改混同。

### 交接内容

协作请求说明 `invocation_id`、接收方、需要补充的信息或业务选择、待审批的具体动作或待接续工作，以及证据引用；澄清与审批分开表达。

向主 Agent 移交还提供失败与变更上下文、诊断与修复依据、当前缺口、工作空间或候选 ref、基线与 fingerprint、修改文件及归属、候选恢复依据、逐项验证结果和未完成检查。区分用户/Job 原有修改、本次修改及继承候选；可用受控引用提供，无需导出完整 Patch。

等待用户答复时报告请求和当前事实，保留本次调用。子 Agent 分别报告通道是否确认提交、子任务是否结束，以及整次修复未完成事项；不将交接提交报告为已接手、已验证或整次修复已完成。

## 基线与候选恢复

- 将 Healing Session 绑定到一个 `baseline_sha`，用于 Git 来源追溯和创建远端候选 ref；它不一定等于修复介入时的工作空间内容，也不是撤销本轮修改时的默认恢复目标。
- 流水线 Job 已提供独占工作空间时，以宿主指定且后续提取脚本会读取的目录为修复和编译目录。不要自行切换到脚本无法读取的临时 checkout；确需另一个目录时，遵循宿主已声明的目录交接方式。
- 工作树脏本身不要求更换目录。先识别用户和流水线已有的修改、继承的候选及相关未跟踪文件；共享目录无法安全开展修复时，在开始修改前选择保留所需输入的隔离环境，或按关键缺口规则处理。
- 在首次修改相关位置前，保留其原始内容和文件原本是否存在的依据；这也适用于诊断实验、临时插桩和会改写文件的命令。由 Agent 跟踪自己的改动，不要求备份整个工作空间、生成完整 Patch 或提供专用快照/恢复脚本。
- 决定放弃一个候选时，Agent 自行撤销该候选引入的修改：恢复被改写或删除的原有内容，仅移除可确认由本轮新增且未被其他参与者改动的文件，保留用户和 Job 预先存在的内容。恢复依据是修复介入时的内容，而不是直接取 Git 版本覆盖。可以跨 Attempt 保留证据与假设，但不能叠加被放弃候选的代码修改。
- 恢复后读取相关文件并检查差异及文件存在性，确认被放弃候选无残留，再构建下一候选。原始依据缺失、出现并发修改，或无法区分命令副作用的归属时，暂停相关写操作，报告未恢复项并按[交互与移交](#交互与移交)处理；取得可核对的恢复依据前，不猜测性覆盖，也不对用户工作空间做整体 reset、checkout 或清理。
- 验证前为实际候选代码状态生成 fingerprint；纳入参与验证的已有修改和相关未跟踪文件，区分原有内容与本轮修复。这用于绑定被验证的状态，不要求导出 Patch 文件。

例如，Git 中配置为 `A`，Job 准备阶段改为 `B`，Agent 改为 `C` 后放弃候选，应恢复为 `B`，而不是 `A`。

## `local_verify`

取得本地候选准入后，在已确认工作空间执行候选修改与验证计划，按 [结果判定](repair-and-verification.md#结果判定)决定交付、继续候选或结束。调用身份和循环限额只按 [核心合同](core-contracts.md#调用身份与限额)计算。

在 `inline_ci_job` 中，包装器须在结论固化前捕获失败命令并保留证据，且仅在满足本地验证合同时返回成功。若 Provider 已固化失败步骤或 Job，按 `terminal_repair` 保留该失败事实，不将工作空间验证成功描述为原始流水线已通过。

## CI Job 工作空间交付

在远端 Runner 的指定 Job 工作空间内修改、编译并交给后续脚本提取 Patch，属于 `local_verify`。本场景不执行 commit、push，不发布候选 ref，也不自动触发另一轮流水线；Agent 留下已修改、已验证的代码并按 [结果报告](#结果报告)交付。

后续脚本负责 Patch 提取、打包和归档；Skill 无需导出完整 Patch，也不以是否已导出作为验证成功前提。交付后保持待提取内容不变，不 reset、清理或继续改写。脚本需在工作空间销毁前接手，Skill 只能报告已观察事实，不能声称尚未观察到的提取或持久化已完成。

## `remote_verify`

另行远端验证时读取 [远端执行指南](remote-verification.md)和 [Provider 合同](provider-contract.md)。本地工作空间规则仍适用；外部写入的权限与步骤不从 Job 运行位置推导。

## 结果报告

报告 `invocation_id`、模式、已观察失败，引用诊断与修复依据；分别说明候选要实现或保留的目标行为及其依据、实际执行的检查及其覆盖范围，不用检查通过替代行为判断。列出实际工作空间绝对路径、`baseline_sha`、候选 fingerprint、修改文件及归属、逐项检查与结果、按 [结果判定](repair-and-verification.md#结果判定)复核后的结论和剩余缺口。仅有取证或被拒绝的调用如实注明没有候选，候选字段不适用；未决目标行为如实报告为缺口，不为补齐报告而猜测。

CI Job 交付注明代码已留在指定目录供后续脚本提取，以及尚未覆盖的外层检查。远端模式补充专用 ref、候选 SHA、触发方式、Provider 运行身份、最近观察时间和是否仍需后续观察。需要协作时按本文件交接规则单列请求和调用是否结束。
