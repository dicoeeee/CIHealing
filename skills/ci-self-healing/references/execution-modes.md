# 工作空间安全与模式约束

本文件定义写入式诊断实验、候选修改或验证中的工作空间规则与模式约束。模式选择以[入口](../SKILL.md#选择模式)为准，本文件不重新选择模式或授予权限；关键缺口须记录影响及继续所需条件，不自行发起协作或结束整次调用。

## 运行时上下文

| 上下文 | 含义 |
| --- | --- |
| `local_checkout` | 在本地仓库检出中进行交互式或自动化修复 |
| `inline_ci_job` | Job 结论固化前，由能捕获失败命令的包装器调用修复 |
| `terminal_repair` | Provider 已固化步骤或 Job 失败后才开始修复 |

运行时上下文不是验证模式，也不证明协作能力。`local_verify` 可在以上任一工作空间中执行；`terminal_repair` 的本地验证不能改写已固化的原 CI 结论。

## 基线与候选恢复

工作空间保护要求保留修改归属与恢复依据，不表示介入时的内容正确、稳定或不得作为修复对象。满足修复准入且处于授权范围内的内容，可以进行必要修改、整合或删除；仍须按下方规则保留原始内容，并在放弃候选时安全恢复，不能覆盖无关或并发修改。不得仅凭内容由失败变更新增或参与失败机制，就认定其应被删除，或免除恢复责任。

- 同一次 Healing Session 对每个参与仓库分别固定 `baseline_sha`，关联仓库身份和实际工作空间；单仓调用只有一项，多仓调用按仓库与基线绑定分别记录。每个基线用于对应仓库的 Git 来源追溯和远端候选 ref 创建，不一定等于介入时的工作空间内容，也不是撤销本轮修改时的默认恢复目标。
- 流水线 Job 已提供独占工作空间时，以宿主指定且后续提取脚本会读取的目录为修复和编译目录。不要自行切换到脚本无法读取的临时 checkout；确需另一个目录时，遵循宿主已声明的目录交接方式。
- 工作树脏本身不要求更换目录。先识别用户和流水线已有的修改、继承的候选及相关未跟踪文件；共享目录无法安全开展修复时，在开始修改前选择保留所需输入的隔离环境，或按关键缺口规则处理。
- 在首次修改相关位置前，保留其原始内容和文件原本是否存在的依据；这也适用于诊断实验、临时插桩和会改写文件的命令。由 Agent 跟踪自己的改动，不要求备份整个工作空间、生成完整 Patch 或提供专用快照/恢复脚本。
- 决定放弃一个候选时，Agent 自行撤销该候选引入的修改：恢复被改写或删除的原有内容，仅移除可确认由本轮新增且未被其他参与者改动的文件，保留用户和 Job 预先存在的内容。恢复依据是修复介入时的内容，而不是直接取 Git 版本覆盖。可以跨 Attempt 保留证据与假设，但不能叠加被放弃候选的代码修改。
- 恢复后读取相关文件并检查差异及文件存在性，确认被放弃候选无残留；这一事实是后续候选的前置条件，不自行启动下一候选。原始依据缺失、出现并发修改，或无法区分命令副作用的归属时，暂停相关写操作，记录未恢复项及继续所需依据；取得可核对的恢复依据前，不猜测性覆盖，也不对用户工作空间做整体 reset、checkout 或清理。
- 验证前为实际候选代码状态生成 fingerprint；纳入参与验证的已有修改和相关未跟踪文件，区分原有内容与本轮修复。这用于绑定被验证的状态，复用已有修改读回与候选记录；不要求额外导出 Patch、全仓快照或逐项产物清单。未变化的有效绑定直接复用。

例如，Git 中配置为 `A`，Job 准备阶段改为 `B`，Agent 改为 `C` 后放弃候选，应恢复为 `B`，而不是 `A`。

## 候选与验证有效性

验证后、交付前复用已有差异、修改读回和检查记录，核对最终候选的源码、配置及需要交付的生成代码仍受验证覆盖，保护用户/Job 原有修改和相关未跟踪文件。构建正常生成且已被本轮检查覆盖的交付代码可保留；发现未验证的候选变化、误删误改或必要输入漂移时，处理相关范围并重评受影响检查。无法确认的关键变化如实记为缺口，不沿用失效的通过记录。

普通编译产物、缓存和空目录可以保留，不要求全量扫描、前后哈希清单、产物登记或与构建前路径集合一致。仅当实际构建入口要求 clean，或已有证据表明旧产物会干扰验证时，在原权限内按项目已确认的安全方式处理相关范围，保护原有输入与证据；不为结束任务额外执行 clean。不新增检查文件或可选清理流程。

停止本次仍在写入的实验/验证进程，保留必要日志、原始结果、身份收据和恢复依据。产物、独立验证目录和临时空间的回收由宿主或用户按工作空间生命周期管理；Skill 不逐项登记或证明回收完成，也不把文件回收当作进程已停止。无法确认进程停写且影响候选稳定性时披露缺口。

## `local_verify`

取得本地候选准入后，候选修改与验证使用已确认工作空间及相应计划，沿用核心合同确定的调用身份和循环限额；记录实际修改、逐项结果与剩余缺口，供主入口判断后续动作。

在 `inline_ci_job` 中，包装器须在结论固化前捕获失败命令并保留证据，且仅在满足本地验证合同时返回成功。若 Provider 已固化失败步骤或 Job，按 `terminal_repair` 保留该失败事实，不将工作空间验证成功描述为原始流水线已通过。

## CI Job 工作空间交付

在远端 Runner 的指定 Job 工作空间内修改、编译并交给后续脚本提取 Patch，属于 `local_verify`。本场景不执行 commit、push，不发布候选 ref，也不自动触发另一轮流水线；Agent 在最终报告中说明实际留下的代码及其验证范围。

后续脚本按宿主接入约定负责 Patch 筛选、提取、打包和归档，排除普通编译产物、报告与取证输出。Skill 留下修复后的源码和配置，无需导出完整 Patch，也不以产物已回收或 Patch 已导出作为验证成功前提。交付后保持待提取内容稳定；接手规则未知或无法满足时披露交接缺口，不声称可安全提取，也不恢复全量清理流程。只报告已观察到的提取或持久化结果，宿主需在工作空间销毁前接手。

企业需要变更清单或其他接手文件时，在固定企业输出规范中声明，按输出适配与交付逐项生成。实际变更数据须与最终工作空间一致，排除普通编译副产物，按用途保留实际交付的生成代码；清单不替代修改归属核对或证明外层已按它提取；无数据使用企业明确的合法空模板，未配置规范时不自行增加清单。

## `remote_verify`

另行远端验证使用入口已安排的远端指南及 Provider 合同，保留实际候选、权限及逐项检查计划。本地工作空间规则仍适用；外部写入的权限与步骤不从 Job 运行位置推导。

## 结果报告

本模式需保留的报告事实包括实际工作空间、候选与来源、修改/恢复情况、逐项验证及未完成事项。双参数流水线修复使用结果报告；其他调用按输出适配交付普通结果说明。交付由主入口安排。
