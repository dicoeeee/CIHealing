# 依赖诊断与修复

本指南补充依赖问题的取证、修复位置与验证要求；共用[诊断与上下文](diagnosis-and-repair.md)，不新增准入、审批或状态流程。只读任务保持只读取证，涉及实验写入、候选修改和验证的内容仅在已授权修复分支使用。

## 适用范围与分流

依赖问题的诊断范围包含项目的直接与传递依赖、构建插件依赖、仓库内模块产物，以及依赖下载、私服访问、制品缺失、锁定不一致和平台/二进制兼容问题。是否进入自愈由实际原因决定，不由错误名称决定；源码与依赖问题重叠时按信息缺口组合使用领域指南。

- 请求坐标、版本约束、可见性或项目仓库配置有误，可以在满足通用准入后修复；下载或认证失败不自动等于基础设施故障。
- 已确认属于临时网络、仓库服务或其他基础设施恢复的失败，按[通用失败准入](diagnosis-and-repair.md#准入正确的失败)分流，不通过改版本、替换来源或删除依赖绕过。
- 制品未找到时，区分请求错误、访问受限、上游尚未提供，以及仓库内生产或消费关系错误。不能仅凭一次查询失败认定制品不存在，也不能默认发布制品或扩展外部权限。
- 原因尚未确认时继续针对性取证；不能因暂时无法修复就判为非修复路径。仍有关键缺口时按[自主推进与停止](diagnosis-and-repair.md#自主推进与停止)处理，领域示例见[依赖问题中的关键缺口](#依赖问题中的关键缺口)。

## 目标与实际依赖

目标是在符合目标行为、兼容性和来源约束的前提下，让构建及运行取得并使用正确依赖，而不是找到任意能下载或能编译的版本。

区分“项目需要什么 → 声明了什么 → 实际解析结果 → 取得了什么制品 → 实际使用了什么”。这些是判断视角，不是必须依次完成的阶段；按当前关键缺口检查，复用有效证据。失败发生在解析之前时，先依据当时的声明、请求、配置与日志定位，不要求取得尚不存在的完整依赖图或消费结果。

按[变更上下文与预期行为](diagnosis-and-repair.md#变更上下文与预期行为)联查相关 MR/提交中的源码、依赖声明、锁定记录、构建配置、测试和迁移材料。当前声明、历史锁定或本机已有产物都是待核对的证据，不能单独当作必须保留的目标；也不因某个版本更新或曾构建成功就推导当前意图。

下表用于选择区分性证据，类别允许交叉，不映射为固定修法：

| 诊断视角 | 当前需要区分的问题与证据 |
| --- | --- |
| 声明与可见性 | 依赖是否被正确声明，坐标/包名、scope、可选项或条件配置是否让它进入失败阶段；区分未声明与声明后不可见 |
| 版本与约束 | 直接/传递关系、有效版本管理、覆盖/排除和解析规则为何选中当前版本；核对相关消费者要求，不把清单中的版本等同于实际结果 |
| 获取与来源 | 实际请求的制品身份、仓库/镜像选择、访问结果与缓存来源；区分错误请求、错误路由、权限不足和暂时不可取得 |
| 锁定与产物一致性 | 项目使用的声明、锁文件、制品修订与校验记录是否对应；产物来自受控仓库、宿主准备、当前构建还是未说明的手工安装 |
| 平台与二进制兼容 | 实际选中的架构、ABI、运行时要求、构建变体及工具运行平台/目标平台；名称和版本相同不保证产物适用 |
| 构建内生产与消费 | 应由哪个模块或任务产出、是否已执行、当前消费路径是否指向该产物；区分上游未构建、顺序/依赖关系错误与消费旧产物 |

### 按生态选择证据入口

- **Maven**：按需检查父 POM/BOM、Profile、属性、有效依赖树、scope、仓库与镜像配置及失败阶段的实际产物。区分项目依赖和插件自身依赖，项目的 `dependencyManagement` 不控制插件的传递依赖，不能据项目依赖树推断插件依赖已经正确。[Maven 依赖机制](https://maven.apache.org/guides/introduction/introduction-to-dependency-mechanism.html)。涉及 Java 编译时结合[Java/Maven 指南](java-maven-compilation.md)核对实际 classpath/module-path 和接口。
- **C/C++**：结合项目实际使用的包管理声明/锁定、配置、工具链、包查找结果和构建产物。使用 CMake 时区分 `find_package` 的查找来源、实际 package config/Find module 和 imported target，以及从源码引入的依赖；核对实际头文件与库路径，不仅看包名。[CMake 依赖指南](https://cmake.org/cmake/help/latest/guide/using-dependencies/index.html)。涉及编译、链接或 ABI 时结合[C/C++ 指南](c-cpp-compilation.md)。

使用项目已有工具和适用版本，不照搬另一生态或最新版本的解析规则。优先读取已有日志与元数据；解析、安装、查询或生成依赖图的命令也可能联网、写缓存/锁文件或运行插件及脚本，不能仅凭“取证”目的认定为只读。执行权限与副作用遵循[请求范围](../SKILL.md#1-确认任务与现场)和[工作空间保护](execution-modes.md#基线与候选恢复)，不输出凭据或完整敏感配置。

## 修复位置与变更影响

候选修改前沿用[修复依据核查](diagnosis-and-repair.md#修复依据核查)与[修复准入](repair-and-verification.md#候选修改前的准入记录)，不另设依赖专属表单。

- 升级、降级、排除、替换、补齐依赖和修改源码都只是候选，没有固定优先级。先说明目标要求，核对实际依赖与实际用法是否满足这些要求，定位不一致发生在哪一环；不能从某个候选可下载、冲突消失或编译通过倒推它符合目标。
- 修复声明、上层版本管理、模块关系、项目配置或源码时，核对该位置的权威来源与影响范围；不能因子模块更容易改，就用局部覆盖掩盖上层错误。既有依赖与较新调用都不自动代表最终意图，有据的相反目标仍按[语义方向歧义](diagnosis-and-repair.md#语义方向歧义)取证。
- 核对候选实际改变的直接/传递依赖、来源、可见性、构建变体和相关消费者。存在多版本不自动意味着必须统一；排除或统一不能只解决当前模块而忽略已确认的兼容性要求。
- 按项目机制维护声明与锁定的一致性。刷新锁文件、变更 BOM 或修改一行版本都可能扩大实际依赖变化；检查生成差异，解释与目标相关的变化，不顺带升级无关依赖。锁文件与声明冲突时先判断当前权威依据，不默认删除或重建其中一方。
- 不默认清空共享缓存、改全局环境或手工安装“能用”的产物。确有证据需要刷新或隔离缓存时，控制范围并保留必要恢复依据；不要破坏 Job 已准备且无法重建的输入。
- 来源与校验必须有独立依据。校验不一致不能直接证明攻击，也不能通过关闭校验或将当前文件的哈希改作预期值来消除疑点；需核实可信来源和预期内容后再处理。[制品校验机制](https://maven.apache.org/resolver/expected-checksums.html)。不得为修绿绕过适用的来源、安全或访问策略。

项目内有据且已授权的依赖调整自主执行，不逐项重新申请同一授权。发布上游制品、调整共享私服、配置新凭据或修改范围外仓库属于另行协调或授权问题，本指南不授予这些权限。

## 验证与结果范围

在既有[验证计划](repair-and-verification.md#分层验证)中声明检查，不新增验证层级。以原失败目标、配置和验收范围为基准，通过候选对应的正常构建入口复验；构建规则或依赖参数经有据修正时，验证当前实际生成的动作，不机械重放旧参数，也不以临时手改命令绕过项目配置。

按失败与候选影响选择必要检查：

- **选择正确**：当前解析结果与已确认目标相符；相关版本、来源、变体和锁定内容对应实际制品，而不是只确认声明已被修改。
- **消费正确**：原失败及相关编译、链接、测试、插件或加载检查实际通过；共享依赖变更覆盖受影响消费者。下载或解析成功不能代替必要的消费验证。
- **恢复条件明确**：说明依赖如何由项目或宿主约定的可信来源、构建步骤取得。不以仅存在于本机且未纳入约定的手工制品证明交付可复现；宿主合法准备的产物不要求重新发布或下载。

只有缓存、来源或环境差异可能影响判断时，才补充范围受控的刷新、隔离或重建验证，不要求每次全量清缓存或启动干净环境。仅当前工作空间恢复时如实限定结果范围，不冒充其他平台或新流水线已验证；没有候选修改时报告环境恢复事实，不冒充候选修复成功。

在[既有收据](core-contracts.md#收据绑定与失效)中记录与结论有关的依赖结果、制品身份、来源和执行环境；版本号不足以区分产物时，补充可用的修订或内容标识。相关解析结果或产物漂移后复核受影响的证据。成功仍按[通用结果判定](repair-and-verification.md#结果判定)，不以编译变绿豁免目标行为复核，也不因验证环境缺失自动切换远端模式。

## 依赖问题中的关键缺口

以下示例帮助识别依赖问题中的关键缺口；是否暂停相关修改或继续取证，按[自主推进与停止](diagnosis-and-repair.md#自主推进与停止)判断。

- 升级依赖与修改源码对应不同目标，证据仍不足以区分；或已确认现有必要约束无法兼容，必须由外部决定新的取舍。
- 决定修法的内部兼容性材料、实际产物或来源事实无法取得；或制品完整性与可信来源疑点仍无法解释。
- 必要动作涉及未授权的上游发布、共享仓库、凭据或范围外修改，需要有权限的负责人提供条件。
- 所选模式下必需验证无法完成且无有效替代证据。

需要协作时，按[交互与移交](execution-modes.md#交互与移交)处理；在[现有交接内容](execution-modes.md#交接内容)中补充相关依赖的目标要求、实际版本/制品与来源、未决差异及其证据引用。
