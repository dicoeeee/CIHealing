# 远端验证

仅在任务明确选择另行远端 CI 验证时读取。CI Runner 内修改、编译并交给脚本提取 Patch 的路径按 [CI Job 工作空间交付](execution-modes.md#ci-job-工作空间交付)执行，不因运行位置而进入本分支。

## 授权与能力

在任何外部写入前，确认请求或可信宿主已授权所需的专用候选 ref 提交、推送及流水线触发/重跑动作，并满足适用策略。`remote_verify` 标签和工具可用性本身不构成授权；已有授权范围内自主执行，无需逐阶段重批。

允许的发布目标限于专用候选命名空间。不得写入默认或受保护分支、覆盖用户或共享 ref、对这些 ref force-push、合并、打标签、发布版本、部署、弱化检查/分支保护或自动删除分支。Provider 专用实现也须保持基线隔离、候选身份、审计与幂等性。

读取 [Provider 合同](provider-contract.md)，完成该模式的能力协商，确认可发布准确候选、解析或触发对应运行，并直接或通过宿主取得逐项验证证据。缺少权限、能力或验证条件时，暂停依赖该条件的动作，按 [交互与移交](execution-modes.md#交互与移交)处理；保留仍有依据的候选与实际取得的收据。

## 执行

1. 核对 [修复准入与验证](repair-and-verification.md)中的计划：发布前本地检查与远端承担的检查已区分，远端检查映射到具体命令或 Job/Check；当前候选满足 `allow_remote_candidate`。
2. 从固定 `baseline_sha` 创建以本次调用和 Attempt 标识的唯一专用候选 ref，只纳入获准的连贯修复。工作空间已有修改不自动获得发布授权；转移候选使代码或相关输入变化时，按收据失效规则重跑受影响的发布前检查。
3. 外部写入前立即复核实际候选、HEAD、差异范围、策略及授权仍然匹配；通过后在授权范围内 commit 并 push 专用 ref。
4. 按 Provider 的 [触发与幂等规则](provider-contract.md#完成与身份规则)解析已有运行或触发目标流水线，记录准确候选 SHA、运行身份和观察时间。
5. 获取验证计划各项检查的实际结果，按 [结果判定](repair-and-verification.md#结果判定)决定是否通过。失败时保留新证据，再按通用修复流程和本次调用限额决定后续候选。

流水线排队或运行时，按预算继续观察；需要结束当前执行时保留运行引用和观察时间，后续观察由宿主按 [实时观察边界](provider-contract.md#实时观察边界)接续。本 Skill 不自行建立新的唤醒服务。

V4 期间的基础设施或 Provider 失败不证明候选正确或错误；保留实际失败状态，注明候选验证证据不完整，交给适当恢复机制或按关键缺口规则处理，不以无限基础设施重试消耗修复 Attempt。

原 Job 失败已经固化时，新候选只能通过新的运行取得新结论，不能改写旧运行。具体报告字段遵循[文字版结果报告](result-report.md)。
