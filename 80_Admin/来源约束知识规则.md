# 来源约束知识规则

> [!important] 规则目标
> 来源约束目录只保存能够由公开原文直接支持的内容。引用不能把推断变成事实；命题范围不得超过原文范围。

## 1. 适用目录

以下目录默认执行 `source-bound` 内容策略：

- `30_Resources/**/Sources/`
- `30_Resources/**/Knowledge/`

以下目录保存原始证据，不写分析正文：

- `99_Attachments/**/Web/`
- `99_Attachments/**/Papers/`

路径规则优先于笔记的 `type` 或 `subtype`。严格目录中的笔记即使标记为 Evergreen，也不得加入个人推理或设计内容。

## 2. 原文与权威来源

“原文”指对命题拥有直接说明权的公开材料，包括：

- 官方产品文档、官方 API 文档与官方发布说明；
- 官方公开仓库中的源码、配置、测试与规范；
- 论文原文、标准或规范原文；
- 作者本人发布的工程文章、演讲文字稿或案例记录。

二手转述只能作为检索线索，不能独立支撑严格目录中的机制命题。无法读取原文时，记录为覆盖缺口，不用其他材料补写成已确认事实。

## 3. 允许内容

严格目录只允许以下四类判断：

| 判断类型 | 写作要求 |
| --- | --- |
| 直接事实 | 原文或公开源码明确描述；保持适用条件、对象与时态 |
| 厂商主张 | 明确保留“厂商称/页面称”等来源归属，不改写成独立事实 |
| 证据缺口 | 只说明已核对的公开材料没有披露什么，不推测可能实现 |
| 来源冲突 | 并列记录各原文的不同表述、版本与核验日期，不自行归一化 |

允许忠实翻译、结构化摘录和不增加新含义的压缩摘要。译文存在多种合理解释时，保留原文术语并注明歧义。

## 4. 禁止内容

严格目录禁止：

- 个人判断、价值评价、建议与经验性结论；
- “合理推断”“可抽象为”“这意味着”等超出原文的解释；
- 自定义组件、角色、状态机、因果关系或能力边界；
- 自有架构、接口、算法、伪代码、落地顺序和验收方案；
- 把厂商效果描述改写成已独立验证的效果；
- 用常见实践补齐原文没有公开的实现；
- 用任务级验证代替完整 CI、Required Checks、业务正确性或生产安全。

常见审查信号包括：“值得借鉴”“应当”“更适合”“合理推断”“我们可以认为”“设计判断”“自有方案”。这些表述出现时，内容必须迁出严格目录，除非它们是带清晰归属的原文引述。

## 5. 命题与证据

每个独立机制命题必须同时具备：

1. 可访问的原文链接或公开源码链接；
2. 可定位的章节、标题、源码路径或稳定锚点；
3. 原文适用对象、条件与版本信息；
4. 核验日期；
5. 判断类型。

一条证据可以支持多个不超出其范围的命题；一个组合命题若包含多个事实，必须分别给出证据。只有首页链接、搜索结果或笼统的“官方文档”不足以完成命题级追溯。

## 6. 目录职责

### Sources

回答“原文具体说了什么”：

- 保存来源身份、版本、URL、快照与内容指纹；
- 保存忠实翻译、结构化摘录和单一来源的命题表；
- 不保存准入评价、个人理解、跨来源推理或方案建议。

资料准入评价保留在 `00_Inbox/`；正式导入后，`Sources` 只保存原文约束内容。

### Knowledge

回答“公开原文能够共同确认什么”：

- 可以按机制重新组织多个原文中的直接事实；
- 每个命题仍须逐条回到原文；
- 只能记录公开边界、缺口和冲突，不能创造新的解释层。

### 非严格目录

推理、设计和验证分别进入：

- `10_Projects/**/Architecture/`：架构推理、本地假设与设计选择；
- `10_Projects/**/ADR/`：需要明确取舍的决策；
- `10_Projects/**/Experiments/`：需要实验证明的假设；
- 明确标注为个人洞察且不位于严格目录的笔记。

迁出内容必须反向链接对应 Source 或 Knowledge，不能切断证据链。

## 7. Frontmatter 契约

严格目录中的正式笔记统一使用：

```yaml
content_policy: source-bound
inference_allowed: false
design_content_allowed: false
claim_citation_required: true
authority_scope: public-primary-sources
```

设计与实验笔记应显式使用 `content_policy: design`、`decision` 或 `experiment`，避免与来源约束知识混淆。

## 8. 审核与变更

- AI 新建或修改正文后设置 `ai_generated: true`、`reviewed: false`。
- 人工逐条确认命题与证据后，才能设置 `reviewed: true`。
- `reviewed: true` 只表示经过人工确认，不会扩大允许内容类型。
- 原文发生实质变化时创建新快照，更新 `verified_at` 和内容指纹；旧快照不覆盖。
- 发现严格笔记混入主观内容时，先迁入相应非严格目录，再收敛原笔记；不静默丢弃仍有价值的设计内容。

## 9. 最小验收清单

- [ ] Frontmatter 声明 `content_policy: source-bound`
- [ ] 正文只出现四类允许判断
- [ ] 每个机制命题都有可定位原文
- [ ] 厂商效果描述保留来源归属
- [ ] 没有推断、自有方案、建议或新造实体
- [ ] 未公开内容保持为证据缺口
- [ ] 迁出的推理或方案保留反向证据链接
