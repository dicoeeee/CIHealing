# CI 自愈通用与企业领域诊断修复技术方案

> [!warning] 设计边界
> 本文是尚未经过实验验证的技术方案草稿。本期范围包括 CI 失败材料收集、问题路径判断、根因诊断、修复候选生成、Healing Session 自适应循环和流水线验证；不包括权限、人工审核、合并与发布。网络抖动、资源不足、Runner 故障和 Flaky 等执行问题也不在本期范围内。

## 方案摘要

CI 失败后，系统先形成统一的失败材料，再判断根因是否依赖企业内部规则或当前业务状态：

- 不依赖企业内部知识时，进入通用问题路径；
- 依赖企业内部知识时，进入企业领域问题路径；
- 两条路径形成根因证据后，进入同一个 Healing Session；
- 一个 Healing Session 最多连续生成并验证 5 个完整修复候选；
- 每轮累积诊断证据，但都从同一 `baseline_commit` 重建代码状态；
- 首个通过全部三层验证的候选结束本次 Healing Session。

```text
CI 失败
  → 收集失败材料
  → 判断根因是否依赖企业内部知识
      ├─ 否：通用问题诊断
      └─ 是：企业领域问题诊断
  → 建立根因证据
  → 启动 Healing Session
      → Attempt 1：生成完整候选 → 三层验证
      → 未通过：吸收新证据并自主规划下一轮
      → Attempt 2…5：重建完整候选 → 三层验证
  → candidate_passed / no_progress / inconclusive
```

两条路径的差异只在诊断材料和专用工具；候选生成、循环控制、验证标准与结束状态保持一致。

## 1. 术语与状态

| 术语 | 定义 |
| --- | --- |
| 通用问题 | 仅依靠 CI 日志、仓库上下文、标准工程工具和公共软件工程知识即可解释根因的问题 |
| 企业领域问题 | 必须依靠企业内部规则、当前业务状态或专用工具才能正确解释根因的问题 |
| 领域识别 | 根据失败上下文选择通用路径或企业知识域，并定位兼容的知识包、工具集和策略命名空间；不在路由阶段预判具体根因 |
| Domain Knowledge Pack | 可版本化、可校验且适用范围明确的企业领域能力包，包含知识、规则、Schema、工具、验证器、来源和外部控制边界引用 |
| Case Library | 保存历史诊断、修复和验证经验的案例库，只提供参考证据，不直接给出当前答案 |
| 企业领域诊断证据 | 企业领域路径在运行时形成的事实性中间产物，记录路由结果、知识包版本、适用规则、当前状态、最近变更、业务意图及证据缺口，不直接给出修复候选 |
| 统一诊断结论与修复约束 | 对通用诊断材料或企业领域诊断证据进行综合推理后形成的候选生成契约，包括根因假设、证据链、影响范围、修复边界和必需验证 |
| Healing Session | 针对一次初始 CI 失败开展的有界诊断、候选生成和验证过程 |
| Attempt | 一个完整修复候选进入验证的计数单位；诊断和证据收集本身不单独计数 |
| `baseline_commit` | Healing Session 固定使用的基线提交；每个候选都相对该提交完整生成 |
| 修复候选 | 针对 `baseline_commit` 的完整变更集合，不是在上一轮失败候选上追加的增量补丁 |
| `candidate_passed` | 候选通过本方案要求的全部验证，但尚未被正式采用、合并或发布 |
| `no_progress` | 连续尝试未产生足以支持继续修复的新证据、假设或有效候选 |
| `inconclusive` | 因证据、规则、环境、验证条件或资源边界不足而无法得出可靠结论 |
| Case Draft | Healing Session 结束后形成的案例草稿，未经审核和准入，不具备案例权威性 |

`max_attempts` 固定为 5，表示一个 Healing Session 最多验证 5 个候选，而不是必须完成 5 轮。满足成功或停止条件时应提前结束。

## 2. 实施范围与控制边界

### 2.1 本期负责的能力

- 收集并保存可复现的失败材料；
- 识别通用问题路径或企业知识域，并路由兼容的知识包与工具；
- 通过当前证据形成可解释的根因判断；
- 在隔离环境中生成并验证完整修复候选；
- 在一个 Healing Session 内开展最多 5 次自适应尝试；
- 保存每轮证据、候选、验证结果和停止原因；
- 在 Healing Session 结束后形成 Case Draft。

### 2.2 本期不负责的能力

- 获取或扩大代码、配置和内部系统权限；
- 代替人工审核业务意图或高风险变更；
- 自动合并、发布或部署候选；
- 处理网络、资源、Runner 和 Flaky 等执行恢复问题；
- 证明当前流水线未覆盖的业务正确性或生产安全性。

`candidate_passed` 是验证状态，不是采用状态。正式采用、合并和发布必须由本方案之外的控制流程决定。

## 3. 通用问题与企业领域问题的判定

问题分类依据是**正确解释根因所需的知识类型**，不是失败发生在编译、测试还是构建阶段。

### 3.1 通用问题

通用问题可以仅凭以下材料完成诊断：

- CI 日志和错误信息；
- 当前仓库的代码、测试、配置和最近变更；
- 编译器、测试框架、构建工具和包管理器；
- 公共软件工程知识。

典型问题包括语言类型错误、链接错误、导入错误、接口不匹配、lint 失败、稳定可复现的测试断言失败和公开依赖版本冲突。

### 3.2 企业领域问题

企业领域问题必须补充至少一类内部信息：

- 产品、版本、场景或构建变体之间的关系；
- 内部配置、领域专用语言或代码生成规则；
- 内部基线、上游配置、继承和分支组合规则；
- 当前业务状态或参数来源；
- 企业专用的检查、试运行或构建任务。

日志中的“上游配置非法”只能说明存在不一致；如果正确修改依赖当前产品场景、参数来源、合法组合或业务意图，就必须进入企业领域路径。

### 3.3 判定规则

| 判断问题 | 通用问题 | 企业领域问题 |
| --- | --- | --- |
| 日志概念 | 公开语言、工具或框架概念 | 内部命令、参数、服务、缩写或领域专用语言 |
| 根因所需材料 | 仓库和公开资料足够 | 必须补充企业规则或当前状态 |
| 修复适用条件 | 通常不依赖企业产品场景 | 明确依赖产品、版本、场景或内部基线 |
| 当前状态查询 | 不需要内部系统 | 必须查询内部配置或业务状态 |
| 专项验证 | 标准工程工具足够 | 需要企业专用检查或验证任务 |

只要根因判断依赖一条关键企业内部规则，就按企业领域问题处理。通用诊断过程中遇到无法解释的内部概念时，应转入企业领域路径，不得继续猜测。

缺少普通日志、代码或运行环境等基础证据，不等于企业领域问题。只有缺失内容明确属于企业规则、内部状态或专用能力时，才切换路径；否则以 `inconclusive` 结束或等待补充证据。

### 3.4 领域识别输出

领域识别只需达到能够唯一选择兼容的 Domain Knowledge Pack、工具集和案例索引的粒度。构建配置、测试数据、版本打包等领域已经足够用于路由；参数缺失、参数冲突或继承错误等具体根因留给后续诊断确认。

| 输出 | 要求 |
| --- | --- |
| 路径 | 选择通用问题路径或企业领域路径 |
| 主领域与次领域 | 记录足以选择知识包和工具集的领域位置，不强制展开到错误子类型 |
| 路由证据 | 记录任务归属、内部标识、配置键、产品、版本、场景和依赖关系等判断依据 |
| 备选领域 | 保留仍可能适用但证据不足的其他领域，不用固定分数掩盖不确定性 |
| 知识包引用 | 记录选中的 Domain Knowledge Pack 标识与版本 |
| 路由缺口 | 记录领域冲突、知识包缺失、不适用、过期或关键上下文缺失 |

路由是否充分由 AI 基于证据判断，不设置固定置信度阈值。无法唯一选择领域时以 `inconclusive` 结束，并记录 `termination_reason: ambiguous_domain`；缺少兼容知识包时记录 `termination_reason: knowledge_pack_unavailable`。不得通过扩大到无边界检索或猜测内部语义来绕过路由失败。

## 4. 统一失败材料

两条诊断路径使用同一份基础输入：

| 信息 | 用途 |
| --- | --- |
| 失败流水线、作业、任务和命令 | 确定诊断入口 |
| 原始日志、错误位置和退出码 | 描述失败现象 |
| 当前提交与最近代码变更 | 判断失败与本次变更的关系 |
| 相关代码、测试、配置和依赖 | 建立根因证据 |
| 模块关系和任务依赖 | 确定影响范围 |
| 运行环境和工具版本 | 判断能否稳定重现 |

```text
失败材料
  = 失败命令
  + 原始日志
  + 当前代码版本
  + 最近变更
  + 相关文件
  + 依赖关系
  + 运行环境
```

失败材料只陈述可观察事实，不预先写入问题分类、根因或修复结论。

## 5. 两条诊断路径

### 5.1 通用问题诊断

通用路径执行以下基本过程：

1. 从日志定位直接失败位置；
2. 找到相关代码、测试、配置或依赖；
3. 提出一个或多个根因假设；
4. 使用代码、最近变更和工具结果排除不符合证据的假设；
5. 选择能够解释主要证据的根因与修复方向；
6. 将根因证据交给 Healing Session 生成候选。

错误表象不能直接决定修改对象。测试失败可能来自生产代码、测试预期、模拟对象或运行配置，必须通过当前实现、输入、预期和最近变更判断实际原因。

```text
TypeScript 编译失败
  → 日志：UserConfig 缺少 region
  → 最近变更：接口新增必填字段 region
  → 代码证据：两个调用点仍使用旧接口
  → 根因：接口升级后调用点未同步
  → 修复方向：为调用点补充正确的 region 来源
```

可使用的诊断工具包括编译器、LSP、静态分析器、单元测试、集成测试、覆盖率工具、格式化与 lint 工具、依赖树、锁文件、Git 差异和模块依赖信息。工具输出只能作为证据，不能仅因自动修复命令消除了错误就认定根因已经解决。

### 5.2 企业领域问题诊断

企业领域路径不是直接对全部内部文档进行语义检索，而是先用领域识别结果选择兼容的能力包和工具空间：

```text
失败上下文
  → 领域识别
  → 兼容的 Domain Knowledge Pack
  → 知识与工具路由
  → 当前状态查询
  → 企业领域诊断证据
  → 统一诊断结论与修复约束
```

知识路由先使用领域、产品、构建系统、版本和场景等结构化元数据限定范围，再在兼容范围内检索内容。检索结果必须保留来源、版本、适用范围和冲突信息，不能仅按语义相似度混用其他产品、版本或场景的规则。

工具路由只暴露当前诊断需要的查询、比较、候选生成和验证能力。工具至少区分只读诊断、候选生成与验证三类；加载工具不代表获得新的写权限，所有操作仍受本方案既有执行边界约束。

Domain Knowledge Pack 至少包含：

| 内容 | 作用 |
| --- | --- |
| Knowledge | 解释企业领域概念、实体、关系和术语 |
| Rules | 描述依赖、继承、互斥、默认值和组合约束，并使用稳定规则编号 |
| Schema | 描述参数类型、枚举、来源、版本和作用域 |
| Examples | 提供正例、反例和边界场景，辅助理解但不替代当前证据 |
| State Queries | 定义当前值、来源、继承关系、基线和生效结果的查询方式 |
| Tools | 声明当前领域可使用的只读查询、比较和候选生成接口 |
| Validators | 声明 Schema、约束、试运行、任务和下游验证方法 |
| Case Library Ref | 指向独立治理的案例库版本和索引，不把案例正文写入规则资产 |
| Control Boundary Ref | 指向本方案之外的策略与权限边界，不由知识包自行授予权限 |
| Provenance | 记录来源、所有者、版本、适用产品和更新时间 |

最小契约示例：

```yaml
domain_pack:
  id: build_configuration
  version: v3
  applies_to:
    product: product_a
    product_version: v3
    build_system: cie
    scene: feature_build
  knowledge_ref: knowledge/build-configuration-v3
  rules_ref: rules/build-configuration-v3
  schema_ref: schemas/build-configuration-v3
  examples_ref: examples/build-configuration-v3
  state_queries:
    - query_config
    - trace_config_origin
    - query_baseline
  tools:
    read:
      - compare_configuration
    propose:
      - propose_configuration_change
  validators:
    - validate_schema
    - validate_constraints
    - dependency_resolution_dry_run
  case_library_ref: cases/build-configuration@v2
  control_boundary_ref: controls/build-configuration-v3
  provenance:
    owner: build_platform
    updated_at: <更新时间>
```

领域包缺少适用范围、版本、来源或 Validator，或者适用规则发生冲突时，不得仅凭语义相似度用于自动生成候选。

企业领域路径在运行时生成企业领域诊断证据。它只记录经过查询或有明确来源的事实，不在这一层生成根因结论或修复候选。

| 输出字段 | 要求 |
| --- | --- |
| 领域识别结果 | 记录主领域、次领域、路由证据、备选领域和路由缺口 |
| 知识包引用 | 记录实际使用的 Domain Knowledge Pack 标识、版本和适用范围 |
| 适用规则 | 记录规则编号、规则内容及其适用条件 |
| 当前状态 | 记录当前值、来源、继承关系、基线和查询结果 |
| 最近变更 | 记录与当前状态或失败现象相关的本次变更 |
| 业务意图 | 记录本次变更必须保留的行为；未确认内容列入证据缺口 |
| 专用验证能力 | 记录当前可用的企业专项检查、前置条件和预期结果 |
| 证据缺口 | 记录缺失、冲突或不可查询的规则与状态 |

Case Library 提供的相似案例、历史假设、负向约束和验证线索必须单独标记为历史先验，不得写入适用规则、当前状态或根因证明。

统一诊断结论与修复约束步骤使用以下关系对企业领域诊断证据进行综合推理：

```text
企业领域诊断证据
  = 领域识别结果与知识包版本
  + 当前实际状态
  + 当前产品、版本和场景适用的规则
  + 最近变更
  + 变更要保留的业务意图
  → 根因假设与因果证据链
  → 修复约束与必需验证
```

示例：

```text
失败：upstream 配置非法
  → 领域识别
      主领域：Build Engineering
      次领域：Build Configuration
      知识包：build_configuration@v3
  → 企业领域诊断证据
      当前状态：feature_mode = independent，upstream = weekly_xxx
      当前规则：independent 模式必须使用 daily 基线
      最近变更：只将 feature_mode 从 integrated 改为 independent
      业务意图：保留 independent 模式
  → 统一诊断结论与修复约束
      根因：模式变化后基线未同步迁移
      必须保留：independent 模式
      允许修改：将 upstream 更新为 daily 基线
      禁止修改：恢复 integrated 模式以绕过失败
      必需验证：参数组合检查、依赖解析试运行和三层流水线验证
```

领域无法唯一识别、兼容知识包缺失或过期、关键参数来源不可查询、规则冲突或专用验证不可用时，应记录缺口并以 `inconclusive` 结束，不得使用旧规则或相似日志猜测答案。

### 5.3 统一诊断结论与修复约束

通用问题路径的诊断材料和企业领域路径的诊断证据最终进入同一个综合步骤。该步骤负责把不同来源的事实整理为 Healing Session 可消费的统一候选生成契约，但不直接生成补丁。

| 输出 | 要求 |
| --- | --- |
| 来源与路径 | 说明为何使用通用路径或某个企业领域，并保留关键证据来源 |
| 根因假设 | 可以保留多个候选假设及其当前可信依据 |
| 因果证据链 | 说明失败现象、相关状态、最近变更与根因假设之间的关系 |
| 影响范围 | 标明直接修改对象、相关测试、下游任务和企业专项检查 |
| 修复约束 | 分别说明必须保留的行为、允许修改的范围和禁止采用的方向 |
| 必需验证 | 列出候选必须通过的原失败复验、影响范围验证、企业专项检查和完整 CI |
| 未知项 | 明确尚未取得或无法确认的信息 |

能够形成可验证根因假设、明确修复边界和必需验证时，以上输出进入 Healing Session，作为首轮候选生成和后续自适应调整的起点。规则、状态或证据不足以支持该契约时，以 `inconclusive` 结束，不得把不完整证据转化为修复候选。

## 6. Healing Session 自适应循环

### 6.1 Healing Session 契约

一次初始 CI 失败只创建一个 Healing Session。Healing Session 固定基线、上限和结束状态，同时允许 AI 自主决定每轮的诊断与修复策略。

```yaml
healing_session:
  id: <Healing Session 标识>
  baseline_commit: <固定基线提交>
  initial_failure: <失败材料引用>
  policy:
    max_attempts: 5
    time_budget: <可选时间预算>
    compute_budget: <可选计算预算>
  attempts: []
  final_status: candidate_passed | no_progress | inconclusive
  termination_reason: <结束原因>
```

`max_attempts: 5` 是自治候选验证的硬上限。时间、计算资源、规则或证据不足可以使 Healing Session 在第 5 次之前结束。

### 6.2 循环不变量

每轮必须遵守以下不变量：

- `baseline_commit` 在整个 Healing Session 内保持不变；
- 每个候选都在干净、隔离的验证环境中相对基线完整生成；
- 失败候选不得作为下一轮代码基底直接叠加修改；
- 日志、验证结果、被否定的假设和负向约束在轮次之间持续累积；
- AI 可以复用尚未被证伪的思路，但必须重新形成完整候选；
- 所有候选使用同一成功标准；
- 首个通过全部必需验证的候选立即结束 Healing Session。

核心原则是：

> 证据持续累积，代码状态每轮重建。

### 6.3 自适应执行框架

```text
读取当前证据与历史 Attempt
  → 更新根因假设、未知项和负向约束
  → AI 选择下一步最有价值的诊断或修复行动
  → 相对 baseline_commit 生成完整候选
  → 执行三层验证
      ├─ 全部通过：candidate_passed，立即结束
      ├─ 仍有有效方向：吸收证据，进入下一 Attempt
      └─ 无法可靠继续：no_progress 或 inconclusive
```

AI 可以自主选择：

- 深化、替换或组合根因假设；
- 修正当前实现或改用另一种修复策略；
- 扩大或缩小候选范围；
- 先收集针对性证据，再决定是否生成候选；
- 调整验证顺序或增加专项检查；
- 判断新失败与候选的关系；
- 在上限前主动停止无价值的继续尝试。

本方案不为第 2 至第 5 轮规定固定脚本，也不要求 AI 在“继续细化”与“重新诊断”之间互斥选择。系统只约束证据记录、候选隔离、验证门槛和停止边界。

### 6.4 Attempt 记录

```yaml
attempt:
  index: 1
  evidence_snapshot: <本轮使用的证据>
  hypotheses: <当前根因假设及依据>
  candidate: <相对 baseline_commit 的完整候选引用>
  verification:
    original_failure: passed | failed | not_run
    affected_scope: passed | failed | not_run
    full_ci: passed | failed | not_run
  evidence_delta: <本轮新增证据与被否定的假设>
  failure_assessment: # 出现新失败时记录
    relation: related | unrelated | uncertain
    basis: <AI 的主要判断依据>
  decision:
    control: continue | pass | stop
    strategy_tags:
      - <可选的一个或多个说明标签>
    rationale: <为何继续、通过或停止>
    next_objective: <继续时填写下一轮目标>
    expected_signal: <继续时填写能够支持或否定该方向的结果>
```

`strategy_tags` 是开放、可多选的说明性标签，例如 `refine`、`rediagnose`、`alternative`、`collect_evidence` 或 `hybrid`，也可以根据实际策略增加新标签。它不是状态机转移规则，只有 `control` 控制 Healing Session 继续、成功或停止。

新出现的 CI 失败由 AI 结合候选差异、依赖关系、基线记录和验证证据判断为 `related`、`unrelated` 或 `uncertain`。本方案不规定评分阈值或固定决策树，但要求保存主要依据。只要必需验证仍失败，就不能标记为 `candidate_passed`。

### 6.5 结束规则

| 条件 | Healing Session 结果 | 说明 |
| --- | --- | --- |
| 某个候选通过全部三层验证 | `candidate_passed` | 首次通过即结束，不继续寻找更优候选 |
| 连续尝试没有有效信息或策略增量 | `no_progress` | 可以在第 5 次之前提前停止 |
| 证据、规则、环境或验证条件不足 | `inconclusive` | 不得宣布修复成功 |
| 第 5 个候选仍未通过且已无有效进展 | `no_progress` | `termination_reason: max_attempts_reached` |
| 第 5 个候选仍未通过但存在未验证方向 | `inconclusive` | `termination_reason: max_attempts_reached` |

通过后的进一步重构或优化应作为独立任务处理，不占用当前 Healing Session 的剩余 Attempt。

## 7. 三层验证

候选在隔离工作区或验证分支中应用。验证允许在确定失败后提前结束，只有进入下一层所需的前置检查通过后才继续消耗完整流水线资源。

### 7.1 原失败验证

重新运行最初失败的命令或任务，确认原始失败是否消失。原失败仍然存在时，本轮候选失败，新日志进入下一轮证据。

### 7.2 直接影响范围验证

根据候选内容运行受影响模块测试、调用方或下游检查、配置组合检查、依赖解析或构建试运行，用于发现候选对相邻功能造成的回归。

### 7.3 完整流水线验证

使用候选重新运行仓库声明的完整验证流水线。只有三层验证全部通过，才能得到 `candidate_passed`。

| 验证结果 | 含义 |
| --- | --- |
| `candidate_passed` | 原失败消失，直接影响范围正常，完整流水线通过 |
| `failed` | 至少一个必需验证明确失败，结果作为后续 Attempt 的新证据 |
| `inconclusive` | 环境、规则、证据或验证步骤不足，无法确认候选有效 |

流水线通过只能证明候选满足当前流水线覆盖的检查，不能证明完整业务正确性或生产安全性。

## 8. Domain Knowledge Pack 与 Case Library

### 8.1 职责边界

| 资产 | 回答的问题 | 权威边界 |
| --- | --- | --- |
| Domain Knowledge Pack | 当前产品、版本和场景应满足什么规则，可使用什么查询与验证能力 | 当前规则、Schema、工具和验证方法的能力依据 |
| Case Library | 相似问题过去如何诊断、修复和验证 | 提供假设、负向约束和验证线索，不直接决定答案 |

当前适用的 Domain Knowledge Pack、状态查询结果、外部控制边界、`baseline_commit`、依赖关系、业务意图和验证结果始终优先于历史案例。两类资产可以由同一个领域路由器共同定位，但必须保持独立版本、准入状态和失效条件。

### 8.2 首期存储

首期在同一个 Git 仓库中分目录保存领域规则和案例，不建设独立案例平台：

```text
enterprise-knowledge/
├── domains/
│   └── build-configuration/
│       ├── domain-pack.yaml
│       ├── rules.yaml
│       ├── schema.yaml
│       ├── tools.yaml
│       ├── validators.yaml
│       └── examples/
└── cases/
    └── build-configuration/
        ├── CASE-001.yaml
        └── CASE-002.yaml
```

- `domain-pack.yaml` 保存能力包版本、适用范围、组成引用、案例索引、外部控制边界引用和来源信息；
- 规则、Schema、工具、验证器和 Examples 分开维护，但必须由同一个能力包版本固定组合；
- 每个案例保存一次 Healing Session 的关键诊断、Attempt 与结果；
- 原始日志、候选和流水线报告只保存稳定引用，不在案例中重复复制；
- 只有明确字段筛选无法满足使用需求时，才评估专用检索和证据存储。

### 8.3 最小案例结构

```yaml
case:
  id: CASE-001
  domain: build_configuration
  context:
    product: product_a
    product_version: v3
    scene: feature_build
  initial_failure:
    task: validate_config
    error_code: INVALID_UPSTREAM
    commit: abc123
    ci_run: <CI 运行记录地址>
  knowledge:
    domain_version: v3
    rule_ids:
      - BC-UPSTREAM-003
  diagnosis:
    root_cause: 模式变化后基线未同步迁移
    evidence_refs: <证据引用>
  healing_session:
    session_ref: <Healing Session 记录地址>
    attempts: 2
    final_status: candidate_passed
  applicability:
    requires:
      - 当前业务意图是保留 independent 模式
    not_for:
      - 当前业务意图是恢复 integrated 模式
  record_status: complete
  admission_status: draft
```

记录完整性与案例准入必须分开：

- `record_status` 表示失败、诊断、修复和结果是否记录完整；
- `admission_status` 使用 `draft → reviewed → admitted → stale / retired`；
- AI 可以在 Healing Session 结束后生成 Case Draft，但不能自动将案例提升为已审核或已准入；
- 成功、失败、误修、人工否决和回滚都可以成为完整案例。

### 8.4 案例使用规则

| 使用阶段 | Case Library 输出 | 当前流程必须完成的工作 |
| --- | --- | --- |
| 诊断之前 | 对相似案例中的根因假设进行排序 | 使用当前失败材料、知识包和状态查询逐项确认或反驳，不把排序当作结论 |
| 自适应规划期间 | 提供成功、失败、误修和人工否决策略及其适用条件 | 比较当前上下文差异，生成适配后的候选，不重放旧 Patch |
| 验证规划期间 | 提供历史上能够暴露回归的验证层级、命令和成本 | 以当前影响范围、知识包 Validator 和三层验证为下限，不用历史案例降低门禁 |

```text
按领域、产品、版本和场景筛选
  → 比较失败任务、错误码、关键日志和最近变更
  → 列出相同点、不同点和未知点
  → 提取可能根因、负向约束和验证线索
  → 使用当前规则与当前状态重新建立证据
  → 生成当前候选并重新验证
```

案例遵循 `Retrieve → Compare → Adapt → Verify`，不得执行 `Retrieve → Replay`。日志相似度只能帮助检索，不能证明根因相同，也不能授予修改或执行权限。没有适用案例时，企业领域诊断仍可依靠当前规则和状态查询继续进行。

一个 Healing Session 只在结束后形成一个 Case Draft；各个失败 Attempt 作为同一案例中的尝试轨迹和负向约束保存，不分别制造多个孤立案例。

## 9. 最小系统组成与记录

| 部分 | 作用 |
| --- | --- |
| 失败信息收集器 | 收集失败任务、日志、代码版本、最近变更和运行环境 |
| 领域路由器 | 选择通用问题路径或企业知识域，并定位兼容的知识包、工具集和案例索引 |
| 知识与工具路由器 | 加载兼容的 Domain Knowledge Pack、受限工具、当前状态查询和适用案例 |
| 修复 Agent | 形成统一诊断结论与修复约束，管理根因假设，生成每个完整候选并自主规划后续行动 |
| 验证执行器 | 在隔离环境中运行三层验证并返回新证据 |
| Healing Session 记录器 | 保存 Attempt、状态、停止原因和 Case Draft |

```text
失败信息收集器
  → 领域路由器
  → 知识与工具路由器
  → 统一诊断结论与修复约束
  → Healing Session
      → 修复 Agent
      → 验证执行器
      ↺ 新证据返回当前 Healing Session
  → Healing Session 结果与 Case Draft
```

每个 Healing Session 至少保存：

1. 初始失败材料和 `baseline_commit`；
2. 路径选择及其依据；
3. 每轮根因假设、证据快照和未知项；
4. 每个完整候选及其生成理由；
5. 三层验证结果与新增失败；
6. AI 对新失败关系的判断依据；
7. 最终状态和停止原因。

## 10. 落地顺序

### 10.1 第一阶段：通用问题闭环

先支持边界明确且验证命令稳定的问题：

- 格式化和 lint；
- 类型检查与编译错误；
- 局部、稳定可重现的测试失败；
- 有明确解析工具的公开依赖问题。

第一阶段应验证完整 Healing Session 契约、5 次上限、候选隔离、证据累积、三层验证和提前停止机制。

### 10.2 第二阶段：一个企业领域

选择一个规则清楚且已有验证工具的内部领域，例如构建配置，建立：

- 带版本、适用范围、Schema、来源和 Validator 的 Domain Knowledge Pack；
- 稳定编号的业务规则；
- 当前状态和参数来源查询；
- 专用检查和试运行；
- 统一案例格式和一组真实历史失败；
- 按明确字段筛选案例的简单程序。

使用同一组真实故障比较三种输入条件：

```text
A. 日志、代码和通用工具
B. A + Domain Knowledge Pack + 当前状态查询
C. B + Case Library
```

B 用于验证企业知识是否提高根因和候选正确率；C 用于验证案例是否进一步缩短诊断时间或减少无效 Attempt。未观察到增益时，不扩建相应知识或案例基础设施。

### 10.3 第三阶段：扩展领域

前一个领域通过实验后，再增加新的构建、测试或发布领域，并积累成功、失败和误修案例。领域扩展不得改变通用 Healing Session 契约和验证标准。

### 10.4 后续扩展：执行问题恢复

网络、资源、Runner 和 Flaky 问题由未来的执行恢复层处理。执行恢复成功只表示流水线恢复运行，不表示根因已经消除；恢复后仍存在确定性失败时，再进入本方案。

## 11. 评估指标

| 指标 | 回答的问题 |
| --- | --- |
| 领域识别与路由正确率 | 问题是否进入正确路径，并选择了兼容的知识包和工具集 |
| 根因正确率 | 根因是否解释了主要证据，而非只处理表面现象 |
| 首轮候选通过率 | Attempt 1 通过全部验证的比例 |
| Healing Session 通过率 | 5 次上限内获得 `candidate_passed` 的比例 |
| 平均通过轮次 | 成功 Healing Session 平均需要多少个 Attempt |
| `no_progress` 比例 | 有多少 Healing Session 因缺少有效增量而停止 |
| `inconclusive` 比例 | 有多少 Healing Session 因证据或条件不足而停止 |
| 回归拦截率 | 第二层和第三层验证拦截了多少错误候选 |
| 平均修复时间 | 相比人工定位是否缩短恢复时间 |
| 额外验证成本 | 自适应循环增加了多少流水线时间与计算资源 |
| 案例有效帮助率 | Case Library 是否减少诊断时间或无效 Attempt |
| 案例误导率 | 历史案例是否引入了不适用的根因或修复方向 |

指标必须分别统计通用问题、各企业领域、失败类型和复杂度，不能用大量简单问题的成功掩盖企业领域问题的低有效率。

## 12. 可行性与成立条件

通用问题路径适合日志定位明确、修改范围受控、失败可稳定重现且验证命令可靠的问题。效果主要取决于失败材料质量、根因证据、上下文完整性和测试覆盖。

企业领域路径还依赖：

- 带版本与适用范围的正确领域规则；
- 当前状态、参数值和来源查询；
- 能证明配置或参数组合有效的专用验证；
- 可追溯的业务意图；
- 受控、可隔离的候选验证环境。

只有内部文档而没有适用范围、当前状态查询和专用验证时，企业领域路径无法稳定成立。Case Library 可以提高效率，但不是企业领域诊断成立的前提。

> 方案采用“分类诊断 + 有界自适应修复 + 独立验证”的统一闭环。系统固定证据、隔离、验证和停止边界，同时保留 AI 对后续诊断与修复路径的自主选择。

## 14. 待验证问题

- 通用问题与企业领域问题的路由信号在真实故障中的准确性；
- 根因证据要求是否能降低只修复表面现象的比例；
- 5 次上限在成功率、时间和计算成本之间是否合理；
- 候选从固定基线重建是否能稳定避免轮次间污染；
- AI 自主选择后续策略是否产生足够的信息增量；
- 三层验证对错误候选和回归的拦截效果；
- Domain Knowledge Pack 按领域、产品、构建系统、版本和场景过滤后是否降低错误规则混入；
- Case Library 是否减少诊断时间和无效 Attempt，同时不增加误修；
- `no_progress` 与 `inconclusive` 的结束记录是否足以支持后续人工分析。
