# CI 自愈通用与企业领域诊断修复技术方案评审讲解稿

> [!warning] 材料定位
> 本材料是配合交互图使用的 20 分钟讲解稿。只讲清楚每个节点做什么、输出什么、输出如何被后续节点使用。方案仍处于设计阶段，尚未经过真实故障实验验证。

## 二、开场：0:00～1:00

### 可直接讲述

这套方案解决的是：当 CI 出现确定性失败后，如何让 AI 在明确的证据、隔离和验证边界内完成诊断与修复候选验证。

方案不假设 AI 一次就能修复成功。一次 CI 失败会创建一个 Healing Session，AI 可以根据每轮验证产生的新证据，自主调整下一轮诊断和修复策略，最多验证 5 个完整候选。

整个流程固定四类工程边界：失败事实必须可追溯、每个候选都从固定基线生成、候选必须通过三层验证、Session 必须能够成功或带原因停止。

本方案只负责形成并验证修复候选，不负责权限扩大、人工审核、自动合并、发布和部署，也暂不处理网络、Runner、资源不足和 Flaky 等执行恢复问题。

## 三、入口与领域识别：1:00～3:30

### 节点 1：CI 失败

**做什么**

识别一次需要进入诊断流程的确定性 CI 失败，保存失败流水线、作业、任务和命令的定位信息。

**输出什么**

一次诊断与修复流程的触发信号，以及初始失败运行的引用。

**怎么被使用**

失败信息收集器根据该引用提取日志、代码版本、环境和相关上下文，形成统一失败材料。

**讲解句**

> 这个节点只表示“发生了需要诊断的确定性失败”，还不判断根因，也不直接生成 Patch。

### 节点 2：失败材料

**做什么**

统一收集失败命令、原始日志、错误位置、退出码、当前提交、最近变更、相关代码与配置、依赖关系、运行环境和工具版本。

**输出什么**

一份可追溯、可复现、只包含可观察事实的失败材料包。

**怎么被使用**

领域识别使用这些事实判断应进入通用路径还是企业领域路径；后续诊断也使用同一份材料建立根因证据。

**讲解句**

> 失败材料只陈述事实，不提前写入问题分类、根因或修复结论，避免采集阶段的判断污染后续诊断。

### 节点 3：领域识别

**做什么**

判断正确解释当前根因是否需要企业内部规则或当前业务状态；如果需要，再识别足以选择兼容知识包和工具集的企业知识域。

**输出什么**

- 通用路径或企业领域路径；
- 主领域和必要的次领域；
- 路由证据和备选领域；
- 选中的 Domain Knowledge Pack 标识与版本；
- 领域冲突、知识包缺失或上下文缺失等路由缺口。

**怎么被使用**

通用问题进入通用诊断；企业领域问题进入知识与工具路由。无法唯一识别领域时直接输出 `inconclusive`，不允许猜测内部语义。

**讲解句**

> 领域识别只决定“使用哪类知识和能力”，不在这个节点预测“参数缺失、参数冲突还是继承错误”等具体根因。

## 四、两条诊断路径：3:30～9:30

### 节点 4：通用诊断

**做什么**

使用日志、仓库代码、测试、配置、依赖、最近变更和公共软件工程知识建立根因假设，并通过编译器、静态分析、测试和 Git 差异等证据排除不成立的假设。

**输出什么**

通用诊断材料，包括根因假设、支持或反驳证据、影响范围、候选修复方向和未知项。

**怎么被使用**

这些材料进入统一诊断结论节点，被整理为 Healing Session 可以消费的修复约束与验证要求。

**讲解句**

> 通用诊断不是看到某条报错就修改对应文件，而是要求根因能够解释日志、代码状态和最近变更之间的关系。

### 节点 5：知识与工具路由

**做什么**

根据领域、产品、构建系统、版本和场景等结构化信息限定知识空间，只加载当前问题兼容的知识包、状态查询、受限工具、Validator 和案例索引。

**输出什么**

本次企业领域诊断允许使用的能力集合，以及能力缺失、版本不兼容或规则冲突信息。

**怎么被使用**

后续节点只能在这个兼容范围内读取规则、查询当前状态、检索案例和执行专项验证，避免混入其他产品、版本或场景的知识。

**讲解句**

> 这个节点做的是能力选择，不是根因判断；加载某个工具也不代表系统获得新的写权限。

### 节点 6：Domain Knowledge Pack

**做什么**

提供当前企业领域的版本化能力包，组合该领域的 Knowledge、Rules、Schema、Examples、State Queries、Tools、Validators、来源信息和外部控制边界引用。

**输出什么**

当前产品、版本和场景适用的规则、参数结构、查询方式、可用工具和专项验证能力。

**怎么被使用**

状态查询节点按能力包定义获取当前实际状态；企业领域诊断证据节点使用其中的适用规则和 Validator；后续验证使用其中声明的企业专项检查。

**讲解句**

> Domain Knowledge Pack 不是一组散乱文档，而是一个有版本、有适用范围、有来源、也有验证能力的领域能力包；它提供规则依据，但不直接输出当前问题的根因。

### 节点 7：查询当前状态

**做什么**

按照 Domain Knowledge Pack 定义的只读查询方式，获取当前参数值、来源、继承和覆盖关系、基线以及实际生效结果。

**输出什么**

带来源的当前状态快照，以及不可查询、缺失或互相冲突的状态信息。

**怎么被使用**

企业领域诊断证据将“规则要求”与“当前实际状态”进行对照；后续根因诊断据此判断错误发生在哪个配置、继承或基线关系中。

**讲解句**

> 规则说明“应该怎样”，状态查询说明“现在实际怎样”；只有规则没有当前状态，仍然无法可靠诊断企业领域问题。

### 节点 8：Case Library

**做什么**

根据领域、产品、版本、场景、失败任务和错误特征检索历史 Healing Session，比较当前案例与历史案例的相同点、不同点和未知点。

**输出什么**

历史根因假设、成功或失败的修复策略、人工否决方向、负向约束和验证线索。

**怎么被使用**

案例输出进入 Session 上下文，用于帮助自适应规划排序假设、规避已知无效方向和补充验证；它不能写入当前适用规则或当前状态，也不能直接证明当前根因。

**讲解句**

> Case Library 采用 `Retrieve → Compare → Adapt → Verify`，而不是直接重放历史 Patch；当前规则、当前状态和当前验证结果始终高于历史案例。

### 节点 9：企业领域诊断证据

**做什么**

把领域识别、能力包、当前状态、最近变更、业务意图和专项验证能力整理成一份运行时事实包，并显式保留缺失或冲突信息。

**输出什么**

- 领域识别结果和知识包版本；
- 当前场景适用的规则；
- 当前值、来源、继承和基线；
- 与失败相关的最近变更；
- 已确认的业务意图；
- 可用专项验证；
- 证据缺口。

**怎么被使用**

统一诊断结论节点基于这些事实推理根因、因果关系、修复边界和必需验证。

**讲解句**

> 这个节点回答“当前已经确认了哪些企业领域事实”，不直接回答根因是什么，也不生成修复候选。

### 节点 10：统一诊断结论

**做什么**

把通用诊断材料或企业领域诊断证据综合为同一种候选生成契约。

**输出什么**

- 路径选择及来源；
- 一个或多个根因假设；
- 失败、状态、变更与根因之间的因果证据链；
- 直接影响范围；
- 必须保留、允许修改和禁止修改的边界；
- 原失败、影响范围、企业专项和完整 CI 等必需验证；
- 尚未确认的未知项。

**怎么被使用**

自适应规划使用这份契约决定首轮候选和后续策略。契约不完整时不能进入候选生成，而是以 `inconclusive` 结束。

**讲解句**

> 企业领域诊断证据是事实层，统一诊断结论是推理层；这个节点的输出不是 Patch，而是 Healing Session 生成候选时必须遵守的根因、边界和验证契约。

## 五、Healing Session Loop：9:30～18:30

### 节点 11：自适应规划

**做什么**

读取统一诊断结论和当前 Session 上下文，更新根因假设、未知项和负向约束，自主选择下一步最有价值的诊断或修复行动。

**输出什么**

本轮目标、采用的诊断或修复策略、预期信号、候选范围，以及需要增加的专项验证。

**怎么被使用**

Attempt 节点根据该规划相对固定基线生成完整候选；如果规划认为证据不足，也可以先补充证据或主动停止。

**讲解句**

> 第 2～5 轮没有固定脚本。AI 可以深化或替换根因、换策略、调整范围或先补证据；系统只固定记录、隔离、验证和停止边界。

### 节点 12：Attempt N

**做什么**

在干净、隔离的环境中，相对同一个 `baseline_commit` 生成一个完整修复候选。只有候选进入验证时才增加 Attempt 计数。

**输出什么**

完整候选引用、本轮证据快照、根因假设、候选生成理由和 Attempt 序号。

**怎么被使用**

完整候选依次进入三层验证；候选本身不会成为下一轮的代码基底。

**讲解句**

> `max_attempts = 5` 表示最多验证 5 个完整候选，不是必须运行 5 轮，也不是把思考和查询次数限制为 5 次。

### 节点 13：① 原失败复验

**做什么**

在候选上重新运行最初失败的命令或任务，确认原始失败是否消失。

**输出什么**

`passed` 或 `failed`，以及失败时产生的新日志和错误位置。

**怎么被使用**

通过后进入影响范围验证；失败时不再消耗后续验证资源，结果直接进入本轮决策和 Session 上下文。

**讲解句**

> 第一层先回答最基本的问题：候选是否真的消除了最初的失败，而不是只改变了错误表现。

### 节点 14：② 影响范围验证

**做什么**

根据候选差异和依赖关系，运行受影响模块测试、调用方或下游检查、配置组合检查、依赖解析、构建试运行和必要的企业专项 Validator。

**输出什么**

直接影响范围内的验证结果、相邻回归、新失败及其证据。

**怎么被使用**

通过后进入完整 CI；失败时结果进入本轮决策，成为下一轮调整候选范围或策略的依据。

**讲解句**

> 第二层用于拦截“原错误消失了，但相关模块、下游或企业规则被破坏”的表面修复。

### 节点 15：③ 完整 CI

**做什么**

在当前候选上执行仓库声明的完整验证流水线。

**输出什么**

完整 CI 的通过或失败结果、失败任务和新增日志。

**怎么被使用**

结果进入本轮决策。只有原失败、影响范围和完整 CI 全部通过，才允许输出 `candidate_passed`。

**讲解句**

> 完整 CI 通过只证明候选满足当前流水线覆盖的检查，不证明完整业务正确性或生产安全性。

### 节点 16：本轮决策

**做什么**

综合本轮候选、三层验证、新失败、历史 Attempt 和剩余边界，决定当前 Session 是通过、继续还是停止。

**输出什么**

- `pass`、`continue` 或 `stop`；
- 决策理由；
- 新失败与候选的关系：`related`、`unrelated` 或 `uncertain`；
- 继续时的下一轮目标和预期信号；
- 停止时的终止原因。

**怎么被使用**

`pass` 进入 `candidate_passed`；`continue` 将新增证据写入 Session 上下文；`stop` 进入未解决退出。

**讲解句**

> 方案不为新失败关系设置固定评分阈值，但要求保存主要判断依据；只要必需验证仍失败，就不能标记为通过。

### 节点 17：Session 上下文

**做什么**

跨轮保存初始诊断契约、每轮日志、验证结果、被支持或否定的假设、未知项、历史案例线索和负向约束。

**输出什么**

下一轮自适应规划使用的累积证据快照。

**怎么被使用**

自适应规划基于该上下文决定下一轮是深化诊断、替换根因、调整候选、增加验证还是停止。

**讲解句**

> 跨轮累积的是证据，不是失败候选的代码状态。核心原则是：证据持续累积，代码状态每轮从基线重建。

### 节点 18：`candidate_passed`

**做什么**

记录首个通过全部必需验证的候选，并立即结束当前 Healing Session。

**输出什么**

通过候选、完整验证凭证、Attempt 轨迹和 `candidate_passed` 状态。

**怎么被使用**

这些材料可以交给本方案之外的人工审核、采用、合并和发布流程，也可以在 Session 结束后形成 Case Draft。

**讲解句**

> 首次完整通过就结束，不继续寻找更优候选；同时必须明确 `candidate_passed` 不等于已采用、已合并或已发布。

### 节点 19：未解决退出

**做什么**

在继续尝试没有有效增量，或者证据、规则、环境、验证条件与资源不足时，结束当前 Healing Session。

**输出什么**

- `no_progress`：没有足以支持继续的证据或策略增量；
- `inconclusive`：仍无法形成可靠结论；
- 对应的停止原因和完整 Attempt 轨迹。

**怎么被使用**

结果交给人工分析或后续补证据流程，并用于形成 Case Draft、改进领域知识、工具、Validator 和停止规则。

**讲解句**

> 达到 5 次不是唯一停止条件，可以提前停止；第 5 个候选仍未通过时，有效方向已经耗尽就输出 `no_progress`，仍有方向但无法继续验证就输出 `inconclusive`。

## 六、收尾：18:30～20:00

### 6.1 用一句流程串起所有节点

```text
CI 失败
  → 收集统一失败事实
  → 识别所需知识域
  → 通过通用或企业领域路径建立诊断证据
  → 形成统一的根因、修复边界与验证契约
  → AI 相对固定基线生成完整候选
  → 依次执行原失败、影响范围和完整 CI 验证
  → 通过则结束，失败则累积证据并自适应规划下一轮
  → 最多验证 5 个候选，或在证据不足、无进展时提前停止
```

### 6.2 最后强调三条边界

1. **企业领域知识不是直接给答案。**Domain Knowledge Pack 提供适用规则和能力，状态查询提供当前事实，Case Library 提供历史先验，统一诊断结论才负责根因推理。
2. **循环不是在失败 Patch 上不断叠加。**证据跨轮累积，每个候选都从同一个 `baseline_commit` 洁净重建。
3. **通过状态不是采用状态。**`candidate_passed` 只表示候选通过本方案规定的验证，不代表获得权限、通过人工审核、完成合并或可以发布。

### 6.3 结束语

这套方案的核心不是保证 AI 一定修复成功，而是把 AI 的诊断和修复能力放入一个可解释、可追溯、可验证、可提前停止的工程闭环。后续需要通过真实故障实验验证领域路由、知识增益、5 次上限、三层验证和停止判断是否有效。

## 七、节点输出速查

| 节点 | 输出 | 下游用途 |
| --- | --- | --- |
| CI 失败 | 失败运行引用与触发信号 | 启动失败材料收集 |
| 失败材料 | 可追溯的统一事实包 | 领域识别和根因诊断 |
| 领域识别 | 路径、领域、证据、知识包版本和路由缺口 | 选择通用诊断或企业能力空间 |
| 通用诊断 | 根因假设、证据、影响范围和未知项 | 形成统一诊断结论 |
| 知识与工具路由 | 兼容能力包、查询、工具、Validator 和案例索引 | 限制企业诊断能力范围 |
| Domain Knowledge Pack | 适用规则、Schema、工具和验证能力 | 查询状态、建立证据、执行专项验证 |
| 查询当前状态 | 当前值、来源、继承、基线和生效结果 | 将规则与实际状态对照 |
| Case Library | 历史假设、差异、负向约束和验证线索 | 辅助诊断和自适应规划 |
| 企业领域诊断证据 | 规则、状态、变更、意图、验证能力和证据缺口 | 支持根因和修复边界推理 |
| 统一诊断结论 | 根因、证据链、影响范围、修复边界和必需验证 | 约束候选生成和验证 |
| 自适应规划 | 本轮目标、策略、预期信号和验证计划 | 指导完整候选生成 |
| Attempt N | 相对固定基线的完整候选及生成依据 | 进入三层验证 |
| 原失败复验 | 原失败是否消失及新日志 | 决定是否进入第二层 |
| 影响范围验证 | 相关模块、下游和企业专项验证结果 | 拦截相邻回归并决定是否进入第三层 |
| 完整 CI | 仓库完整流水线结果 | 作为候选通过的最后门禁 |
| 本轮决策 | `pass`、`continue` 或 `stop` 及依据 | 路由到成功、下一轮或停止 |
| Session 上下文 | 跨轮累积的证据、反证、未知项和负向约束 | 支持下一轮自适应规划 |
| `candidate_passed` | 通过候选、验证凭证和 Attempt 轨迹 | 交给外部审核与采用流程 |
| 未解决退出 | `no_progress` 或 `inconclusive` 及停止原因 | 人工分析、补证据与系统改进 |
