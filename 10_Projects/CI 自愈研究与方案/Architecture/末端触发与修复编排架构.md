# 末端触发与修复编排架构

> [!warning] 设计边界
> 本文是从 Nx `fix-ci` 公开触发位置延伸出的自有架构设计，不代表 Nx 已公开的内部组件或服务拓扑。原文能够确认的事实见 [[CI 自愈触发机制 - nx fix-ci 末端触发步骤]]。

## 设计问题

如何在 CI tasks 结束后，以不覆盖原 CI 结果的方式收集失败、判断修复资格、派发候选修复和验证，并处理末端 step 未执行、重复执行或运行不完整等情况。

## 设计假设

- CI provider 能提供 pipeline、job、attempt 和 commit identity。
- task runner 能产生结构化 task completion events。
- 修复系统不能直接改变原 task 的结果。
- 候选写回会产生新的 commit，并由外层 CI 重新执行宿主门禁。
- Nx 未公开的 `fix-ci` 聚合和调度行为不作为本设计的事实依据。

## 逻辑组件

| 组件 | 设计职责 | 明确不负责 |
| --- | --- | --- |
| Run Aggregator | 收集 job、task、log reference 与 completion event | 生成代码修复 |
| Terminal Trigger | 在相关执行单元末端请求一次 finalization | 宣布 PR 已变绿 |
| Completion Barrier | 判断预期事件是否收齐并生成 sealed snapshot | 推测缺失事件为成功 |
| Eligibility Resolver | 根据 branch、task、policy 和 PR 状态筛选 failure | 解释代码根因 |
| Repair Orchestrator | 组织上下文、候选生成和验证 | 持有长期 VCS 写权限 |
| Verification Runner | 对候选执行声明过的验证计划 | 代替 Required Checks |
| Writeback Gateway | 使用受限凭据发布 suggestion 或 commit | 接受未绑定 HEAD 的候选 |
| Async Watchdog | 处理末端 step 未执行或 runner 丢失 | 覆盖原 CI 失败状态 |

## 建议状态

```text
RECORDING
  -> FINALIZING
  -> NO_OP_HEALTHY
  -> INCOMPLETE
  -> NO_ELIGIBLE_FAILURE
  -> REPAIR_DISPATCHED
  -> AWAITING_OUTER_CI
  -> FINALIZER_ERROR
```

这些状态属于自有设计。`NO_OP_HEALTHY` 只能在 completion barrier 证明预期事件收齐后使用；运行不完整时使用 `INCOMPLETE`。

## 身份与幂等

建议将以下维度纳入幂等键：

```text
repository
+ ci_execution_id
+ execution_environment
+ run_attempt
+ head_sha
+ trigger_version
```

候选、验证回执和写回授权都应绑定同一 `head_sha`。HEAD 变化后，旧候选不能直接写回。

## 时间预算

建议区分：

- trigger deadline：末端 step 可以等待多久；
- analysis deadline：上下文构建和候选生成可以运行多久；
- verification deadline：候选验证可以运行多久；
- writeback deadline：验证结果保持有效多久。

当末端 job 剩余时间不足时，Terminal Trigger 只派发异步 repair workflow，不在原 job 内阻塞完成全部修复。

## 权限边界

- Aggregator、Trigger 和 Verification Runner 不持有仓库长期写权限。
- Writeback Gateway 使用短期、单用途 capability。
- capability 绑定 repository、PR、head SHA、candidate fingerprint 和允许动作。
- 自动写回失败不能把原 CI 状态改成成功。

## 外层验证边界

自有修复微环最多证明候选满足声明的验证计划。新 commit 是否可合并，仍由 SCM/CI provider 配置的 Required Checks 决定。

## 需要 ADR 的问题

- Trigger 在原 main job 同步等待，还是只派发异步 workflow？
- 多 agent job 的 trigger 如何去重与聚合？
- `INCOMPLETE` 是否阻止生成任何候选？
- Finalizer 自身故障是否成为独立 Required Check？
- Watchdog 使用 CI webhook、schedule 还是 Nx Cloud execution event？

## 需要实验的问题

- runner cancellation、job timeout 和网络中断时末端 step 的实际执行率；
- 多 job、多 agent 与 retry 下的重复派发概率；
- 同步等待与异步修复对 TTG 和 CI 资源的影响；
- completion barrier 对动态 affected task set 的准确性。
