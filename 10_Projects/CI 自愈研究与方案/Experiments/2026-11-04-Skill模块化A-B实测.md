## 6. 宿主修订 r2：MCP 初始化被模型门禁误拦截

最初 handoff 试次的实际 Agent 报告案例工具没有暴露，MCP 服务没有收到搜索或原文调用。检查确认 `tools.mcp` 配置已正确保存，工具名称、允许清单及当前 iCode schema 都有效。

根因是评测器的 HTTP 计时包装对所有 `httpx` 请求调用 Skill 注册前置检查。iCode 在加载 Skill 前初始化 MCP；MCP 的 HTTP initialize 因尚未注册 Skill 被误当作模型请求拒绝。iCode 将单个 MCP 连接异常记录为 Warning 后继续构建 Agent，返回空工具列表；旧观察器没有保留该 Warning，所以空 stderr 不能证明接入正常。

r2 在 HTTP 计时器增加可选请求过滤器，并在 A/B 执行宿主中只对已配置模型网关的精确 scheme/host/port 应用注册门禁与模型计时。其他已授权 MCP 请求不经过该模型门禁；不记录 URL、headers、prompt 或 body。未指定过滤器的既有调用保持原行为。

[r2 无模型 canary](/Users/zhujiayi/personal/01_program/03_github/CI-selfhealing/evals/ci-self-healing/runs/ab-modular-20261104-01/diagnostics/mcp-transport-r2/result.json) 在真实 macOS sandbox 内验证：MCP 可在 Skill 注册前暴露两个工具并实际完成搜索与完整原文读取；未注册的模型请求仍在发出网络请求前被阻止。该 canary 不调用模型。

按 [r2 修订记录](/Users/zhujiayi/personal/01_program/03_github/CI-selfhealing/evals/ci-self-healing/runs/ab-modular-20261104-01/harness-revision-2.json)，发现时已有 **5 个受影响试次启动**，其中 A 版 3 个、B 版 2 个；另有 9 个未启动 handoff adapter 得到修订。五个受影响原始记录保留，按 [r2 补测清单](/Users/zhujiayi/personal/01_program/03_github/CI-selfhealing/evals/ci-self-healing/runs/ab-modular-20261104-01/supplemental-r2-manifest.json) 新建五个隔离试次。补测选择覆盖已确认受影响的启动记录，不参考模型裁决是通过还是失败。

## 7. 宿主修订 r3：默认资源登记深度不足

企业深层资源出现 `resource_not_found` 后，确认实际 iCode 默认只登记至 depth 2，企业 Profile 的目录与细则、独立策略或案例源路径未全部进入原生 Skill 资源清单。资源文件存在不等于已被宿主登记，因此模型无法通过原生资源工具访问这些文件。
